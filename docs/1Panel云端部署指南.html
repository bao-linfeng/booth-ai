从一台云服务器，
到上线的展台方案平台。

基于 1Panel 的单机生产部署手册。完整覆盖面板安装、数据库与队列、API 与 Worker、双门户、对象存储、证书与日常运维。

适用：1Panel v2 · Ubuntu 24.04 LTS项目核对日期：2026-10-15部署方式：Docker Compose + OpenResty
阅读方式：首次部署按 01 → 10 顺序执行。全文的 example.com、仓库地址和发布版本均为占位符，请替换为实际值。生产 Compose 在第 05 节提供，需要在云服务器创建；当前仓库只有开发编排。

00部署全景与约定

采用一台 Linux 云服务器承载全部组件。1Panel 管理 OpenResty、证书、文件和容器；API 与 Worker 使用项目已有 Dockerfile 的 runtime 阶段，前端构建成静态文件。

REQUEST FLOW
浏览器 ── HTTPS :443 ── 1Panel / OpenResty（宿主机网络）
                         ├─ booth.example.com  → client 静态文件
                         │    └─ /api/*         → 127.0.0.1:3000
                         ├─ admin.example.com  → admin 静态文件
                         │    └─ /api/*         → 127.0.0.1:3000
                         └─ files.example.com  → 127.0.0.1:19000 → Silo S3

Docker 私有网络： API + Worker → PostgreSQL 17 / Redis 7.4 / Silo
一次性初始化：   migrate → 数据库迁移；storage-init → 创建私有 bucket
对象本文约定说明
参展商门户https://booth.example.comVue history 路由，需要 index.html 回退。
管理后台https://admin.example.comVben web-antd；生产 API 基地址为 /api。
资源域名https://files.example.com私有桶的签名下载，保持 Host 与 URL 路径不变。
后端发布目录/opt/booth-ai源代码、编排与持久化数据分开存放。
生产项目名booth-ai-prod所有运维命令固定同一 Compose 项目名。

单机部署 这是可运维的单机方案，不提供多机高可用。AI 通过供应商 API 调用，通常不需要 GPU；实际 CPU、内存和磁盘需按并发、上传量与图片存储量扩容。

01云服务器准备

  1. 购买干净的 Ubuntu 24.04 LTS、x86_64 云服务器，建议起点为 4 核 / 8 GB / 100 GB SSD。服务器同时编译管理后台时建议 16 GB 内存，或在构建机产出前端后上传。
  2. 准备公网 IP 和三个域名，分别创建 A 记录指向服务器。只有实际配置 IPv6 时才添加 AAAA 记录。
  3. 中国大陆云主机使用域名提供网站服务时，按云厂商要求完成备案；确认服务器能访问 Docker 镜像仓库、npm registry、灵通认证接口和 AI 供应商。
  4. 通过云控制台或 SSH 登录，以下示例以 root 执行；普通用户先执行 sudo -i。不要把示例命令直接放进 Windows PowerShell。
端口云安全组 / 系统防火墙用途
22/TCP仅运维 IPSSH；如果改过端口，以实际为准。
80、443/TCP公网开放网站、HTTPS 和 HTTP-01 证书验证。
面板实际端口仅运维 IP安装时设置，例如 18080，不要假定默认端口。
3000、19000不开放公网仅绑定 127.0.0.1，由 OpenResty 转发。
5432、6379、9001不开放公网数据库、Redis、Silo 控制台仅供内部使用。
BASH · 基础工具
sudo -i
apt-get update
apt-get install -y curl ca-certificates git openssl rsync
timedatectl set-ntp true
timedatectl status
uname -m
free -h
df -h

保持系统时间同步：S3 签名 URL、会话与证书均依赖准确时间。开放规则需同时检查云安全组和主机防火墙。

02安装 1Panel

在服务器 SSH 终端执行官方 v2 交互式安装命令。按提示选择安装目录（本文使用 /opt）、面板端口、用户名、密码和安全入口；需要安装 Docker 时同意安装。

BASH · 官方安装入口
bash -c "$(curl -sSL https://resource.fit2cloud.com/1panel/package/v2/quick_start.sh)"
  1. 保存终端打印的访问地址、用户名和安全入口，访问格式为 http://服务器公网IP:面板端口/安全入口。
  2. 在云安全组与主机防火墙放行这个面板端口，仅允许自己的运维 IP。
  3. 登录后进入应用商店，安装 OpenResty，使用 80 / 443 监听端口。确认不存在其他 Nginx、Apache 或容器占用这两个端口。
  4. 在容器详情确认 OpenResty 的网络模式为 host。本文代理地址依赖它与宿主机共享网络；bridge 模式中的 127.0.0.1 指向容器自身，不能直接套用本文地址。
  5. 在面板设置中配置面板 HTTPS、强密码及可用的双因素认证。网站证书与面板自身证书是分别配置的。
BASH · 安装确认
1pctl version
1pctl status
1pctl user-info
docker version
docker compose version
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
检查点：能打开面板、Docker 和 Compose v2 可用、OpenResty 正常运行。面板菜单名称可能随小版本调整，按“应用商店 / 容器 / 网站 / 证书”等功能入口操作。

将已验证的发布版本放到 /opt/booth-ai/source。使用只读部署密钥拉取私有仓库，或通过 1Panel 文件管理上传源码压缩包并解压；不要上传本地 node_modules。

04生产环境变量

先生成一次随机密钥，再在 1Panel 文件编辑器中调整域名。下面的脚本遇到已有 .env 会停止，避免覆盖运行中的加密密钥。

BASH · 仅首次创建
(
  set -eu
  cd /opt/booth-ai
  if [ -e .env ]; then
    echo '.env 已存在，请编辑现有文件，不要重新生成密钥。'
    exit 1
  fi
  umask 077
  {
    for key in POSTGRES_PASSWORD REDIS_PASSWORD S3_SECRET_KEY SESSION_SECRET AI_MODEL_ENCRYPTION_KEY; do
      printf '%s=%s\n' "$key" "$(openssl rand -hex 32)"
    done
    printf 'S3_ACCESS_KEY=booth%s\n' "$(openssl rand -hex 8)"
    cat <<'ENV'
APP_VERSION=initial
CLIENT_PUBLIC_URL=https://booth.example.com
S3_PUBLIC_ENDPOINT=https://files.example.com
CORS_ORIGINS=https://booth.example.com,https://admin.example.com
EXTERNAL_API_URL=https://api.lingtong.net.cn
SESSION_TTL_SECONDS=86400
TRUST_PROXY=1
SMTP_HOST=
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM=
PROJECT_NOTIFICATION_WEBHOOK_URL=
PROJECT_NOTIFICATION_WEBHOOK_SECRET=
ENV
  } > .env
  chmod 600 .env
)
变量填写要求 / 作用
APP_VERSION本地后端镜像标签，首次为 initial；后续每次更新改成新的发布标识，例如 release-20261015-01。
POSTGRES_PASSWORD / REDIS_PASSWORD示例使用十六进制随机值，直接放入连接 URI 不需要额外编码。数据库已有数据后，修改环境变量不会自动修改库内密码。
SESSION_SECRET至少 32 字节；API 和 Worker 使用同一份配置。
AI_MODEL_ENCRYPTION_KEY必须为 64 位十六进制，用于数据库中的 AI 凭据加密。备份时必须保留，丢失后已有密文不能正常解密。
S3_PUBLIC_ENDPOINT浏览器可访问的 HTTPS 文件域名，不带 bucket 或自定义路径前缀。不能写 silo、localhost 或容器 IP。
CORS_ORIGINS两个 HTTPS 前端来源，逗号分隔，不带末尾斜杠，不填通配符。
TRUST_PROXY=1适用于本文单层 OpenResty 代理且 API 只监听回环地址。接入 CDN 或负载均衡时，重新核对代理链和真实 IP 配置。
EXTERNAL_API_URL灵通企业认证 API，必填。全新数据库不会自动生成独立的本地管理员密码。
SMTP_*选填。开启时同时配置 HOST、FROM；使用认证时配置 USER / PASSWORD。465 通常 secure=true，587 通常 secure=false。邮件链接使用 CLIENT_PUBLIC_URL。
PROJECT_NOTIFICATION_WEBHOOK_*选填。URL 生产要求 HTTPS；配置 URL 后 SECRET 至少 32 字节。未配置时相关通知留在 outbox。
密钥与前端变量分开：后端密钥只能放在服务器 .env。任何 VITE_* 变量都会进入浏览器可见的构建产物，不能放数据库密码、S3 Secret 或 AI API Key。AI 供应商密钥在管理后台配置。

通过文件编辑器填写含 $、#、空格的 SMTP 密码时，按 Compose env-file 语法使用单引号包裹并核对转义；不要把这份 .env 当作 Bash 脚本 source 执行。

05创建后端生产编排

在 1Panel → 文件中创建 /opt/booth-ai/compose.prod.yaml，完整复制以下 YAML。该文件是依据当前仓库整理的生产模板，使用已有的 Dockerfile，不需要修改业务代码。

FILE · /opt/booth-ai/compose.prod.yaml
name: booth-ai-prod

x-logging: &logging
  driver: json-file
  options:
    max-size: '20m'
    max-file: '5'

x-server: &server
  image: booth-ai-server:${APP_VERSION:?Set APP_VERSION}
  build:
    context: /opt/booth-ai/source/apps/server
    target: runtime
  init: true
  working_dir: /app
  stop_grace_period: 30s
  logging: *logging
  environment:
    NODE_ENV: production
    HOST: 0.0.0.0
    PORT: '3000'
    LOG_LEVEL: info
    DATABASE_URL: postgres://booth:${POSTGRES_PASSWORD:?Required}@postgres:5432/booth
    REDIS_URL: redis://:${REDIS_PASSWORD:?Required}@redis:6379
    S3_ENDPOINT: http://silo:9000
    S3_PUBLIC_ENDPOINT: ${S3_PUBLIC_ENDPOINT:?Required}
    S3_REGION: us-east-1
    S3_BUCKET: booth-assets
    S3_ACCESS_KEY: ${S3_ACCESS_KEY:?Required}
    S3_SECRET_KEY: ${S3_SECRET_KEY:?Required}
    SESSION_SECRET: ${SESSION_SECRET:?Required}
    AI_MODEL_ENCRYPTION_KEY: ${AI_MODEL_ENCRYPTION_KEY:?Required}
    SESSION_TTL_SECONDS: ${SESSION_TTL_SECONDS:-86400}
    EXTERNAL_API_URL: ${EXTERNAL_API_URL:?Required}
    CORS_ORIGINS: ${CORS_ORIGINS:?Required}
    TRUST_PROXY: ${TRUST_PROXY:-1}
    CLIENT_PUBLIC_URL: ${CLIENT_PUBLIC_URL:?Required}
    SMTP_HOST: ${SMTP_HOST:-}
    SMTP_PORT: ${SMTP_PORT:-465}
    SMTP_SECURE: ${SMTP_SECURE:-true}
    SMTP_USER: ${SMTP_USER:-}
    SMTP_PASSWORD: ${SMTP_PASSWORD:-}
    SMTP_FROM: ${SMTP_FROM:-}
    PROJECT_NOTIFICATION_WEBHOOK_URL: ${PROJECT_NOTIFICATION_WEBHOOK_URL:-}
    PROJECT_NOTIFICATION_WEBHOOK_SECRET: ${PROJECT_NOTIFICATION_WEBHOOK_SECRET:-}

services:
  postgres:
    image: postgres:17-bookworm
    environment:
      POSTGRES_USER: booth
      POSTGRES_DB: booth
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Required}
    volumes:
      - /opt/booth-ai/data/postgres:/var/lib/postgresql/data
    healthcheck:
      test: [CMD-SHELL, pg_isready -U booth -d booth]
      interval: 5s
      timeout: 3s
      retries: 30
    restart: unless-stopped
    logging: *logging

  redis:
    image: redis:7.4-bookworm
    environment:
      REDIS_PASSWORD: ${REDIS_PASSWORD:?Required}
    command:
      - /bin/sh
      - -ec
      - exec redis-server --appendonly yes --maxmemory-policy noeviction --requirepass "$$REDIS_PASSWORD"
    volumes:
      - /opt/booth-ai/data/redis:/data
    healthcheck:
      test: [CMD-SHELL, 'REDISCLI_AUTH="$$REDIS_PASSWORD" redis-cli ping | grep -q PONG']
      interval: 5s
      timeout: 3s
      retries: 30
    restart: unless-stopped
    logging: *logging

  silo:
    image: pgsty/silo:RELEASE.2026-09-16T00-00-00Z
    command: [server, /data, --console-address, ':9001']
    environment:
      MINIO_ROOT_USER: ${S3_ACCESS_KEY:?Required}
      MINIO_ROOT_PASSWORD: ${S3_SECRET_KEY:?Required}
    ports:
      - '127.0.0.1:19000:9000'
    volumes:
      - /opt/booth-ai/data/silo:/data
    restart: unless-stopped
    logging: *logging

  migrate:
    <<: *server
    profiles: [tools]
    command: [node, dist/scripts/migrate.js]
    restart: 'no'

  storage-init:
    <<: *server
    profiles: [tools]
    command: [node, dist/scripts/storage-init.js]
    restart: 'no'

  api:
    <<: *server
    command: [node, dist/api.js]
    ports:
      - '127.0.0.1:3000:3000'
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
      silo:
        condition: service_started
    healthcheck:
      test: [CMD, node, -e, "fetch('http://127.0.0.1:3000/health/ready').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 20s
    restart: unless-stopped

  worker:
    <<: *server
    command: [node, dist/worker.js]
    stop_grace_period: 180s
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
      silo:
        condition: service_started
    healthcheck:
      test: [CMD, node, -e, "process.exit(Date.now()-require('node:fs').statSync('/tmp/worker-ready').mtimeMs<30000?0:1)"]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 20s
    restart: unless-stopped
  • PostgreSQL、Redis 不映射宿主机端口，API 和 Worker 通过 Compose 服务名访问。
  • Silo 使用仓库目前固定的镜像标签。首次上线前确认目标服务器可拉取；发布后记录镜像 digest，避免直接升级为未知的 latest。
  • Worker 必须独立运行，用 node 直接启动并保留 180 秒停止等待时间。
  • 迁移与存储初始化放在 tools profile，需按下一节显式执行。直接点“启动全部”不会替你完成这两步。
  • 持久化使用绝对路径，重建容器不删除数据；不要删除 /opt/booth-ai/data。

06初始化与启动

在 1Panel 终端或 SSH 中执行。先定义简写函数 dc；每次打开新终端都需要重新定义。它固定 env 文件、编排文件和项目名，避免操作到开发栈。

BASH · 当前会话命令简写
dc() {
  docker compose --project-name booth-ai-prod \
    --env-file /opt/booth-ai/.env \
    -f /opt/booth-ai/compose.prod.yaml "$@"
}

以下每条命令成功后再执行下一条；迁移或存储初始化失败时先解决错误。

BASH · 首次启动顺序
dc config --quiet
dc pull postgres redis silo
dc build api
dc up -d --wait --wait-timeout 180 postgres redis silo
dc --profile tools run --rm --no-deps migrate
dc --profile tools run --rm --no-deps storage-init
dc up -d --no-build --wait --wait-timeout 180 api worker
dc ps
curl --fail --silent --show-error http://127.0.0.1:3000/health/ready
dc exec -T worker cat /tmp/worker-status.json
dc exec -T postgres psql -U booth -d booth -c \
  'SELECT version, applied_at FROM schema_migrations ORDER BY version DESC LIMIT 5;'

迁移成功输出 Database migrations ready，存储初始化成功输出 Private storage bucket ready。API 的 readiness 应为 HTTP 200，且返回 database / redis / storage 正常；Worker 应为 healthy。

在 1Panel 中查看与管理

  1. 进入 容器 → 容器，查看带 booth-ai-prod 项目标识的容器、健康状态和日志。
  2. 若使用 容器 → 编排 → 创建编排 → 路径选择，选中 /opt/booth-ai/compose.prod.yaml，确保项目名仍为 booth-ai-prod、工作目录为 /opt/booth-ai，且加载同目录 .env。
  3. 面板版本若不能保证以上参数一致，保留 CLI 作为编排操作入口，在面板中查看容器即可。不要用另一个项目名再部署一套。
生产环境的正常现象：/docs 与 /openapi.json 在 production 模式不注册；不是部署失败。检查使用 /health/ready，不是 Swagger。

07构建两个前端

使用临时 Node 24.15.0 容器构建，宿主机无需再安装 Node。两个前端均使用 pnpm@11.16.0（与当前管理端声明及 CI 选择一致），按锁文件安装。构建命令需要完整源码和网络访问。

7.1 参展商门户

在 /opt/booth-ai/source/apps/client/.env.production.local 创建以下内容。API_BASE_URL 留空，因为业务代码已经带 /api/v1/client/… 路径；填成 /api 会造成重复前缀。

FILE · apps/client/.env.production.local
VITE_APP_TITLE=灵通AI展台方案平台
VITE_API_BASE_URL=
VITE_LINGTONG_API_URL=https://api.lingtong.net.cn
BASH · client 构建
docker run --rm \
  -v /opt/booth-ai/source:/workspace \
  -w /workspace/apps/client \
  node:24.15.0-bookworm-slim \
  sh -ec 'npm install -g pnpm@11.16.0; pnpm install --frozen-lockfile; pnpm build'

输出目录：/opt/booth-ai/source/apps/client/dist/。

7.2 管理后台

在 /opt/booth-ai/source/apps/admin/apps/web-antd/.env.production.local 创建以下内容，将最后一项替换为单独生成的随机值（例如执行 openssl rand -hex 32）。这是前端本地存储加密配置，不是服务端认证密钥。

FILE · apps/admin/apps/web-antd/.env.production.local
VITE_BASE=/
VITE_GLOB_API_URL=/api
VITE_NITRO_MOCK=false
VITE_ROUTER_HISTORY=hash
VITE_APP_NAMESPACE=booth-ai-prod-admin
VITE_APP_STORE_SECURE_KEY=REPLACE_WITH_A_NEW_RANDOM_VALUE
BASH · admin 构建
docker run --rm \
  -e CI=true \
  -v /opt/booth-ai/source:/workspace \
  -w /workspace/apps/admin \
  node:24.15.0-bookworm-slim \
  sh -ec 'npm install -g pnpm@11.16.0; pnpm install --frozen-lockfile; pnpm build:antd'

输出目录：/opt/booth-ai/source/apps/admin/apps/web-antd/dist/。CI=true 仅避免在发布机安装 Git hooks，安装和构建脚本仍照常执行。

本项目特有的坑：仓库中的管理端 .env.production 默认指向 https://mock-napi.vben.pro/api，必须用上述 local 文件覆盖。前端变量在构建时生效，修改后要重新构建并重新上传完整 dist。

内存不足时在另一台构建机执行相同构建流程，上传两份 dist 即可。仅发布构建产物；不要把项目源码目录或后端 .env 设为网站根目录。

08在 1Panel 创建网站与代理

8.1 创建两个静态网站

  1. 进入 网站 → 创建网站 → 静态网站，创建 booth.example.com 与 admin.example.com。
  2. 在各站点的“网站目录”查看实际宿主机路径，将对应 dist 内的全部内容复制到该目录，确保根目录直接存在 index.html，而不是多一层 dist。
  3. 保留 1Panel 自动生成的证书、日志、ACME 验证和目录配置。站点配置中的 root 通常是 OpenResty 容器内路径，不能随意替换为宿主机路径。

在每个网站的 server { … } 中配置以下 location。已有同路径规则时应编辑原规则，避免重复的 location / 或 location /api/。

NGINX · 两个前端站点的 server 内
client_max_body_size 64m;

location ^~ /api/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}

location / {
    try_files $uri $uri/ /index.html;
}

location = /index.html {
    add_header Cache-Control "no-cache" always;
}
  • proxy_pass 末尾不加 /：保留原始 /api/v1/… 路径。管理端构建配置 /api 与接口中的 /v1 正好拼成完整路径。
  • SSE 必须关闭缓冲：在线客服与任务进度依赖长连接。若面板或 CDN 开启额外缓存，也要排除 /api/。
  • 64 MB 是代理请求上限，给 multipart 留出额外空间；后端仍按业务限制校验，当前普通单文件为 50 MiB、Excel 导入为 20 MiB。
  • 参展商页面需要 SPA 回退，直接刷新详情页才不会 404。完整 dist 中的 buildy/ 独立入口也要保留。
  • 本文直接面向公网的 OpenResty 覆盖 X-Forwarded-For，避免信任客户端自填头。引入 CDN 后须先配置可信来源和真实 IP 解析。

8.2 创建文件域名反向代理

创建 files.example.com 的反向代理网站，目标 http://127.0.0.1:19000。编辑其生成的 location /，保持以下配置。S3 API 是 9000 映射出的 19000，不是控制台 9001。

NGINX · files.example.com 的 server 内
client_max_body_size 64m;

set $booth_cors_origin "";
if ($http_origin ~* "^https://(booth|admin)\.example\.com$") {
    set $booth_cors_origin $http_origin;
}

location / {
    proxy_pass http://127.0.0.1:19000;
    proxy_http_version 1.1;
    proxy_set_header Host $http_host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_request_buffering off;
    proxy_read_timeout 300s;

    proxy_hide_header Access-Control-Allow-Origin;
    proxy_hide_header Access-Control-Allow-Credentials;
    proxy_hide_header Access-Control-Allow-Methods;
    proxy_hide_header Access-Control-Allow-Headers;
    proxy_hide_header Access-Control-Expose-Headers;
    add_header Access-Control-Allow-Origin $booth_cors_origin always;
    add_header Access-Control-Allow-Methods "GET, HEAD, OPTIONS" always;
    add_header Access-Control-Allow-Headers "Range, Content-Type" always;
    add_header Access-Control-Expose-Headers "ETag, Content-Length, Content-Range, Content-Disposition" always;
    add_header Vary Origin always;
    if ($request_method = OPTIONS) {
        return 204;
    }
}

替换上面 CORS 正则中的实际域名，并对域名中的点保留转义。当前上传经过业务 API，文件域名主要用于 GET/HEAD 签名下载；如果以后增加浏览器直传，需要同步重新设计允许的方法与请求头。

S3 签名的三个不变量：Host 必须是签名时的 files 域名；请求路径保留 bucket 与 object key；查询参数完整转发。不要添加 /s3 前缀、改写路径、改成控制台地址，或把私有桶改为公共读取。

每次保存前使用 1Panel 的配置检测，确认通过后重载 OpenResty。若版本没有检测按钮，可在 OpenResty 容器终端执行 nginx -t。

09配置 HTTPS 与验证文件访问

  1. 在 1Panel 的证书功能中创建 ACME 账户，申请覆盖上述三个域名的证书（可以分别申请，也可以使用多域名证书）。
  2. HTTP-01 验证要求 DNS 正确、80 端口可达且验证目录未被错误代理；DNS-01 需要对应 DNS API 凭据，可用于通配符证书。
  3. 进入各网站 HTTPS 设置绑定证书，启用 HTTPS 和 HTTP → HTTPS 跳转，并确认自动续签任务正常。
  4. 确认生产 .env 中的 CLIENT_PUBLIC_URL、S3_PUBLIC_ENDPOINT、CORS_ORIGINS 都是最终 HTTPS 域名。修改后执行 dc up -d --no-build --force-recreate api worker。
BASH · 网络与证书检查
curl -I https://booth.example.com
curl -I https://admin.example.com
curl --fail --silent --show-error http://127.0.0.1:3000/health/ready
curl -i https://booth.example.com/api/v1/admin/me

最后一条请求未携带 token，预期返回 401 错误 JSON；用于确认 /api 没有回落到前端 HTML。文件域名根路径返回 AccessDenied 可以是私有 S3 的正常表现，不等于故障。

随后在管理后台上传一份资源，从业务页面获取新生成的完整签名 URL并打开，确认是 HTTPS 文件域名且能下载。不要通过手动拼接对象 URL 验证私有对象；默认下载签名通常 300 秒后过期。

10首次业务配置与上线验收

先完成业务初始化

  1. 管理员：使用灵通企业用户系统账号登录。首次应准备具有本项目已授权角色的账号，迁移会给 ROLE_ADMIN 初始化权限。没有独立的默认 admin/admin 账号。
  2. AI 模型：在管理端配置供应商、模型和用途分配，再设置提示词等业务配置。API Key 在管理端录入并由服务端加密入库。
  3. 方案与资源：导入方案、基线图片和物料信息。空数据库只有迁移产生的基础数据，不包含本地开发已有的业务资源。
  4. 邮件与通知：需要询价回执、客服离线提醒时配置 SMTP 并做实际投递测试；需要 Webhook 时配置对应 URL / SECRET。
  5. 灵通接口：验证服务器端认证调用可达；若浏览器直接请求灵通公开接口，还需由对方允许你的生产前端来源。

逐项确认

  • API、Worker、PostgreSQL、Redis 持续健康；Silo 正常运行，storage-init 成功。
  • readiness 返回 200，schema_migrations 包含当前发布的全部迁移。
  • 两个站点 HTTPS 正常，前端页面刷新正常，管理端请求没有指向 mock-napi.vben.pro。
  • 参展商和管理员均能登录、登出，权限与菜单正确。
  • 能上传资源、预览图片、下载文件；签名链接没有 localhost 或内部主机名。
  • 能实际提交一个 AI 生成任务：Worker 消费、状态更新、结果落库与文件展示完整。
  • 完成一次询价交接；启用邮件时收到真实邮件，启用客服时消息实时到达。
  • SSE 在浏览器网络面板保持事件流连接，消息及时出现，无代理缓冲延迟。
  • 完成重启后的状态检查，完成一次备份，并在隔离环境验证恢复。
验收范围：健康接口通过只证明基础依赖可用，不证明外部 SSO、AI、SMTP 和全部业务配置正确。请以实际用户流程验收为准。项目自动化 check/smoke 在独立测试环境执行，不要用生产数据库代替测试库。

11更新、备份与恢复

11.1 更新发布

先在测试环境通过检查，再选择维护窗口。记录当前提交、APP_VERSION 和镜像 digest，保存两站点当前完整静态目录及 1Panel 站点配置。

  1. 按下节完成备份，并记录备份时间。维护期间可通过 1Panel 临时启用维护页，阻止新业务写入。
  2. 拉取目标版本，保留服务器的 .env 和两个前端 .env.production.local；不覆盖已执行的数据库迁移文件。
  3. 将 /opt/booth-ai/.env 的 APP_VERSION 改为新的唯一发布标识；构建后端镜像和两份前端。
  4. 停止 API / Worker，执行迁移；成功后启动新后端并发布匹配版本的前端产物。
BASH · 更新主流程（每步成功后再继续）
git -C /opt/booth-ai/source fetch --tags
git -C /opt/booth-ai/source checkout NEW_RELEASE_TAG_OR_COMMIT
# 此时在文件编辑器中更新 APP_VERSION，再构建。
dc build api
# 按第 07 节构建 client / admin，确认都成功后进入维护窗口。
dc stop api worker
dc --profile tools run --rm --no-deps migrate
dc --profile tools run --rm --no-deps storage-init
dc up -d --no-build --wait --wait-timeout 180 api worker
# 用对应 dist 更新两站点静态文件，再执行第 10 节验收。
curl --fail --silent --show-error http://127.0.0.1:3000/health/ready
dc exec -T worker cat /tmp/worker-status.json

Worker 停止最多可能等待 180 秒，给正在进行的供应商调用留出结束时间。不要急于强杀。迁移失败时保持维护状态，先排查，避免让旧程序访问部分升级后的 schema。

11.2 一致性冷备份：数据库 + Redis + 对象文件 + 密钥

下面是一种简单、可恢复的停机备份。先停 API / Worker 排空写入，再停数据服务，最后归档；tar 包不能直接复制在线 PostgreSQL 的数据目录来替代这个过程。大数据量需要设计独立的在线备份方案。

BASH · 停机备份（已定义 dc）
(
  set -eu
  umask 077
  backup="/opt/booth-ai/backups/booth-$(date +%Y%m%d-%H%M%S).tar.gz"
  dc stop api worker
  dc stop postgres redis silo
  tar --numeric-owner -czpf "$backup" -C /opt/booth-ai \
    data .env compose.prod.yaml \
    source/apps/client/.env.production.local \
    source/apps/admin/apps/web-antd/.env.production.local
  tar -tzf "$backup" > /dev/null
  sha256sum "$backup" > "$backup.sha256"
  dc up -d --no-build --wait --wait-timeout 180
  printf '备份完成：%s\n' "$backup"
)

若归档中途因磁盘不足等原因失败，服务会保持停止；排查后执行 dc up -d --no-build --wait --wait-timeout 180 恢复。备份包含凭据，需加密后同步到异机或独立对象存储，设置保留周期。不要把备份放进网站目录。

同时通过 1Panel 备份两站点的静态文件、站点配置、证书及面板配置，并记录精确源码提交与镜像版本。仅备份数据库不包含 Silo 图片；仅做面板快照也不能假定已经包含此自定义目录的全部数据。

11.3 恢复与回滚

  1. 优先在隔离服务器恢复演练；准备同一架构、同一 PostgreSQL 17 版本及备份记录的 Redis / Silo 镜像。
  2. 目标服务器停止所有 booth-ai-prod 容器，保留现有数据目录作为现场备份。将备份恢复到空的数据目录，不要与现有文件混合覆盖。
  3. 使用 root 解包以保留 UID/GID：核对 sha256sum -c 备份文件.sha256 后，执行 tar --numeric-owner -xzpf 备份文件.tar.gz -C /opt/booth-ai。
  4. 恢复相同版本源码、前端构建文件、站点配置及证书；确认 AI_MODEL_ENCRYPTION_KEY 等密钥与备份数据库成套一致。
  5. 按第 06 节先启动基础服务，使用对应版本镜像运行 migrate / storage-init，再启动 API / Worker，执行完整验收。
回滚不等于 git checkout：仅当数据库变更已确认兼容旧程序时，才能切回旧镜像与旧前端。否则需要协调恢复升级前的 PostgreSQL、Redis、Silo 和密钥备份，且会丢失备份时间之后的新业务数据。已发送邮件与已发生的 AI 供应商调用不会随恢复自动撤销。

12常见故障排查

BASH · 常用诊断
dc ps
dc logs --tail 150 api worker
dc logs --tail 100 postgres redis silo
curl -i http://127.0.0.1:3000/health/ready
dc exec -T worker cat /tmp/worker-status.json
docker stats --no-stream
df -h
现象优先检查
1Panel 无法打开用 1pctl status、1pctl user-info 核对服务与完整安全入口；检查面板端口的云安全组和系统防火墙。
网站 502API 是否健康，宿主机 curl 是否通；OpenResty 是否为 host 网络；proxy_pass 是否为 127.0.0.1:3000。
API 返回前端 HTML / 404/api/ location 是否生效、是否被其他正则覆盖、proxy_pass 是否错误添加末尾斜杠；管理端 /api 与客户端空前缀是否填对。
管理端仍调用 mock.env.production.local 是否在 apps/admin/apps/web-antd；是否重新构建、上传全部 dist（含运行时配置文件）并刷新缓存。
API readiness 503返回的 checks 里是哪一项失败；迁移是否齐全、bucket 是否存在、数据库 / Redis 密码是否一致。
反复退出 / Missing environment variable.env 是否加载、所有必填字段是否存在；AI_MODEL_ENCRYPTION_KEY 是否为 64 位十六进制；不要在日志中打印完整配置。
登录 403外部账号启用状态、外部角色与本地 admin_roles 授权是否匹配；不是面板管理员账号。外部调用失败则检查 EXTERNAL_API_URL 与出口网络。
图片 403 / SignatureDoesNotMatchS3_PUBLIC_ENDPOINT、原始 Host、完整路径和查询参数、签名是否过期、服务器时间是否准确。
图片可打开，下载报 CORSfiles 站点允许来源正则是否替换正确；是否出现重复 Access-Control-Allow-Origin；预检是否 204。
客服消息 / 任务进度延迟OpenResty / CDN 缓冲和缓存是否关闭，proxy_read_timeout 是否足够，Worker 与 Redis 是否正常。
AI 一直排队Worker 是否启动且 healthy；用途是否分配模型；供应商凭据、额度、出口访问及相关任务日志。
上传 413区分 OpenResty 请求限制和后端业务文件限制；代理 64m 并不会取消后端 50 MiB / 20 MiB 限制。
多人共用限流 / 429TRUST_PROXY 与实际代理链是否匹配，X-Forwarded-For 是否被正确设置。
构建被 Killed / OOM内存、Docker stats 与系统 OOM 日志；单独构建前端或使用更大构建机。管理端构建脚本允许最高 8 GB Node 堆。
修改 .env 没生效必须重新创建 API / Worker 容器；单纯 docker restart 不刷新容器环境变量。VITE 变量则需要重新构建前端。
邮件未发送SMTP_HOST 是否配置、FROM 与凭据是否正确、465/587 出口是否受限；未配置时 outbox 待发送是预期行为。
