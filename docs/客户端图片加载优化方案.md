# 客户端图片加载优化方案

## 一、目标与范围

优化客户端方案效果图、换主题结果、四向画稿及检索记录的图片加载速度，适配约 10 Mbps 公网出口、十几人同时浏览的场景。

本期沿用现有自建 Silo 对象存储与 OpenResty 反代，不引入 CDN 或云对象存储，也不新增依赖（后端已有 `sharp`）。

核心原则：

> 同一张图在签名有效期内地址不变；小图位置加载缩略图，主图和放大弹窗加载预览图，只有明确下载或作为 AI 输入时才读取原图。

## 二、现状

用真实图片生成 WebP 的结果（`sharp` 0.35，effort 4）：

| 样本 | 原图 | 480 px q82 | 1600 px q82 | 1600 px 编码耗时 |
|---|---|---|---|---|
| 方案效果图（透明） | 959 KB | 26 KB | 127 KB | 225 ms |

1600 px q82 与原图按同尺寸裁切对比，品牌文字、灯箱画面和线条看不出差别。预览图只有原图的 1/8～1/25。

### 2.2 签名地址每次都变，浏览器缓存失效

`infra/storage.ts` 的 `signDownload` 每次调用都以当前时间签名，同一个对象每次拿到的 URL（`X-Amz-Date`、`X-Amz-Signature`）都不同。浏览器缓存按完整 URL 匹配，所以每次刷新数据都会重新下载全部图片：

- **四向画稿页**（`ArtworkJob.vue`）：任务进行中，`useAsyncJob` 每 10 秒兜底刷新一次，SSE 每推送一次也刷新一次。每次刷新都会重新下载主题参考图（约 2 MB PNG）和所有已完成方向的图，直到任务结束。
- **AI 智选**：`useSchemeImages` 大约每 4.5 分钟换一次链接，所有卡片图重新下载。
- 重新进入任何页面，缓存都用不上。

另外，Silo 返回的图片没有 `Cache-Control`，浏览器只能靠启发式缓存或重新校验。

### 2.3 各位置直接加载原图

| 页面 / 组件 | 位置 | 现在加载 |
|---|---|---|
| `SchemeGallery.vue`（AI 智选卡片、方案详情、换主题页） | 主图、3 个视角缩略图、放大弹窗 | 全部原图（`signImages` 把同一原图地址赋给 `url` 和 `thumbnailUrl`） |
| `ThemeJob.vue` | 结果主图、结果缩略条、已选效果、原图对比 | 全部原图 PNG |
| `ArtworkJob.vue` | 主题参考图、四个方向卡片、放大弹窗 | 全部原图 |
| `MySearches.vue` | 方案小图、主题小图、四向小图、放大弹窗 | 全部原图 |
| `MyProjects.vue` | 已选主题 | 原图 |
| `SchemeDetail.vue` 资料区 | 报馆图 / 平面素材的缩略图与预览 | 原图，而且每张缩略图单独请求一次签名接口 |
| 客服上下文卡片 | 主题封面（`/theme-cover` 302 跳转） | 原图 |

以 AI 智选为例：3 张方案卡片 ×（主图 + 3 个视角）≈ 9 张不同原图，约 6 MB。

### 2.4 带宽影响

10 Mbps 理论上约 1.25 MB/s。15 人同时打开 AI 智选，每人约 6 MB，合计 90 MB，理论上需要 72 秒；改成预览图加缩略图后，每人约 0.6 MB，合计 9 MB，约 7 秒。

## 三、方案总览

1. **稳定签名与缓存头**：同一对象在同一时间窗内签出相同的 URL，并带上 `Cache-Control`，让浏览器缓存真正生效。
2. **两档衍生图**：每张展示用图片生成缩略图和预览图（WebP），记录在 `asset_versions` 上；图片写入时就地生成，Worker 定时补齐存量和失败项。
3. **按位置选规格**：接口同时返回缩略图和预览图地址，各页面按位置使用；原图只用于下载和 AI 输入。

## 四、稳定签名与缓存头（第零阶段）

### 4.1 签名时间窗

`signDownload` / `signDownloadWithName` 把签名时间向下取整到 10 分钟边界，有效期相应加上 10 分钟：

```text
signingDate = floor(now / 600s) × 600s
实际有效期 = 调用方要求的有效期 + 600s
```

- 同一个 10 分钟窗口内，同一对象签出的 URL 完全相同，轮询和重复进入页面都会命中浏览器缓存。
- 链接剩余有效期始终不少于调用方要求的时长，前端现有的续签节奏（270 秒、5 分钟、15 分钟）不需要修改。
- 代价是链接最多比要求多存活 10 分钟。这些都是私有对象的只读链接，可以接受。

### 4.2 Cache-Control

签名时附加 `ResponseCacheControl: private, max-age=<实际有效期>, immutable`，由 Silo 在响应中返回。存量对象不需要重新上传。

- 对象 key 一经写入就不再修改（`asset_versions.object_key` 唯一，版本更新会生成新 key），可以使用 `immutable`。
- `private` 禁止中间代理缓存。
- API 响应仍然是 `no-store`，与图片对象各自设置缓存策略。

### 4.3 生产反代检查

`boothapi.baolinfeng.cn` 的图片和 API 共用一个域名。需要确认 OpenResty 站点开启了 HTTP/2，否则在 HTTP/1.1 下每个域名最多 6 个并发连接，图片和 API 会互相排队。不需要改 `/booth-assets/` 的代理规则：签名参数原样转发即可。

## 五、衍生图

### 5.1 规格

| 规格 | 名称 | 长边 | 编码 | 典型体积 | 用途 |
|---|---|---|---|---|---|
| 缩略图 | `thumb` | 480 px | WebP q80 | 15～30 KB | 视角切换、结果缩略条、检索记录小图、资料区缩略图、客服卡片 |
| 预览图 | `preview` | 1600 px | WebP q82 | 70～130 KB | 卡片主图、结果主图、四向卡片、放大弹窗 |
| 原图 | — | 原始 | 原文件 | 0.7～3.5 MB | 下载、ZIP 交付、AI 输入、弹窗中的「查看原图」 |

- 预览图只有约 100 KB，卡片主图直接使用预览图，不再单独设卡片图规格。卡片和放大弹窗用同一个地址，点开放大时可以直接命中缓存。
- 保持原比例，不裁切、不放大；先按 EXIF 校正方向（`rotate()`）；WebP 保留透明通道。
- 原图小于目标尺寸时按原尺寸编码。

### 5.2 存储与记录

- 对象 key：`renditions/v1/<原 object_key>/thumb.webp`、`.../preview.webp`。`v1` 是规格版本，以后调整参数时升级为 `v2`，并用迁移清空记录，Worker 会自动重新生成，旧缓存也不会被误用。
- `asset_versions` 追加三列（迁移）：
  - `renditions jsonb`：`{ "thumb": { key, width, height, bytes }, "preview": { ... } }`，为空表示还没有衍生图。
  - `rendition_attempts smallint`、`rendition_attempted_at timestamptz`：失败重试计数，最多重试 3 次。
- 所有展示图（方案效果图、换主题结果、四向画稿、方案资料图片）都在 `asset_versions` 中，`object_key` 唯一且不会被覆盖，不需要新建表。

### 5.3 生成时机

| 来源 | 生成方式 |
|---|---|
| 换主题结果（`theme/results.ts`） | 上传原图后，用内存中的图片就地生成并写入，与资产版本同一次插入 |
| 四向画稿（`artwork/directions.ts`） | 同上 |
| 管理端上传 / 存量 / 就地生成失败 | Worker 定时任务 `image-renditions`（background 链，每 5 秒一批，每批最多 4 张，逐张串行），用 `FOR UPDATE SKIP LOCKED` 领取 `renditions IS NULL` 的图片版本 |

- 就地生成失败只记日志，不影响生成任务本身，之后由定时任务补齐。
- 定时任务天然支持断点续跑和多副本；对象 key 固定，重复生成也只会覆盖为相同内容，满足幂等。
- 只处理 `image/png`、`image/jpeg`、`image/webp`；PDF、模型文件不处理。
- 进度查询：`SELECT count(*) FILTER (WHERE renditions IS NOT NULL), count(*) FILTER (WHERE renditions IS NULL AND rendition_attempts >= 3) ... FROM asset_versions WHERE mime_type LIKE 'image/%'`。

### 5.4 缺失时的回退

接口签名时，如果某个版本还没有衍生图，就回退为原图地址。存量补齐后只剩下损坏的图片（重试 3 次仍失败），这种情况下回退原图，至少还能正常显示。失败项可以通过上面的查询看到。

## 六、接口字段

衍生图地址的签名都集中在 `modules/media/links.ts` 的 `signImage(storage, { objectKey, renditions }, variant, expiresIn)`。各处 SQL 在已经查询 `object_key` 的地方一并带出 `renditions`。

| 接口 | 调整 |
|---|---|
| 智选匹配 / 方案详情 / 方案图片续签（`SchemeImage`） | `url` 改为 `originalUrl`；`thumbnailUrl` 指向缩略图；新增 `previewUrl` |
| 智选封面跳转（`cover`） | 跳转到预览图 |
| `GET /client/theme-jobs/:id` | `results[]` 新增 `thumbnailUrl`，`previewUrl` 改指预览图；`original.previewUrl` 改指预览图 |
| `GET /client/artwork-jobs/:id` | `directions[].previewUrl`、`referencePreviewUrl` 改指预览图（方向卡片本身就要预览图的清晰度，不另加缩略图） |
| 检索记录列表 | 方案 `thumbnail` 改指缩略图，新增 `preview`；`theme`、`artwork.views[]` 新增 `thumbnailUrl`，`previewUrl` 改指预览图 |
| 项目详情 `selectedThemeSummary.previewUrl` | 改指预览图 |
| 方案资料 `downloads/...?disposition=preview` | 图片改为返回预览图，PDF 仍返回原文件；列表项新增 `thumbnailUrl`，前端不再逐张请求签名 |
| 客服 `/theme-cover` | 跳转到预览图（卡片与放大弹窗共用同一地址） |

- 下载接口（单张下载、ZIP）和 AI 输入继续读取原图，不受影响。
- 资料集合的摘要（`revision`）不包含衍生图字段，Worker 补齐前后摘要不变，不会导致打包下载误报“资料已变更”。
- 管理端本期不改：流量很小，相关字段继续返回原图。

## 九、验收标准

- 默认浏览和放大预览都不请求原图；「查看原图」、下载、ZIP 和 AI 输入仍然使用原图。
- 同一页面轮询或刷新数据时，已显示的图片不会重新下载（同一签名窗口内）。
- 新上传或新生成的图片自动生成衍生图；存量补齐完成，失败项可以查询。
- 衍生图比例、方向和透明背景正确，文字与线条清晰。
- server：Docker `check` 通过，dev 栈重新部署，并检查迁移版本、API 就绪状态和 Worker 状态。
- client：`pnpm build`、`pnpm test` 通过。
