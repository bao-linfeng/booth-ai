# 客户端业务梳理与 UI 优化建议

> 评审日期：2026-10-03  
> 评审范围：`apps/client` 现有业务页面、公共组件、路由与前端请求逻辑  
> 评审方式：基于现有代码的静态分析，未进行浏览器视觉与交互验证  
> 文档性质：优化建议；3.1 导航业务化、3.2 首页聚焦、3.3 方案卡片、3.4 详情页重新分工已实施（2026-10-04），验证范围见各节实施记录，其余建议待实施

## 一、总体判断

现有客户端已经覆盖方案选型、AI 换主题、四面素材生成、报价申请、人工需求和项目跟进等主要业务，但整体体验仍存在“模板导航、业务表单、生成工具”组合感较强的问题。

建议按以下顺序优化：

1. **业务路径清晰**：用户知道从哪里开始、下一步做什么、结果在哪里找。
2. **交互真实一致**：界面提供的选择确实生效，操作失败有可见反馈。
3. **视觉形成品牌感**：突出展台图片和空间设计，减少后台表单感。

现有草稿恢复、登录返回、重复提交保护、资料修订确认和项目回执等机制具有业务价值，优化时应保留。

## 二、现有业务链路

### 2.1 主流程与分支

```text
描述需求 / 选择展位条件
         ↓
AI 解析 → 必要时澄清 → 匹配方案
         ↓
      查看方案详情
         ├─ 使用标准方案 ─────────────────→ 申请报价
         │
         └─ AI 换主题 → 选定效果 ──────────→ 申请报价
                              │
                              └─ 生成四面素材 → 携带素材申请报价

无合适方案 / 特殊需求 ─→ 提交人工需求

报价申请 / 人工需求
         ↓
      建立项目
         ↓
我的项目：查看处理结果、资料状态、补充四面素材
```

辅助能力：

- **检索记录**：查看历史匹配、换主题和四面视图。
- **账户与积分**：登录、签到、余额与生成费用。

### 2.2 已实现页面与职责

| 页面 | 路由 | 当前职责 |
|---|---|---|
| 首页 / AI 智选 | `/`、`/ai-selection` | 需求输入、条件筛选、解析澄清、方案匹配、人工需求入口 |
| 方案详情 | `/schemes/:code` | 效果图、空间规格、适用说明、物料清单和资料、换主题及报价入口 |
| AI 换主题 | `/schemes/:code/theme` | 选择原图、行业与风格、品牌色与关键词、数量和积分确认 |
| 换主题结果 | `/theme-jobs/:jobId` | 任务状态、结果对比、最终效果选择、素材生成和报价入口 |
| 四面素材 | `/schemes/:code/artwork`、`/artwork-jobs/:jobId` | 生成、验收状态、下载、项目绑定 |
| 报价申请 | `/schemes/:code/quote` | 展会信息、需求范围、材料预算、联系方式、受理回执 |
| 人工需求 | `/manual-request` | 承接特殊需求，复用申请表单并建立项目 |
| 检索记录 | `/my-searches` | 历史检索与相关生成成果展示 |
| 我的项目 | `/my-projects`、`/my-projects/:projectId` | 申请记录、资料状态和公开处理结果 |
| 个人中心 | `/profile` | 账户信息、积分签到 |
| 登录 | `/auth/sign-in` | 账户登录与外部注册、找回密码入口 |

### 2.3 应在界面中明确的业务关系

#### AI 换主题是可选增强

用户可以直接使用标准方案申请报价，不应被引导为必须先生成主题或素材。

评审时详情页首先突出换主题，报价按钮位于资料区之后。3.4 已将报价提升为决策区主操作，并明确标准方案可直接申请报价。

#### 标准资料与生成素材应区分

| 内容 | 建议表达 |
|---|---|
| 已发布方案的物料清单 | 物料清单 |
| 已发布方案的图纸资料 | 按实际内容统一命名为报馆参考图或三视图 |
| 已发布方案的平面文件 | 标准平面素材 |
| AI 根据选定主题生成的四方向图像 | AI 四面方向底图 |
| 与具体项目关联的资料 | 项目交付资料 |

“四面生成完成”不应被理解为已经具备直接印刷或施工条件。现有代码已有相关说明，建议进一步通过标题、分区和状态表达强化区别。

#### 检索记录与我的项目应明确分工

- **检索记录**：我看过什么、生成过什么。
- **我的项目**：我提交了什么、目前处理到哪里。

不建议简单合并，应通过任务、方案和项目入口相互衔接。

## 三、关键问题与优化建议

### 3.1 全局导航业务化

**代码位置：**

- `apps/client/src/components/sections/navbar/MainNavigation.vue`
- `apps/client/src/components/sections/navbar/UserAvatar.vue`
- `apps/client/src/router/index.ts`
- `apps/client/src/components/theming/ThemingSettings.vue`

**评审时现状（实施前）：**

- 主导航根据 `isGroupParent` 生成，当前主要展示 Hero Sections、Blog Sections 等模板入口。
- 检索记录和我的项目位于登录后的头像菜单中。
- 顶部同时展示语言、深浅模式、主题设置，以及条件出现的 BuildY 入口。
- 未登录入口主要使用图标表达。

**建议：**

```text
品牌标识    AI 智选    检索记录    我的项目       联系顾问    账户
```

1. 将真实业务入口提升到一级导航。
2. 模板演示入口退出业务导航。
3. 主题配色工具收进设置，保持默认品牌视觉稳定。
4. 未登录时使用明确的“登录”文字。
5. 移动端菜单沿用相同业务结构。
6. 保留多语言切换入口，并逐步补齐业务页面翻译覆盖；当前核心页面存在大量直接写入的中文文案。

**预期收益：**降低首次访问理解成本，提高项目和历史记录的可发现性。

**实施记录（2026-10-04）：**

- 桌面与移动端共用 AI 智选、检索记录、我的项目三个一级入口；首页与选型相关页面归属 AI 智选，项目详情归属我的项目。
- 联系顾问接入现有 `/manual-request` 人工需求申请页；记录与项目页继续使用已有未登录提示和登录返回机制。
- 主导航移除模板分组与 BuildY，保留桌面和移动端的语言切换入口及原有语言选择机制；窄屏使用语言图标以节省空间。未登录账户入口明确显示“登录”。
- 账户菜单聚焦个人中心、积分与退出登录；明暗模式与主题配色、圆角、字体统一收进中文“外观设置”，移除设置中的模板工具入口。
- 移动端点击当前栏目或其他栏目均关闭菜单，路由变化及切换至桌面宽度时也关闭菜单；补充当前栏目标识、键盘焦点样式及面板关闭标签。

**验证结果：**`pnpm build` 通过；浏览器验证了 1280 / 1024 / 375 / 320px 下的导航断点与无横向溢出、导航目标和当前栏目、移动菜单关闭与 Escape 焦点恢复、登录返回地址保留查询参数、外观控件及模板入口清理。真实登录后的账户菜单与退出、真实项目数据、主题设置重载后的持久化尚未验收。

**范围说明：**保留多语言是明确需求；恢复切换入口不代表已完成全站翻译，新增业务导航及其他中文业务文案仍需接入翻译资源。恢复入口后 `pnpm build` 和 `git diff --check` 通过；上述浏览器验证结果对应恢复语言入口前的版本，恢复后尚未重新进行浏览器验收。

### 3.2 AI 智选首页聚焦

**代码位置：**

- `apps/client/src/pages/AISelection.vue`
- `apps/client/src/features/selection/RequirementForm.vue`
- `apps/client/src/features/selection/RequirementField.vue`（实施时新增，共用字段编辑）

**评审时现状（实施前）：**

首页同时承载签到、完整筛选、自然语言输入、条件摘要、解析修正、匹配结果和人工入口，阶段主次不够突出。

**建议采用渐进式呈现：**

| 阶段 | 主要内容 | 次要内容 |
|---|---|---|
| 首次进入 | 需求描述、尺寸、开口方式、查找方案 | 产品体系、详细偏好、适用条件 |
| 需要澄清 | 待确认字段、直接修正操作 | 完整条件与解析依据 |
| 展示结果 | 方案图片、匹配类型、关键差异 | 可收敛的需求摘要与编辑入口 |
| 条件已修改 | 重新匹配操作、旧结果提示 | 原始匹配结果 |

具体建议：

- 将产品体系、风格、行业、功能偏好和材料预算纳入“更多条件”；必须 / 禁止条件、关键词和适用条件不作为首页人工筛选控件。
- 有结果后，让方案结果成为页面主体，输入区收敛为需求摘要。
- 在结果上方就近展示“当前为上次匹配结果”和重新匹配操作。
- 澄清内容应提供直接修改入口，减少在长表单中寻找字段。
- 签到属于辅助功能，弱化其在主业务首屏中的权重。

#### 需优先处理：澄清字段与表单能力不一致

当前表单主要提供已有“长 × 宽 × 高”空间组合，但澄清流程可能要求修正长宽方向。

建议保留常用空间快捷选择，同时提供独立长宽、限高修正入口。

另外，当前选择空间会将组合高度写入 `maxHeightMm`。需要产品确认“方案实际高度”和“场馆限高”的语义及输入关系。

**产品决策（2026-10-04）：**允许独立输入长宽及场馆限高。常用尺寸按长宽去重，仅填写长宽和自动计算面积，不代填或清除场馆限高；限高保持选填。后端现有字段及匹配规则已支持此语义，与《一期功能拆分/AI智选模块详细设计》“方案实际高度 ≤ 客户场馆限高”的约定一致。

**实施记录（2026-10-04）：**

- 首页采用单列渐进呈现，首次进入集中展示需求描述、长宽、开口面数、限高和“查找方案”；产品体系、风格、行业、功能偏好和材料预算折叠至“更多条件”。
- 匹配结果和无结果状态默认收起编辑区，展示需求摘要、全部条件展开入口与“编辑需求”；方案区使用完整内容宽度。
- 修改条件后，在结果区上方显示“当前为上次匹配结果”和“重新匹配”；仅修改表单使用新值直接匹配，修改描述后重新解析文字。
- 澄清区复用字段编辑控件，就地修改长宽、限高、面积、开口、体系和用户偏好等；正确的原值可显式确认，未识别文字可就地修改并重新解析，保留人工入口。识别依据与覆盖记录默认折叠。
- 新增尺寸边界、毫米精度和面积一致性校验；尺寸错误就近展示，错误未修正时阻止匹配。
- 移除首页不需要的必须 / 禁止分区、必须 / 禁止特色、关键词和适用条件控件。服务端仍保留这些字段的匹配能力，供自然语言解析和后续业务流程使用；客户端首页不再将它们作为人工筛选项暴露。
- 签到移至已登录用户的页尾辅助区；移除重复的首屏空间介绍和全程悬浮的匹配按钮。保留会话草稿、结果与视角恢复，并保存澄清原值确认记录。
- 需求卡顶部与底部提供同一查找操作，确保桌面及窄屏首屏可直接开始；匹配完成或进入澄清后将焦点移至当前内容区。

**验证结果：**

- `pnpm build`（含类型检查与生产构建）、`git diff --check` 通过。
- 新增 `apps/client/tests/selection-fields.test.mjs`，在 `apps/client` 执行 `node --test tests/selection-fields.test.mjs`：4 项组件行为测试通过，覆盖米到毫米转换、清空、面积联动、精度错误的无障碍反馈、常用尺寸去重及独立限高保留。
- Chrome 验证静态预览中的更多条件默认折叠、编辑收敛、旧结果提示、重新匹配与摘要更新；使用合法会话数据验证真实首页澄清就地修改、原值确认及刷新恢复。
- 真实首页通过受控 fetch 响应验证请求顺序 `parse → match → match → parse → match`：仅将长 6 m 修改为 7 m 后直接匹配，提交 7000 mm / 3000 mm / 21 ㎡；修改描述后重新解析。
- 真实首页在 1280×800、375×812、320×700 的明暗模式下均无文档或输入卡横向溢出；上方“查找方案”完整位于首屏、可用且未被遮挡。尺寸验证采用桌面 Chrome 同源 iframe，非原生移动设备；主题检查直接切换根元素 dark 类。结果状态的 1280 / 375 / 320px 无溢出在静态预览中验证。

**验收边界：**浏览器测试使用静态预览、受控会话及请求响应，未验证真实 AI 解析、真实匹配结果正确性、真实登录签到和完整人工申请；图片截图存在后台捕获延迟，未将其作为视觉验收证据。最终结论以组件断言、实际 DOM 和请求参数为依据。

**范围说明：**本次覆盖 3.2 首页聚焦及其澄清入口；方案卡片内容排序、人工申请重复步骤和全站多语言仍按后续章节推进。

### 3.3 方案卡片突出设计作品

**代码位置：**

- `apps/client/src/features/selection/SchemeCard.vue`
- `apps/client/src/features/selection/SchemeGallery.vue`
- `apps/client/src/features/selection/types.ts`

**现状：**编号、尺寸、体系和多条解释占据较高权重，偏规格记录展示。

**建议信息顺序：**

```text
大幅方案效果图
匹配类型
易理解的方案标题
尺寸 / 开口 / 面积
为什么适合您
需要确认的差异
查看方案
```

- 提高效果图的视觉占比，方案编号降为辅助信息。
- 匹配理由先展示最关键的两三条，其余展开。
- 结构差异保留清晰、稳定的位置。
- 匹配类型使用文字、图标和语义色共同表达。
- 保留现有多视角查看能力。

**数据边界：**当前 `MatchItem` 和 `SchemeDetail` 没有方案名称字段。真实名称需要接口支持；若先使用尺寸、体系组合标题，应保证只表达已有事实，不编造风格或卖点。

**实施记录（2026-10-04）：**

- 方案卡片改为“大图 + 决策信息”结构，桌面端效果图占主要视觉区域，窄屏保持图片在上、信息在下；效果图改为完整展示并保留缩略图、放大预览和多视角切换。
- 匹配类型改用文字、图标和语义色表达；编号降为辅助信息。因接口没有方案名称，标题仅由已有的尺寸和产品体系组合生成，不表达未提供的风格或卖点。
- 规格信息收敛为尺寸、开口、面积和高度；匹配理由默认展示前三条，其余通过可访问的展开按钮查看。
- “需要确认的差异”固定为决策区段。结构差异、适用条件确认、随机推荐提示和偏好提示统一在该位置表达；保留已有“是 / 否”回答事件和方案详情入口。
- 新增成功、待确认、参考三类语义色变量，明暗模式分别保证文字与背景对比度。

**验证结果：**`pnpm build`（类型检查与生产构建）通过；在 `apps/client` 执行 `node --test tests/scheme-card.test.mjs`，2 项方案卡片行为测试通过，覆盖标题事实边界、理由折叠展开、适用条件回答和多视角切换；仓库根目录执行 `git diff --check` 通过。

### 3.4 方案详情页重新分工

**代码位置：**`apps/client/src/pages/SchemeDetail.vue`

**评审时现状（实施前）：**约 300px 的侧栏同时承载换主题、模型选择、七列物料表格、图纸与素材缩略图、下载和报价，内容拥挤且主操作容易被推到下方。

**建议布局：**

```text
顶部：返回路径 + 方案标题 + 规格摘要

左侧主内容                         右侧决策区
大幅效果图                         方案摘要
多视角切换                         申请报价
                                  AI 换主题（可选）

下方宽内容区
方案说明 | 物料清单 | 图纸与素材
```

- 物料清单进入宽内容区。
- 图片资料提供较大的预览和明确的文件名称。
- 决策区仅放摘要及主要操作。
- 报价入口在首屏可发现。
- 手机端考虑轻量底部操作区。

**建议默认以“申请报价”为主操作，“AI 换主题”为次操作。**最终顺序取决于产品的转化目标。

**实施记录（2026-10-04）：**

- 顶部展示返回入口、辅助方案编号，以及由真实尺寸和产品体系组成的标题；摘要展示面积、开口数量与实际高度。
- 首段改为大幅效果图与右侧决策区，多视角和放大查看沿用现有图库。决策区仅保留规格摘要、主要报价入口及可选的 AI 换主题入口，明确标准方案可直接申请报价。
- 下方整页宽度使用“方案说明 / 物料清单 / 图纸与素材”页签。清单按需加载，七列表格在窄屏内独立横向滚动，保留 XLSX 下载、修订变化确认及报价参数。
- 三视图与标准平面素材使用完整展示的较大预览，显示资料名称和原始文件名；预览、单文件下载与批量下载常显。预览接入现有 Dialog 原语，支持键盘关闭及返回触发按钮。
- 窄于桌面双栏断点时展示轻量底部操作区，突出申请报价，同时保留 AI 换主题；预留底部安全区与正文留白。
- 移除详情页未进入请求链路的模型选择及预计积分展示，主题入口保留 `searchId`。换主题页的模型与费用链路仍属于 3.5 的后续范围。

**验证结果：**

- `pnpm build`（类型检查与生产构建）、仓库根目录 `git diff --check` 通过。
- 新增 `apps/client/tests/scheme-detail.test.mjs`，在 `apps/client` 执行 `node --test tests/scheme-detail.test.mjs`：7 项页面行为测试通过。使用真实页面、Tabs 与 Dialog，覆盖标题事实与操作顺序、两处报价参数一致性、`searchId` 保留、清单懒加载及失败重试、清单与资料修订变化处理、资料文件名与下载参数、预览关闭与焦点恢复、静态示例限制。
- 补充离开资料页签后的延迟响应测试，并修复预览请求返回后仍会自动弹窗的问题。

**验收边界：**行为测试使用 happy-dom 与受控 API 响应，下载验证止于链接参数和文件名，不代表真实后端联调或文件传输成功。当前无可用浏览器控制工具，1280×800、375×812、320×700 明暗模式下的首屏报价可见性、页面无横向溢出与清单容器独立滚动尚待真实浏览器确认；未将 DOM 行为测试作为视觉验收依据。

### 3.5 换主题交互一致性

**代码位置：**

- `apps/client/src/pages/SchemeTheme.vue`
- `apps/client/src/services/api/theme-jobs.ts`
- `apps/client/src/pages/SchemeDetail.vue`

#### 模型选择未进入当前请求链路

换主题页提供 `selectedModel`，但当前费用请求和任务创建请求未携带该选项；详情页原有未传入换主题流程的模型选择已在 3.4 实施时移除。

建议明确一种模式：

- **平台决定模型**：显示实际使用模型，不提供用户选择控件。
- **用户决定模型**：选择贯穿费用确认、任务创建及结果信息。

这是前端代码可见的不一致；服务端最终使用模型的规则需在实施时进一步核对。

#### 费用与生成数量的展示需要同步

当前生成数量变化时，数量显示更新，但费用 offer 不同步刷新；提交确认前会重新获取。

建议参数变化后刷新费用，或明确显示“费用待更新”，避免同时出现新数量和旧总费用。

#### 操作文案避免与展台报价混淆

| 当前表达 | 建议表达 |
|---|---|
| 获取报价并确认 | 确认积分并生成 |
| 展台服务报价入口 | 申请展台报价 |
| 生成参数配置 | 品牌与视觉偏好 |

#### 失败应有可见反馈

当前获取费用、创建任务失败主要记录到控制台，用户反馈不足。

建议统一展示发生的问题、输入是否保留、可执行的重试动作。

#### 视觉方向

采用“大画布 + 品牌调整面板”，突出原图、品牌色与风格偏好，将技术配置降到次级。

### 3.6 换主题结果区分预览与选定

**代码位置：**`apps/client/src/pages/ThemeJob.vue`

**现状：**用户可浏览多张结果，但报价和素材生成使用的是已选定结果，不一定是当前预览图片。

**建议：**

- 显示“正在预览第几张”。
- 单独展示已选定效果的缩略图和标识。
- 主按钮明确使用“已选定效果”。
- 尚未选择时，突出“选用此效果”。
- 多结果切换采用缩略图，减少仅使用数字的识别成本。
- 顶部弱化长任务 ID，突出方案和任务状态。
- 保存最终效果失败时提供明确提示；冲突刷新后也应解释当前状态。

### 3.7 人工需求与报价申请减少重复步骤

**代码位置：**

- `apps/client/src/pages/AISelection.vue`
- `apps/client/src/pages/QuoteRequest.vue`
- `apps/client/src/pages/ManualRequest.vue`

**现状：**人工入口先通过弹窗填写联系人与联系方式，再进入完整申请。虽然信息会带入，但用户仍需经过两轮表单界面。

**建议：**

- 首页人工入口只确认需求摘要，联系方式集中在完整申请页填写。
- 保留草稿恢复、登录返回、重复提交保护和回执机制。
- 延续“展会信息 → 需求与预算 → 联系方式”的分段结构。
- “国家代码”改为“国家/地区”。
- 方案修订号等技术信息放入次级详情。
- 主摘要突出所选方案、所选主题和资料完整度。
- 成功提交后明确进入项目详情查看进展，不展示没有业务依据的响应时限。

### 3.8 检索记录与项目回访体验

**代码位置：**

- `apps/client/src/pages/MySearches.vue`
- `apps/client/src/pages/MyProjects.vue`

#### 检索记录

当前每次检索展开全部方案，每个方案又展开主题和四方向区域，容易产生长页面和大量空占位。

建议：

- 默认展示需求摘要、时间、方案缩略图和生成状态。
- 展开后再查看详细成果。
- 已有主题和素材任务提供直接进入任务页的入口。
- 未生成内容使用紧凑状态，不占据大块空卡片。

#### 我的项目

当前偏申请数据展示，部分条件直接展示 JSON，需求范围直接展示代码。

建议：

- 条件转为可读标签和规格摘要。
- 范围代码映射为用户名称。
- 卡片突出展会、当前状态、最近更新和下一步。
- “公开处理结果”改为“最新进展”等用户语言。
- 在缺少真实事件历史接口时，先完善当前状态和最新结果，不绘制虚构时间线。

## 四、UI 美学方向

### 4.1 推荐定位：专业展陈设计工作室

关键词：**空间感、大图、克制、清晰、可信。**

用户的核心关注是展台外观、适用性和落地方式。视觉应围绕真实方案和决策信息组织。

### 4.2 色彩体系

- 页面底色使用轻微暖灰或中性灰。
- 白色内容面承载表单、规格和资料。
- 深色文字形成稳定层级。
- 灵通品牌色用于主要强调，具体值以品牌规范为准。
- 成功、待确认、异常使用独立语义色。
- 延续现有 HSL CSS 变量机制，建立统一规则。

现有基础位置：

- `apps/client/src/components/theming/themes.css`
- `apps/client/src/styles/global.css`
- `apps/client/tailwind.config.js`

### 4.3 字体与排版层级

以下为建议尺度，需结合实际字体与屏幕验证：

| 内容 | 建议尺度 |
|---|---|
| 首页主标题 | 桌面约 36–44px，移动约 28–32px |
| 普通页面标题 | 28–32px |
| 区块标题 | 18–20px |
| 表单与正文 | 14–16px |
| 编号、时间与次要说明 | 12–13px |

- 重要匹配差异、费用规则和操作说明不应全部使用小字。
- 中文首先保证清晰阅读。
- 等宽字体用于编号、尺寸和数值，不承担全部标题表达。
- 统一页面宽度、标题间距、区块留白和表单行距。

### 4.4 减少卡片嵌套

当前大量区块采用近似的边框卡片，视觉权重平均。

建议按内容性质分配承载方式：

| 内容 | 建议承载方式 |
|---|---|
| 方案图片 | 大幅展示，减少外框 |
| 表单输入 | 浅色面板、明确分组 |
| 规格与说明 | 留白、分隔线、定义列表 |
| 异常与待确认 | 语义底色与清晰行动入口 |
| 主要操作 | 每个阶段突出一个主按钮 |

### 4.5 图片与动效

- 首页可使用已有、可公开展示的真实方案效果图。
- 结果页统一图片比例和背景。
- 详情图优先完整展示结构，避免裁掉展台边缘。
- `BoothIllustration` 适合示例和空状态，不宜承担全部品牌展示。
- 动效集中于图片切换、任务状态变化和轻量进入效果。
- 避免干扰看图和决策的持续动画。

## 五、移动端与可访问性关注点

以下需通过实际浏览器验证：

1. 部分素材预览、下载操作依赖 hover，应支持触屏与键盘操作。
2. 品牌色删除入口依赖 hover，需提供稳定的可操作入口。
3. 换主题结果页的固定宽度骨架与长任务 ID 需检查窄屏溢出。
4. 详情页资料预览应统一使用具备焦点管理和键盘关闭能力的弹窗原语。
5. 底部操作区需避开系统安全区，并避免遮挡内容。
6. 重要状态不能仅依赖颜色表达。
7. 输入错误应靠近相关字段，并保留已填写内容。

## 六、实施优先级与范围

| 优先级 | 内容 | 主要收益 | 实施边界 |
|---|---|---|---|
| P0 | 模型选择与请求一致、费用刷新、失败反馈、澄清字段可直接修改 | 操作可信 | 部分需确认后端契约和产品语义 |
| P1 | 业务导航、详情宽内容区、报价主入口、可选路径说明 | 主流程清晰 | 主要为现有前端调整 |
| P1 | 品牌配色、文字层级、页面宽度、按钮与状态规范 | 视觉一致 | 基于现有主题变量与组件 |
| P2 | 智选首页、方案卡片、换主题工作区、结果选择体验 | 提升吸引力与易用性 | 真实方案名称可能需接口支持 |
| P2 | 历史记录收敛、任务直达、项目详情去技术化 | 提高回访效率 | 优先复用已有数据 |
| P3 | 完整多语言、细节动效、进一步响应式打磨 | 提高完成度 | 根据实际覆盖与验证结果推进 |

触屏不可操作、明显溢出等已验证的移动端问题，应随对应页面前置处理，不因整体打磨排在 P3 而延后。

## 七、需要明确的产品决策

### 7.1 第一目标是什么

是促进报价申请，还是促进 AI 主题生成？

**建议：**报价转化为主，主题生成为可选增强。

### 7.2 是否允许自定义尺寸和独立场馆限高

是否允许用户输入方案库之外的尺寸？方案高度与场馆限高是否应独立表达？

这一决策会影响条件表单、澄清操作和无匹配后的人工承接方式。

**已确认（2026-10-04）：**允许自定义长宽；场馆限高独立、选填，常用尺寸仅填入长宽。实施见 3.2。

### 7.3 模型由谁决定

模型由平台统一配置，还是允许用户选择？

这一决策决定是否保留模型选择控件，以及费用和生成链路是否需要增加对应参数。

## 八、实施后的建议验收方式

以下为各项优化实施时的验收依据；实施范围以对应章节的实施记录为准，不代表所有条目均已通过验证。

### 业务与交互

- 用户能从主导航直接找到智选、记录和项目。
- 标准方案可直接进入报价申请，换主题和素材生成明确为可选路径。
- 每项澄清都有可执行的修正方式。
- 界面上的模型、数量、积分确认与最终请求一致。
- 预览结果与选定结果有清晰区分。
- 请求失败有可见反馈，输入保留与重试行为明确。
- 申请成功后能进入对应项目，历史记录能回到已有任务。

### 视觉与响应式

- 方案图片成为结果页和详情页的视觉中心。
- 物料表格不再挤入狭窄侧栏。
- 桌面和移动端主操作均易发现。
- 重要操作不依赖 hover。
- 长编号、任务 ID、表格及错误文案不造成页面级横向溢出。
- 明暗模式下文字、输入、状态与焦点均清晰可辨。

### 工程检查

- 非平凡前端改动后，在 `apps/client` 执行 `pnpm build`，完成类型检查和生产构建。
- 对涉及请求参数、状态与费用的改动，补充针对性的行为验证。
- 真实登录、积分、生成和报价链路需在具备对应后端与测试账户的环境验证，静态预览不能替代。

## 九、结论

建议先推进 **导航业务化、首页聚焦、详情页重排**，同时修正模型选择、费用展示和澄清入口等交互不一致。

完成业务结构和交互基础后，再通过统一品牌色、排版、图片呈现和适量动效提升美感，比单独换配色更能提升整个客户端的品质。
