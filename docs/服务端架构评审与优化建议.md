# 服务端架构评审与优化建议

## 1. 评审结论与范围

**现有服务端架构总体合适，目录组织符合 Node.js/TypeScript 后端的常见实践。建议保留整体架构，重点加强模块边界、接口契约和 Worker 调度隔离。**

目前最值得投入的是职责隔离、依赖约束和运行可靠性，而不是整体重排目录。

本次检查范围包括：

- API、Worker 入口及生命周期管理。
- 路由注册、鉴权和权限控制。
- 主要业务模块及跨模块依赖。
- 数据库事务、积分账本和任务创建。
- Outbox、任务恢复、调度器及外部通知投递。
- 接口契约、测试组织和工程检查配置。

评审基准为 `main` 分支提交 `308b65c`（2026-10-09）。此时 `apps/server/src` 下有 **238 个 TypeScript 文件、约 1.76 万行代码**，另有 **73 个测试文件**。统计包含占位文件，不能直接作为业务复杂度指标。文中行号均对应该提交，后续代码变动后可能偏移。

本文基于该提交的源码静态检查及 Fastify 官方文档，**未运行测试、压测或故障演练**。文中运行风险表示源码可见的影响路径，其中的耗时为按超时配置推算的最坏情况，不代表已经复现的线上故障。

下文源码路径均相对于仓库根目录。

## 2. 整体架构是否合适

### 2.1 当前架构：模块化单体 + 独立异步 Worker

```text
参展商端 / 管理端
        │
        ▼
Fastify API
  http/：路由、校验、身份、响应
        │
        ▼
  modules/：按业务领域组织
        │
        ▼
  PostgreSQL / Redis / S3 / 外部服务
        ▲
        │
独立 Worker
  队列消费、Outbox、恢复、对账、通知
```

这个方向与当前业务匹配：

1. **业务关联紧密**：项目、方案、资产、积分和生成任务之间存在强关联，共享数据库便于维护事务一致性。
2. **长耗时任务独立执行**：AI 生成通过 Worker 处理，与 HTTP 请求生命周期分开。
3. **多个门户共享业务能力**：参展商端和管理端调用同一套领域模块，减少重复实现。
4. **开发与运维成本可控**：当前规模适合模块化单体，尚无必要仅因目录规模而拆成微服务。

建议继续以模块化单体作为长期基础，让 API 和不同类型 Worker 按实际负载独立扩容。

### 2.2 已有设计中的优点

| 方面 | 源码中体现的设计 | 评价 |
| --- | --- | --- |
| 入口与生命周期 | `api.ts`、`app.ts`、`worker.ts` 分开，包含优雅退出 | 清晰，便于测试和部署 |
| 依赖方向 | `modules` 不依赖 HTTP、Fastify 和 Worker 调度，且有 AST 边界测试 | 比只靠文档约定更可靠 |
| 任务一致性 | 任务、Outbox 和积分预占在同一事务内提交 | 适合付费生成业务 |
| 故障恢复 | Outbox 重投、任务租约、恢复矩阵、积分对账 | 对真实运行问题有明确处理机制 |
| 外部 AI 接入 | 协议注册表、供应商适配器、配置快照 | 能控制供应商变动对业务的影响 |
| 验证体系 | 路由测试、数据库/Redis 集成测试、故障注入测试 | 覆盖方向合理 |

主要依据：

- [`apps/server/src/modules/generation/theme/service.ts`](../apps/server/src/modules/generation/theme/service.ts)：在 `createThemeJob()` 中将任务创建、Outbox 写入和积分预占放在同一事务内。
- [`apps/server/tests/generation-outbox-integration.test.ts`](../apps/server/tests/generation-outbox-integration.test.ts)：包含入队成功但数据库提交失败等故障恢复场景。
- [`apps/server/tests/module-boundaries.test.ts`](../apps/server/tests/module-boundaries.test.ts)：通过 AST 检查约束技术层之间的依赖方向。
- [`apps/server/src/modules/generation/theme/attempts.ts`](../apps/server/src/modules/generation/theme/attempts.ts)：记录供应商尝试和结果不明状态，避免对不确定结果盲目重新提交。

这些设计比目录名称更有价值，后续调整应优先保护其事务、幂等与恢复语义。

## 3. 目录组织是否符合主流

### 3.1 当前采用合理的混合结构

常见组织方式有三类：

| 方式 | 示例 | 适用情况 |
| --- | --- | --- |
| 按技术层 | `controllers/`、`services/`、`repositories/` | 小型 CRUD 项目，上手简单 |
| 按业务功能 | `projects/` 内放路由、服务、数据访问 | 业务模块相对独立 |
| 混合式 | 外层 `http/modules/infra`，业务层再按领域划分 | 多门户、共享业务、HTTP + Worker |

当前项目属于第三种。对于参展商端、管理端共用业务服务的项目，这个选择合理。

Fastify 官方强调插件封装、作用域和注册顺序，并不强制使用固定的 `controller/service/repository` 目录。当前通过 `app.register()` 分别封装门户鉴权与路由，与其设计方式一致。

### 3.2 路由命名存在两套风格

例如：

```text
http/admin/users.controller.ts   # 实际实现
http/admin/users/index.ts        # 只有占位注释

http/admin/roles.controller.ts   # 实际实现
http/admin/roles/index.ts        # 只有占位注释
```

其他大部分模块将路由实现放在 `index.ts` 中。这会增加判断入口和有效实现的成本。

建议逐步统一：

- `index.ts`：门户注册或模块公开导出。
- `routes.ts`：具体路由注册与 handler。
- `schema.ts`：较复杂的请求、响应契约。
- 简单 schema 可以留在路由文件内，按实际复杂度拆分。

### 3.3 占位目录容易误导读者

`http/su/index.ts` 目前只有注释，`app.ts` 实际注册的是 client/admin。根目录 `AGENTS.md` 的“前后端契约”写有“SU 接口在 `apps/server/src/http/su/`”，`apps/server/AGENTS.md` 的源码结构也列出了“SU HTTP 入口”，容易让人误以为 SU 已经有完整实现。

建议清理确认废弃的占位文件（`http/su/index.ts`、`http/admin/users/index.ts`、`http/admin/roles/index.ts`），并修改上述两处文档，明确 SU 尚未实现。清理前应确认文件是否仍承担规划或其他用途。

### 3.4 统一职责，而非强制统一层数

当前业务模块使用了以下名称：

- `domain.ts`
- `service.ts`
- `repository.ts`
- `queries.ts`
- `submission.ts`
- `execution.ts`

这些名称本身没有问题。生成任务采用 `submission/execution/queries`，比将所有逻辑集中到一个 `service.ts` 更能表达业务。

建议统一职责定义：

| 文件类型 | 职责 |
| --- | --- |
| `domain` | 业务规则、状态和纯计算 |
| `service` 或按用例命名的文件 | 流程编排、事务边界 |
| `repository/queries` | 持久化和查询 |
| 对外入口 | 声明其他模块允许调用的能力 |

不必要求每个模块都创建相同数量的文件，也不必为简单功能增加空转发层。

## 4. 主要架构改进建议

### 4.1 模块间边界偏软

**优先级：高。**

当前边界测试主要限制：

```text
infra 不能反向依赖 modules
modules 不能依赖 http/workers
```

但尚未约束：

- 一个业务模块可以调用另一个模块的哪些能力。
- 外部模块是否允许直接引用内部 repository 或执行步骤。
- 哪些模块允许修改某张业务表。

源码中已经出现模块层面的双向依赖：

- `identity/client-service.ts` 调用 `projects/claims.ts`。
- `projects/admin-service.ts` 调用 `identity/roles.ts`。
- `selection` 使用 `prompts`，而 `prompts/preview.ts` 又调用 `selection` 与 `generation` 的内部实现。

这是业务模块依赖图上的双向依赖，**不等于已经出现运行时循环导入故障**，但会增加独立理解、测试和修改模块的成本。

建议：

1. 为核心模块明确少量公开能力，沿用合适的 `service.ts` 或增加精简的 `index.ts`。
2. 外部模块只使用公开能力，减少直接引用内部 repository、执行步骤。
3. 对跨模块用例明确唯一编排位置，例如登录后的游客数据归属处理。
4. 在边界测试中逐步加入允许依赖规则。

公开入口应形成真正的边界，不能只是将所有内部函数重新导出。

### 4.2 数据所有权比 import 边界更需要关注

**优先级：高。**

`credits/service.ts` 的 `lockCreditJob()` 直接读取并锁定 `theme_jobs`、`artwork_jobs`。积分模块了解了生成任务的状态、租约、价格和可用张数。

即使 import 没有形成循环，数据库层面仍然存在紧密耦合。这种设计有合理原因：需要保证积分结算和任务状态一致。但继续增加生成类型时，积分模块可能需要认识更多业务表。

建议先明确表的归属和写入规则：

- `generation` 负责生成任务生命周期。
- `credits` 负责余额、预占、扣费、释放及账本不变量。
- 跨模块结算由明确的用例组织，在同一个数据库事务中完成。
- 保留统一锁顺序、并发检查和现有幂等保障。
- 统计、报表类跨表查询可以设置明确例外。

这项调整涉及积分账本一致性，应在现有集成测试保护下分步推进。若涉及表结构或既有数据，必须通过迁移处理。

依据：[`apps/server/src/modules/credits/service.ts`](../apps/server/src/modules/credits/service.ts)。

### 4.3 Worker 已有异常隔离，但缺少耗时隔离

**优先级：高。**

`workers/scheduler.ts` 在一轮 `tick()` 中逐个执行调度任务：

```ts
await task.run();
```

这些任务包括：

- Outbox 分发（基础、主题、画稿、客服翻译，间隔 1 秒）。
- 任务恢复和积分对账。
- 邮件与 Webhook 投递。
- 客服维护。
- 指标采集。

顺序执行是有意的设计：`scheduler.ts:29` 注释说明，这样能让调度工作只占用一个数据库连接（连接池上限为 10）。后续改造需要在这个约束和耗时隔离之间取舍，不能直接改成全部并发。

问题在于，邮件投递内部逐封等待 SMTP，而健康评估要等整轮 tick 结束才执行。按当前配置推算，SMTP 不可达时的最坏情况如下：

| 环节 | 源码配置 | 影响 |
| --- | --- | --- |
| 单封邮件 | `mailer.ts:15`：连接超时 10 秒、问候超时 10 秒、socket 超时 20 秒 | 每封至少等待 10 秒才失败 |
| 一轮投递 | 回执邮件、客服邮件每批各领取 10 封（`receipt-emails.ts:28`、`customer-service/emails.ts:61`） | 两类邮件合计，一轮 tick 可达 200 秒以上 |
| 生成任务分发 | 主题、画稿 Outbox 每轮只执行一次 | 新建生成任务的入队延迟随 tick 时长增加 |
| Worker 健康 | Outbox 任务 `staleAfterMs` 为 30 秒（`worker.ts:144-146`），健康在 tick 结束后计算 | 本轮结束即判定 unhealthy 并删除 `/tmp/worker-ready`；compose 健康检查要求心跳在 30 秒内，约 2 分钟后容器标记为 unhealthy |
| 多副本 | 两类邮件的领取租约均为 120 秒 | 单批耗时超过租约后，其他 Worker 副本可能重新领取同一批邮件，造成重复发信 |

当前只有单个 Worker 副本，重复发信暂不会发生；但下文建议的按角色拆分 Worker，或者水平扩容，都会让它成为现实问题。

建议：

1. 将高频分发、恢复任务与慢外部投递分开调度，例如分成关键调度和外部投递两条执行链。各链内部仍按顺序执行，这样既能隔离耗时，又能保持数据库连接占用有界。
2. 保留同一任务不重入的约束。
3. 心跳与任务健康评估独立于整轮执行完成，避免慢投递拖累关键任务的健康判断。
4. 让单批投递的最长耗时明显小于领取租约，例如按截止时间提前结束本批，或者缩小批量。
5. 负载增大后，再按生成、通知、客服等角色拆分 Worker 进程。拆分前必须先完成第 4 条。

仅将 `worker.ts` 拆成多个文件不能解决运行隔离问题。

### 4.4 HTTP 契约还不够完整

**优先级：中高。**

目前很多路由同时手写 TypeScript interface 和 JSON Schema，两者存在维护漂移的可能。

本次对 `src/http` 的检索未发现显式的 `response:` schema；`app.ts` 的健康检查则有响应 schema。业务接口的 Swagger 响应描述、输出字段约束和前后端类型联动还有提升空间。

建议：

1. 沿用现有 JSON Schema，评估 Fastify 的 `json-schema-to-ts` Type Provider。
2. 优先补齐核心业务成功响应和公共错误响应 schema。
3. 逐步让请求类型从 schema 推导。
4. 契约稳定后，再用 OpenAPI 生成前端类型或客户端。

引入响应 schema 时，需要验证序列化后的字段和既有前端契约一致，避免因字段未声明而被过滤。

错误响应与根目录 `AGENTS.md` 的约定存在两处已确认的偏差：

1. **错误 code 超出约定集合**：约定只有 `VALIDATION_ERROR`、`REQUEST_ERROR`、`INTERNAL_ERROR`，但有两处返回 `NOT_FOUND`：全局 404 处理 `app.ts:67`，以及模板不存在时的 `http/admin/prompt-templates/index.ts:63`。
2. **错误结构多出字段**：约定的结构是 `{ error: { code, message, requestId } }`，但 `app.ts:65` 的统一错误处理还会输出 `reason`（如 `SIGN_IN_DISABLED`、`USER_NOT_FOUND`）和 `details`。`code` 只区分错误大类，前端区分具体业务错误实际依赖的是 `reason`，但约定中没有记录它。

第 2 处影响更大：`reason` 是事实上的业务错误契约，却没有文档和 schema 约束。建议在补齐公共错误响应 schema 时一并声明 `reason`/`details`，同步更新根目录约定，并统一 `NOT_FOUND` 的处理方式。

### 4.5 权限声明与路由分离过远

**优先级：中。**

`http/admin/authorization.ts` 根据 URL、HTTP 方法和正则集中推导权限。

现有保障比较完整：

- 未知路径返回 `null`，默认拒绝。
- `tests/admin-roles.test.ts:187` 会遍历 `/openapi.json` 中的全部管理端路径，断言每条非认证路由都有权限策略，且权限码都在权限目录中。新增路由漏配会直接导致测试失败。

随着路由增加，主要问题在于维护成本：

- 新增路由需要同步修改远处的匹配表。完整性测试只保证“有策略”，不保证“策略正确”。
- 路由改名可能悄悄落入另一条正则分支，例如以 `/schemes` 开头的路径都会被归入方案权限。
- 资产类型、修改字段等细粒度判断仍分散在其他位置，例如提示词模板的字段级权限在同文件的 `preHandler` 中。

另外有两套权限判断语义并存，需要在文档或代码中写明：

| 位置 | 多个权限码 | 依赖权限（`requires`） |
| --- | --- | --- |
| `registerAdminAuthorization` 的 onRequest hook（`authorization.ts:96`） | 任一满足即可（`.some()`） | 不检查 |
| `hasAdminPermission()` / `requireAdminPermission()` | 单个权限码 | 要求依赖全部授予 |

目前 hook 不检查依赖，一般不会造成越权：通过管理端保存角色时，`identity/roles.ts:56` 会调用 `validatePermissionCodes()`（`identity/permissions.ts:70-79`）校验依赖闭包。但这个安全性依赖“权限数据只经由该入口写入”的隐含前提，而迁移补授权限（如 `072_grant_sign_in_config_to_admin.sql`）直接写表，不经过这项校验。建议把这个前提写进文档，或用测试固定下来：执行全部迁移后，各内置角色的权限满足依赖闭包。

建议：

1. 逐步将基础权限声明放到路由配置旁边，由公共 hook 执行。保留现有完整性测试，并改为检查路由声明本身。
2. 涉及对象归属、字段变化的规则继续由业务策略处理。
3. 统一两套判断语义，或明确记录差异及其依赖的前提。

- [`apps/server/src/http/admin/authorization.ts`](../apps/server/src/http/admin/authorization.ts)
- [`apps/server/tests/admin-roles.test.ts`](../apps/server/tests/admin-roles.test.ts)
- [`apps/server/src/modules/identity/roles.ts`](../apps/server/src/modules/identity/roles.ts)
- [`apps/server/src/modules/identity/permissions.ts`](../apps/server/src/modules/identity/permissions.ts)

### 4.6 薄 Controller 和代码风格执行不完全一致

**优先级：中低。**

HTTP 层仍有直接 SQL 和事务编排，例如：

- 签到配置写入（已修复，见下文）。
- BOM 发布状态检查。
- 项目资产查询。
- 审计日志列表查询。

简单查询直接使用 SQL 不一定产生问题，但写操作和业务可用性判断更适合收回业务模块，便于 HTTP、Worker 等入口复用一致规则。

签到配置写入是一个已经产生缺陷的例子。评审基准中，`PUT /api/v1/admin/credits/sign-in-config`（`http/admin/credits/index.ts:60-77`）直接在 HTTP 层执行 SQL：

- **时区未校验**：`timezone` 只限制了字符串长度，`migrations/069_sign_in_config.sql` 也没有约束。这个值随后被 `modules/credits/account-service.ts` 用于 `AT TIME ZONE $2`。管理端界面只提供三个固定选项，正常操作不会触发；但只要绕过界面直接调用接口，写入非法时区（如拼写错误的 `Asia/Shanghia`），所有用户签到都会因数据库报错返回 500，直到配置被改正。此外，`UTC+8` 这类 POSIX 写法能被 `AT TIME ZONE` 接受，但其正负号与直觉相反，会把签到日期算错，也不应该允许写入。
- **缺少审计**：AI 模型、角色、方案、客服设置等管理端配置写入都记录了审计日志，这个接口没有。

**已修复**：写入已移入 `credits` 模块的 `updateSignInConfig()`。时区必须与 `pg_timezone_names` 中的名称完全一致，否则返回 400（`reason: INVALID_TIMEZONE`），并且不会开启事务。配置写入与审计日志（`sign_in_config.update`，记录修改前后的值）在同一事务内完成。对应测试见 `tests/credits.test.ts` 和 `tests/sign-in-config-integration.test.ts`。这个例子说明，写入逻辑收回业务模块后，校验和审计更容易与读取方保持一致。

此外，代码格式不统一：`http/admin/projects/index.ts` 整个文件都是压缩格式（省略空格、多条语句挤在一行）；`projects/service.ts`、`projects/admin-service.ts` 也有部分代码被压缩成较长的单行。服务端 `package.json` 暂无 lint/format 脚本。

建议：

- 优先迁移 HTTP 层中的其他业务写入和规则判断。
- 为服务端统一格式化与基础静态检查。
- 按实际可读性拆分函数，避免仅根据行数机械拆文件。
- 修改检查命令时同步更新子项目文档、Git hooks 和 CI。

## 6. 推荐实施顺序

| 顺序 | 工作 | 主要收益 |
| --- | --- | --- |
| 0 | ~~修复签到配置时区校验并补审计日志（4.6）~~ **已完成** | 消除已知的全站签到故障路径 |
| 1 | 隔离慢投递与关键 Worker 调度，单批投递耗时控制在租约内 | 提高任务链路稳定性，为拆分 Worker 扫清重复投递风险 |
| 2 | 明确模块公开能力、数据归属，增强边界测试 | 控制业务增长带来的耦合 |
| 3 | 补齐核心响应 schema 和错误 schema（含 `reason`），收敛 schema 与类型 | 提高前后端契约可靠性 |
| 4 | 权限声明贴近路由，统一权限判断语义，收回 HTTP 中的业务写入 | 降低新增接口时的遗漏成本 |
| 5 | 统一命名、格式化，清理占位文件并修正相关文档，整理测试目录 | 改善导航与日常维护 |

每一项应独立控制改动范围，并验证原有业务语义：

- 调度隔离：验证慢投递期间关键调度仍可推进、健康状态不受影响、同一任务不重入、单批耗时不超过租约、停机可完成。
- 模块边界：验证事务边界、锁顺序、积分不变量和幂等性不变。
- 接口契约：验证序列化输出、错误包装及前端调用契约一致。
- 权限调整：验证公开接口、默认拒绝、基础权限和细粒度规则。
- 测试整理：验证测试收集完整，集成测试没有意外跳过。

实际实施非平凡代码改动后，按服务端约定执行标准 Docker `check`；涉及服务端代码或迁移时，按项目要求重新部署并验证 dev 栈。

## 7. 最终判断

**现有架构基础值得保留。当前需要的是把“按领域分目录”进一步落实成“按领域管理依赖与数据”，同时改善异步调度和接口契约。整体重构的收益暂时不如这些定向改进。**
