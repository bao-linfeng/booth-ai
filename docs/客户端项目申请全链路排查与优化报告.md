审查日期：2026-10-09

范围：报价申请、人工需求、草稿与登录交接、后端受理与资料固定、匿名认领、通知与客服、我的项目和素材补交。

## 1. 结论与证据边界

**项目申请主链路已有完整业务骨架，优先优化数据交接准确性、异常恢复和提交后的信息完整性。** 不需要重新搭建申请模块。

已具备的关键能力：

- 两类申请共用表单、草稿与提交协调逻辑。
- 网络结果未知时保存原请求体与幂等键，服务端事务内去重。
- 报价提交重新校验方案、清单、主题及素材版本，并固定资料快照。
- 默认承接人不可用时明确拒绝新增项目，而非创建无人承接的记录。
- 匿名提交按联系邮箱待认领，登录后归入本人项目。
- 受理事件、管理通知、回执邮件在事务内入库，异步投递。
- 回执及项目详情可以携带项目上下文咨询客服。
- 客户仅查看本人项目，后台负责跟进、人工报价及结果处理。

本次交付是**排查与优化实施文档**，未修改业务代码。工作区原有方案导入相关修改及其他报告均保留。

## 2. 完整业务链路

```text
AI 智选结果 ─→ 方案详情/清单 ─→ 标准方案报价 ───────────┐
      │              └→ 换主题结果 ─→ 主题报价 ────────┤
      │                     └→ 完整四面素材 ─→ 素材报价 ┤
      └→ 人工需求交接 ─→ 人工需求申请 ────────────────┤
                                                       ↓
      恢复草稿 → 加载资料/地区字典 → 填写与校验
                                                       ↓
      固定请求体 + requestKey → 持久化 → 提交
                                                       ↓
      身份/限流/Schema → 规范化 → 幂等查询
                                                       ↓
      资料校验与快照（报价）/需求校验（人工）→ 校验承接人
                                                       ↓
      同一事务：项目 + 资产版本引用 + 受理事件
                + 通知 Outbox + 邮件队列 + 幂等回执
                                                       ↓
      受理回执 → 客服咨询 → 登录/邮箱认领 → 我的项目
                                                       ↓
      后台跟进/人工报价/公开结果 → 客户查看状态
                                                       ↓
      主题项目可补齐四面素材 → 校验本人/项目版本/固定主题 → 固定交付
```

### 2.2 数据与状态约束

| 数据 | 当前规则 | 应保持的约束 |
| --- | --- | --- |
| 原始需求与确认条件 | 智选会话经 `selection/handoff.ts` 交接 | 必须与本次检索一致，不能仅凭方案相同附带当前会话 |
| 草稿 | `sessionStorage`，报价按方案/主题任务/素材任务分键 | 已发送未知结果不能换键、换请求体重提 |
| 草稿归属 | 同账号恢复；未提交匿名草稿可接手 | 账号变化不能静默复用别人的联系人或请求状态 |
| 申请身份 | 登录用户 ID；匿名项目先记 `claim_email` | 客服访客身份不等于项目最终归属 |
| 方案资料 | 提交事务重新捕获并记录资产版本引用 | 后续方案改动不能改写已受理项目资料 |
| 自定义主题素材 | 无四面素材时 `pending`；有完整套装才 `available` | 不得以标准素材替代自定义主题素材 |
| 项目状态 | `pending / following / quoted / won / lost / closed` | 受理不等于报价，素材可用不等于生产制作确认完成 |
| 报价状态 | 后台进入 `quoted` 必须有发送依据 | 仅保存报价单并不代表已发送给客户 |

服务端关键证据：`projects/service.ts:20–78`、`snapshot.ts:36–103`、`artwork-delivery.ts:9–37`、`admin-service.ts:78–116`。上述路径均位于 `apps/server/src/modules/`。

### PA-01：报价需求上下文可能串入另一轮检索

**证据：**

- `apps/client/src/pages/ThemeJob.vue:148–150` 继续报价仅传 `themeJobId`。
- `apps/client/src/pages/ArtworkJob.vue:192` 素材报价仅传主题与素材任务 ID。
- `apps/client/src/pages/QuoteRequest.vue:31` 从当前会话读取交接。
- `apps/client/src/features/selection/handoff.ts:31–42` 仅在收到 `searchId` 时才比较检索身份；否则只要求当前匹配结果包含此方案。

**触发：**S1 选方案 A 并生成主题；同标签页再以不同要求做 S2，仍返回 A；从历史 S1 主题或素材结果申请报价。此时可能固定 S1 素材，却附带 S2 的需求。

**优化：**主题任务来源持续传递到报价端，要求显式核对检索身份；来源未知时不自动猜测当前需求。若要支持历史任务完整恢复，按权限从服务端读取原检索，而不是依赖当前唯一会话。

**验收：**同方案的两个检索交叉进入报价，需求、主题、素材始终来自同一链路；原检索无法恢复时明确说明未带入，不串用新会话。

此项与《客户端AI智选至四向图流程审查报告》B06 为同一交接问题，应合并实施，避免重复修复。

### PA-02：路由变化没有重建报价上下文

**证据：**`QuoteRequest.vue:27–35` 将 `code`、草稿键和交接读取一次；`useQuoteContext.ts:65` 只在挂载加载；`App.vue:17` 使用无业务 key 的 `RouterView`。

**触发：**在同一报价组件实例中从方案 A 的报价路由切至 B，或只改变主题/素材 query。页面保留首次 code、表单与 pending，读到的动态 query 又可能属于新路由。

**优化：**按报价业务身份重建局部页面，或统一监听 `code/themeJobId/artworkJobId/searchId` 完成保存、取消旧请求、恢复新草稿。不要仅监听 code；不要将所有路由 query 变化都视为重建，刷新时移除 `bomRevision` 不应误丢表单。

**验收：**真实 Router 内连续切换两方案、两主题、两素材任务；标题、预览、草稿、提交体一致，旧异步响应不能回写新页面。

### PA-03：存储异常会破坏提交状态流

**证据：**`useRequestDraft.ts:34–50` 恢复时直接类型断言，异常分支的 `removeItem` 及 `persist` 的 `setItem` 均无独立保护；`useRequestSubmission.ts:48–56` 先设置 pending、持久化，随后才进入发送异常处理。

**影响：**存储被禁用或配额不足时，提交可能在 POST 前抛错，pending 已存在导致表单冻结，却没有可理解提示。成功回执保存失败也会落入网络错误分支。合法 JSON 但结构错误的草稿没有版本与结构校验。

**优化：**为读取、写入、清理分别提供明确结果；校验草稿版本与必要结构。首次发送前若无法可靠保存未知结果恢复信息，应明确提示并保持可编辑，而不是静默承诺“已保留”；发送后的写入失败应保留内存原请求和回执，不当成服务端受理失败。

**验收：**模拟读取失败、写入失败、清理失败、损坏 JSON、错误结构；无未处理异常，是否已发送明确，重试不更换已发送请求的幂等键。

### PA-04：匿名结果未知后登录，可能重复创建同一业务申请

**证据：**`QuoteRequest.vue:57、76` 待确认时仍可登录；`useRequestDraft.ts:38–39` 拒绝登录账号恢复带 pending 的匿名草稿；`service.ts:14–17、40–46` 匿名与登录用户使用不同幂等主体。

**触发：**匿名提交已经落库，但回执丢失；用户点击登录。同邮箱项目可能已被认领，但返回申请页不会恢复原 pending。用户重新填写提交会使用新身份、新键，产生第二个项目。

**优化：**待确认期间先完成原身份请求的结果确认；或设计有授权边界的提交查询/登录交接，使已认领项目能回到原回执。不能简单把匿名 pending 改为登录请求重发，服务端幂等主体已经不同。

**验收：**匿名真实受理后故意丢弃响应，再登录同邮箱；能找回原项目且不会诱导重复提交。不同邮箱登录不能拿到原申请资料。补测“首次 POST 正在等待时身份改变”，现有逻辑只检查重试前账号，不检查响应归属变化。

### PA-05：我的项目存在异步乱序覆盖

**证据：**`MyProjects.vue:75–94` 没有请求序号、取消或响应路由校验；切换项目仅清空数据后再次调用 load。`95–99` 会把当前 detail 登记为客服项目上下文。

**触发：**A 详情请求慢，转到 B 后 B 先返回、A 后返回；B URL 下可能展示 A，并把 A 登记成“当前项目”。接口仍限制本人项目，这属于展示与上下文错误，不能据此认定服务端越权。

**优化：**在发起时捕获项目 ID、账号与请求序号，只有当前请求可更新详情、错误和 loading；离开页面废弃未完成请求，身份变化清除数据并重新加载。

**验收：**延迟 A、快速返回 B，最终页面和客服上下文均为 B；A 的失败也不能覆盖 B 的成功；列表分页及退出登录后的延迟响应同步覆盖。

### PA-06：地区依赖失败及切换竞态没有恢复策略

**证据：**`useLocationOptions.ts:12–34` 将失败直接变为空数组，没有错误状态、重试入口和请求身份检查；`RequestFormFields.vue:28–73` 城市为必填选择器，没有手工输入入口。

**影响：**外部字典超时与“没有城市数据”不可区分，空城市用户无法正常完成表单。快速切换国家时，旧国家请求后返回会覆盖新国家选项；服务端仅验证国家格式和城市非空，不检查二者对应关系（`domain.ts:51–60`）。

**优化：**区分加载/空数据/失败，提供就地重试；国家变化立即清空旧城市选项并丢弃旧响应。确认字典覆盖范围后决定是否允许手填城市，不应在字典故障时静默提交错误城市。

**验收：**字典超时后可恢复；A→B 快速切换且乱序返回时只显示 B；已有草稿恢复不被无关请求覆盖。

### PA-07：项目详情不能完整回看申请内容

**证据：**服务端 `http/client/projects/index.ts:14–17` 同时返回 `notes`、`originalDescription` 和 `unresolvedQuestions`；客户端 `MyProjects.vue:240–243` 用 `originalDescription ?? notes` 二选一，全页未展示待确认问题。

**影响：**人工需求以及带原始需求的报价申请，用户填写的补充说明被隐藏。销售待确认问题也无法由客户回看。数据仍在服务端，并非提交时丢失。

**优化：**原始需求、补充说明、待确认事项分别展示，空项不占位；公开匹配差异是否展示由业务确认，不暴露后台内部记录。

**验收：**同时填写需求和备注、带两项待确认问题提交，项目详情全部显示；只有备注的历史项目仍正常。

### PA-08：资料读取失败恢复入口不足

**证据：**`useQuoteContext.ts:54` 捕获全部异常并改成“方案或选定效果已变化”；`QuoteRequest.vue:74–75` 只有 conflict 时显示刷新，首次普通请求失败会令 context 为空并禁用提交。

**优化：**区分网络读取失败、认证失败、方案不可用、主题/素材不一致；读取失败提供保留表单的重试。重试不能覆盖已发送 pending；刷新期间清理旧预览并废弃旧响应。

**验收：**首次超时后页内重试成功；404/409/401 各有正确行动提示；表单不丢失，未知结果仍原样重发。

### PA-09：完整素材申请仍显示待补充

**证据：**`QuoteRequest.vue:80` 只要存在 theme 就展示 `artworkPending`，没有排除 `artworkJobId`；但 `useQuoteContext.ts:48–51` 已校验并接受 ready 素材。

**优化：**以选定主题与已校验素材共同决定展示：标准素材、主题素材待补充、完整四面素材随申请固定。回执以服务端 materialsStatus 为准。

**验收：**三个状态文案互斥；携带完整素材的提交前后均不提示待补充。注意 `available` 与服务端 `mappingStatus: unresolved` 可以同时存在，不应宣传为已完成生产制作。

### PA-10：表单前后端校验反馈不一致

**证据：**`useRequestValidation.ts:25–51` 主要校验日期、范围、联系渠道；`RequestFormFields.vue:80` 的预算 pattern 接受 `0`，电话没有格式校验；服务端 `domain.ts:54–60` 拒绝零预算、非法电话、空白展会/联系人/企业名称。`useRequestSubmission.ts:35–39` 多数拒绝统一提示。

**优化：**将正数预算、电话、trim 后必填等明确业务规则纳入字段级校验，统一错误聚焦；服务端继续最终校验。允许的金额精度当前为最多六位小数，不应误用正式报价的币种小数位规则限制“需求预算”。

**验收：**零预算、全空格必填项、非法电话提交前被定位；允许的国际电话和正数预算通过；服务端 400/422 能映射至可行动提示。

### PA-11：通知与跟进闭环优化

**当前实现：**受理及素材补交进入通知 Outbox；管理端改派、跟进、报价修订记录事件。`admin-service.ts:68–104、124–134` 未同步产生对应客户进度通知。客户当前主动刷新查看 `publicResult`。

邮件入队不等于已发送；未配置 SMTP 时待投递。回执邮件最多尝试六次、Webhook 最多八次；异常达到终态后需要人工处理。证据：`receipt-emails.ts:5–18、46–55`、`notifications.ts:5、42–47`、`workers/project-notifications.ts`。

**优化：**明确新申请、改派、资料补交、公开结果更新分别通知谁；展示或监控待投递量、最老等待时间和失败量，给失败任务建立人工重投及操作记录。公开状态通知只发送客户可见字段，不发送内部跟进内容。

**待业务确认：**客户状态变化是否发邮件、跟进响应时效、超过时效如何升级。不要把“客户不能自行跟进项目”认定为缺陷，一期明确客户端只读查看。

### PA-12：上下文读取存在无必要的工作与锁竞争

**证据：**`http/client/quote-requests/index.ts:20` GET 复用 `captureScheme`；`snapshot.ts:44、53–56` 获取方案写冲突锁、读取目录/候选池、锁 BOM。即使无 `requirementContext`，也会读取候选池，而匹配只在 `99–102` 有需求时使用。

**优化：**先将候选池读取放到确实需要计算匹配摘要的分支；再测量上下文 GET 的耗时和锁等待，必要时提供轻量只读上下文查询。POST 事务中的版本校验与资料固定应保留。

**验收：**无需求上下文的请求不读取候选池；并发浏览时减少不必要锁等待；实际提交与资料修改并发时仍能固定一致快照或明确返回版本冲突。

## 4. 异常状态处理目标

| 场景 | 当前策略 | 优化后必须保持/补齐 |
| --- | --- | --- |
| 本地校验失败 | 不发送，保留表单 | 完整字段错误及聚焦 |
| 服务端普通 4xx | 清除 pending，允许修正 | 精确原因；401 登录前保留正确身份边界 |
| 报价 409 | 清除 pending，刷新资料后新键提交 | 区分资料冲突与幂等冲突，不一律解释为资料变化 |
| `503 ASSIGNMENT_UNAVAILABLE` | 明确未受理，清除 pending | 保留内容并给出客服或稍后再试入口 |
| 网络失败、未知 5xx、408 | 保留原 pending | 相同身份、键与请求体恢复，不能随便“重新提交” |
| 429 | 保留原 pending | 读取 Retry-After 显示等待提示，避免反复点击延长排障 |
| 匿名结果未知后登录 | 原 pending 无法按登录身份恢复 | PA-04，确认旧结果或安全找回原项目 |
| 存储失败 | 可能抛出未处理异常 | 明确本地保存能力与是否发送，不误报受理结果 |
| 邮件/Webhook 失败 | 异步重试 | 不回滚已受理项目；达到终态后可人工处理 |
