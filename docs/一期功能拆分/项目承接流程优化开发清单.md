> 日期：2026-10-21 · 版本：v0.1（实施评审稿）

## 2. 业务口径

| 编号 | 口径 | 状态 |
|---|---|---|
| D-1 | 新提交时，如果默认承接人未配置、已停用或缺少权限，项目照常受理，`assignee_admin_id` 置空，进入待分配池。客户端不再出现"暂停受理" | 已确认 |
| D-2 | 待分配项目会通知有 `projects.assign` 权限的管理员：管理端通知中心只对这些人可见，同时推送 Webhook，工作台显示待分配数 | 已确认 |
| D-3 | 待分配项目必须先确定负责人，未分配时跟进、报价、关联方案都返回 409 `ASSIGNEE_REQUIRED`。确定负责人有两种方式：① 角色勾选了 `projects.assign` 的管理员（目前只有超管 `ROLE_ADMIN`）可以分配给任意符合承接条件的人；② 符合承接条件的人（已启用，且有 `projects.read` 和 `projects.follow-up`）在**项目列表**里就能看到待分配项目，点"分配给我"领取。两人同时领取时先到先得，后到的返回 409 `PROJECT_ALREADY_ASSIGNED`。待分配通知仍只发给有分配权限的人 | 已确认（2026-10-21） |
| D-3a | 超管即 `ROLE_ADMIN`，在 `admin_roles` 中配有全部权限码（含 `projects.assign`）。其他角色（`ROLE_ADMIN_USER`、`ROLE_ADMIN_PRODUCT` 等）默认没有任何权限，只有在"用户角色"页配置了 `projects.read` + `projects.follow-up` 后，该角色下的管理员才可能成为承接人。分配和承接都按角色勾选的权限码判断，不写死角色名：分配看 `projects.assign`，其他角色勾选后同样可以分配；承接资格看 `assigneePermissionSql()` | 已确认（2026-10-21） |
| D-4 | 清空默认承接人的含义从"暂停受理"改为"所有新需求进入待分配池" | 已确认（2026-10-21） |
| D-5 | 已受理项目的承接人后来失效时，不自动转入待分配池，保留历史负责人。列表的"需处理分配"筛选会同时列出"待分配"和"承接人失效且未结束"的项目 | 已确认（2026-10-21） |
| D-6 | 项目被分配或改派后，新承接人收到一条只有本人可见的通知 | 已确认（2026-10-21，可延后） |
| A-1 | 状态机新增 `pending → quoted`。待跟进项目打开跟进弹窗时，目标状态默认预选"跟进中"，后端不做隐式状态推进 | 已确认（2026-10-21） |
| A-2 | "保存并标记已发送"在一个事务里完成：保存修订 → 校验修订完整且在有效期内 → 写跟进事件并转为 `quoted`（已经是 `quoted` 的只记录一次发送）。校验不通过时整体回滚，修订也不保存 | 已确认（2026-10-21） |
| B-1 | 客户可见结果改为独立操作，终态项目也可以修改 | 已确认（2026-10-21） |
| B-2 | 报价发送渠道改为与联系类型相同的枚举（电话、邮件、客服、会议、其他）。历史事件中的自由文本照常原样显示 | 已确认（2026-10-21） |
| G-1 | 只有人工需求、非终态且没有任何报价修订的项目可以重新关联方案，否则返回 409 `SCHEME_RELINK_BLOCKED` | 已确认（2026-10-21） |

## 3. 开发方案

### D. 待分配池（P0）

**现状**：`configuredAssignee()` 在承接人失效时抛出 503 `ASSIGNMENT_UNAVAILABLE`，项目不创建；`projects.assignee_admin_id` 为 `NOT NULL`，6 处查询使用 `JOIN admins`；通知收件箱对所有有 `notifications.read` 的人全局可见，不区分接收人。

**数据库（迁移 `089_project_assignment_pool.sql`）**

- `ALTER TABLE projects ALTER COLUMN assignee_admin_id DROP NOT NULL`
- 新增部分索引：`projects(created_at) WHERE assignee_admin_id IS NULL AND status IN ('pending','following','quoted')`
- `project_notification_outbox` 新增两列：
  - `audience text NOT NULL DEFAULT 'all' CHECK (audience IN ('all','assigners','recipient'))`
  - `recipient_admin_id uuid REFERENCES admins(id)`
  - 约束：`audience='recipient'` 时必须有 `recipient_admin_id`，其他取值时必须为空

**服务端**

- `assignment.ts`：`configuredAssignee()` 改为返回 `{ assigneeAdminId: string | null; poolReason: 'unconfigured' | 'disabled' | 'permission_revoked' | null }`，不再抛错。`getAssignmentConfig()` 缺少配置行属于系统不变量被破坏，改抛普通 500。
- `service.ts`：`createQuoteRequest` 与 `createManualProject` 允许承接人为空。`accepted` 事件的 payload 写 `{ assigneeAdminId: null, poolReason }`；对应 outbox 行写 `audience='assigners'`，有承接人时仍为 `all`。
- `repository.ts`、`notification-inbox.ts`、`customer-service/conversations.ts`：`JOIN admins` 改为 `LEFT JOIN`。`assigneeName` 可为空，`assigneeStatus` 增加 `'unassigned'`（`assigneeStatusSql` 增加 `WHEN a.id IS NULL THEN 'unassigned'`）。
- `admin-service.ts`：
  - `assignProject` 支持从空分配，事件 payload 的 `fromAdminId` 为 null。
  - `followUpProject`、`saveQuotation`、`linkProjectScheme` 在 `change()` 内校验承接人非空，否则抛 409 `ASSIGNEE_REQUIRED`。
  - 新增"领取"`claimProject`，接口为 `POST /api/v1/admin/projects/:id/claim`，入参 `{ requestKey }`，权限 `projects.follow-up`（`assertProjectAdmin` 已同时校验 `projects.read`，正好就是承接资格）。
    - 在行锁内判断：承接人已非空就抛 409 `PROJECT_ALREADY_ASSIGNED`；为空则设为当前管理员，项目修订号加 1。
    - 写一条 `assignment` 事件，payload 为 `{ fromAdminId: null, assigneeAdminId: self, selfClaimed: true }`。
    - 列表里的修订号可能已过期，领取以"仍为待分配"为准，不校验 `expectedRevision`。为此 `change()` 要支持跳过修订号校验，幂等仍按 `requestKey`。
    - 领取的是自己，所以不发 D-6 通知。
  - 分配和改派时写一条 `audience='recipient'` 的 outbox 行（D-6）。
- `notification-inbox.ts`：列表、详情、未读数和全部已读都按可见性过滤：`audience='all' OR (audience='assigners' AND :canAssign) OR (audience='recipient' AND recipient_admin_id=:adminId)`。`canAssign` 由路由层根据权限传入。
- `notifications.ts`：Webhook body 增加 `audience` 与 `recipientAdminId`，外部渠道（如企业微信群）可据此路由。
- `dashboard/workspace.ts`：有 `projects.assign` 权限的人新增"待分配"计数和最早 N 条待分配任务。
- `http/errors.ts`：删除 `ASSIGNMENT_UNAVAILABLE` 的 503 特判。`schema.ts` 中项目的 `assigneeAdminId`、`assigneeName` 改为可空。
- 列表查询新增 `assignment=unassigned|needs_assignment`。`needs_assignment` 的含义是：承接人为空，或者承接人状态不是 `active` 且项目未结束。

**管理端**

- `api/core/projects.ts`：`AssigneeStatus` 增加 `unassigned`，`assigneeName` 可空，`assigneeStatusLabels.unassigned = '待分配'`。
- 列表：
  - 承接人列显示"待分配"标签；筛选区新增"分配情况"（全部 / 待分配 / 需处理分配）。
  - 待分配行的操作列增加"分配给我"（需 `projects.follow-up`），领取成功后刷新列表并提示，同时提供"进入项目"链接。遇到 `PROJECT_ALREADY_ASSIGNED` 时提示"已被 XX 领取"，并刷新该行。
  - 有 `projects.assign` 的人，待分配行还会显示"分配"，打开分配弹窗。这个弹窗从 `OperationModal` 抽成可复用组件，列表和详情页共用。
  - "配置默认承接人"弹窗中"留空将暂停受理"的提示改为"留空时新需求进入待分配池"。
- 详情：待分配项目显示提示条，按钮从"改派"变为"分配"（`projects.assign`），另显示"分配给我"（`projects.follow-up`）。跟进、报价、关联方案按钮禁用并说明原因。
- `presentation.ts` 的 `eventSummary`：
  - `accepted` 无承接人时显示"受理项目，进入待分配（原因：未配置 / 已停用 / 缺少权限）"；
  - `assignment` 无原承接人时显示"分配承接人：→ X"；`selfClaimed` 时显示"X 领取项目"。
- 通知中心与工作台：适配新的可见性；新增"待分配"类型文案，跳转到项目详情。
- `api/reason-messages.ts`：新增 `ASSIGNEE_REQUIRED`、`PROJECT_ALREADY_ASSIGNED`。

**客户端**

- `features/quote-request/useRequestSubmission.ts`：删除 503 `ASSIGNMENT_UNAVAILABLE` 分支。
- 所有语言包删除 `quoteRequest.errorAssignmentUnavailable`。

**验收**

1. 默认承接人分别处于未配置、已停用、缺少权限时，报价申请和人工需求都能成功受理。项目进入待分配池；只有有分配权限的管理员能看到通知；Webhook 携带 `audience='assigners'`。
2. 分配后新承接人收到通知，时间线显示分配记录，项目可以正常跟进和报价。
3. 未分配时调用跟进、报价、关联方案，返回 409 `ASSIGNEE_REQUIRED`。
4. 符合承接条件的人可以在列表里一键领取。两人并发领取时，只有一人成功，另一人收到 `PROJECT_ALREADY_ASSIGNED`。不符合承接条件的人调用领取接口返回 403，列表里也不显示该按钮。
5. 幂等重放（同键同体）返回原回执。已有项目和历史事件显示正常。

### A. 报价与状态推进合并（P1）

**服务端**

- `admin-service.ts` 的 `transitions.pending` 增加 `'quoted'`。
- 新增 `GET /api/v1/admin/projects/:id/quotation/revisions`（权限与读取报价相同）。返回 `[{ revision, completeness, currency, totalAmount, validUntil, validityTimeZone, createdAt, createdByName }]`，按修订号倒序。
- `PUT /projects/:id/quotation` 入参增加可选的 `markSent: { sentAt, channel }`。
  - 带 `markSent` 时，额外校验 `projects.follow-up` 权限。
  - 报价修订保存后，复用 `followUpProject` 中的报价依据校验逻辑，把它抽成 `assertPlatformEvidence(quotation, sentAt)`。
  - 写入 `follow-up` 事件：`contactMethod=channel`，`content` 自动生成为"发送报价 QT-xxx rN"，`quoteEvidence` 类型为 `platform`；状态转为 `quoted`。
  - 项目修订号只加一次。
  - 响应返回新的项目状态。

**管理端**

- `QuotationEditor.vue` 在"保存新报价修订"旁新增"保存并标记已发送"按钮，需同时具备 `projects.quotation` 与 `projects.follow-up` 权限。点击后先在小弹窗里选择发送时间（默认当前时间）和渠道。
- `OperationModal.vue`：
  - "已发送的报价修订"从输入框改为下拉框，数据来自 revisions 接口，只列出 `completeness='ready'` 的修订，选项显示总额和有效期。
  - 待跟进项目默认预选"跟进中"。

**验收**

- 待跟进项目可以一步保存完整报价并转为"已报价"，时间线依次出现两条事件：报价修订和跟进。
- 修订不完整时整体失败，报价修订不落库，并提示具体原因。

### B. 跟进弹窗瘦身（P1）

**服务端**

- 新增 `PUT /api/v1/admin/projects/:id/public-result`，入参 `{ requestKey, expectedRevision, publicResult }`，权限为 `projects.follow-up`，终态项目也允许修改。写入 `public-result` 事件，并递增项目修订号。
- `FollowUpInput` 与 schema 删除 `publicResult` 字段。
- `quoteEvidence.channel` 改为联系类型枚举（B-2）。

**管理端**

- 详情页"客户公开结果"旁增加"更新客户进度"按钮，打开独立弹窗，弹窗里标明"提交后客户可见"。
- 跟进弹窗删除"客户可见结果"字段；"报价发送渠道"改为下拉框，复用 `contactMethodLabels`。
- 头部操作区增加快捷按钮：「开始跟进」「标记成交」「标记未成交」「关闭项目」。它们打开同一个跟进弹窗，只是预选好目标状态；按钮按 `statusTransitions` 决定是否显示。
- `eventSummary` 新增 `public-result` 事件的显示。

**验收**

- 普通跟进不再出现"客户可见"字段。
- 更新客户进度后，客户端「我的项目」能看到新内容，时间线有对应记录。

### C. 终态可改派（P1）

- 服务端：`assignProject` 删除 `editable(project)`；承接人资格校验保留。
- 管理端：详情页"改派"按钮去掉终态禁用；提示条文案改为"可直接改派，无需重开"。
- 验收：终态项目改派后状态不变，时间线有改派记录，新承接人收到通知（D-6）。

### E. 列表页改进（P1）

**服务端**

- 把 `dashboard/workspace.ts` 中"最新一条跟进的 `nextFollowUpAt`"的 SQL 抽成共享片段（放在 `projects/repository.ts`），供列表和工作台共用。
- 列表返回 `nextFollowUpAt`。
- 列表查询新增：
  - `mine=true`：按当前登录管理员过滤，避免前端自己匹配用户 ID；
  - `followUp=overdue|today`：过滤逾期或今天到期的跟进，口径与工作台一致。
- 检查 `087_query_indexes.sql` 是否已覆盖 `project_events(project_id, kind, created_at)`，未覆盖就随 089 一起补上。

**管理端**

- 筛选区新增"只看我负责的"开关（默认开启，状态记在 localStorage）和"跟进提醒"筛选。
- 新增"下次跟进"列，逾期显示红色、今天到期显示橙色。
- 状态标签的 `v-if` 链改为颜色映射表。`['closed','lost','won']` 在 list、detail、QuotationEditor 中各写了一遍，统一改为从 `presentation.ts` 导入 `terminalStatuses`。

### F. 报价编辑器体验（P2，只改管理端）

- 新增 `views/projects/quotation-math.ts`，用 BigInt 实现与服务端 `lineAmount` 相同的 HALF_UP 算法，编辑时实时显示每行金额和合计。测试用例与服务端保持一致；保存后仍以服务端结果为准，列名改为"行金额"。
- 新增 `validationIssueLabels`，把 `EMPTY_ITEMS`、`PRICE_MISSING:<id>` 等翻译成中文；缺价的问题定位到具体行并高亮。
- 历史修订改为下拉框（复用 A 的 revisions 接口）。"放弃草稿"和"回到当前"拆成两个按钮。
- 数量和单价仍保留字符串，以免浮点误差，前端按服务端同一正则校验并即时提示；有效期时区改为可搜索的下拉框（`Intl.supportedValuesOf('timeZone')`，常用时区置顶）。
- 保存时遇到 `PROJECT_REVISION_CHANGED` 或 `QUOTATION_REVISION_CHANGED`，提示中带"载入最新"按钮，草稿保留。

### G. 关联方案（P2）

- 服务端：`linkProjectScheme` 按 G-1 放宽限制。重新关联时，先删除该项目原有的 `project_asset_versions`，再写入新快照；事件 payload 记录 `fromSchemeCode`。新增 reason `SCHEME_RELINK_BLOCKED`。
- 管理端：方案编号改为可搜索的下拉框（复用 `getSchemeListApi`，只列出已发布方案；需确认该接口有对应筛选参数），选中后显示方案名称和缩略图；已关联且满足条件时显示"重新关联"。
- `api/reason-messages.ts`：新增 `SCHEME_RELINK_BLOCKED`。

### H. 详情页布局（P2，只改管理端）

- `detail.vue` 改为：顶部摘要卡（编号、状态、承接人、客户、展会、预算、下次跟进、操作按钮），下方分为「概览 / 报价 / 时间线 / 客服会话」四个标签页，默认打开时间线。
- 资料快照和图片放进"概览"标签页；图片地址在首次进入该标签页时再请求。
