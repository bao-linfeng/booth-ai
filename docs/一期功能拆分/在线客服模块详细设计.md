## 2. 角色与概念

| 角色 | 身份 | 能力 |
|---|---|---|
| 访客 | 未登录，持有访客令牌 | 发起咨询、带方案上下文，以及带本访客提交的项目上下文；离线时留言，必须留邮箱 |
| 参展商 | 已登录 `users` | 同上；项目上下文限本人项目（含按邮箱认领的项目） |
| 坐席 | `admins` 中所属角色被授予 `customer-service.reply` 的账号（如“客服”角色） | 抢接、回复、内部备注、释放、结束会话 |
| 客服主管 | 所属角色额外被授予 `customer-service.supervise`（如“客服主管”角色） | 查看他人进行中会话、改派 |

坐席不是独立的数据实体：系统不维护坐席名单，**是否为坐席完全由账号当前所属角色的权限实时决定**（§7.1）。

- **客户主体**：`customer_user_id` 或 `visitor_id`，两者只能有一个。
- **会话（conversation）**：一轮咨询。同一客户主体最多只有一个未结束的会话（`queued` 或 `active`），会话结束后再发消息会开始新一轮。客户端按客户主体展示全部轮次的时间线。
- **上下文（context）**：会话可以挂多张上下文卡片（方案或项目），由服务端生成白名单快照。同一会话内相同上下文只追加一次。
- **消息（message）**：客户消息、坐席消息、系统消息、内部备注。每条消息记录原文和语言，译文单独存储。

**会话不创建、不修改任何项目。** 项目只由报价申请和人工需求接口创建，这两个接口按 `requestKey` 保证幂等。

## 3. 状态机

```
            客户发首条消息/打开会话
                     │
                     ▼
   ┌────────────► queued ──── 坐席抢接 ────► active
   │                 ▲                          │
   │                 └──── 坐席释放 / 主管改派到队列 ─┤
   │                                            │
   │                                    坐席结束 │ 超时自动结束（P1）
   │                                            ▼
   └──── 客户在新一轮发消息（新会话） ◄──────── closed
```

- 抢接用条件更新 `UPDATE … SET status='active', agent_admin_id=$me WHERE id=$1 AND status='queued' AND deleted_at IS NULL`；影响 0 行时返回 409，`reason: CONVERSATION_ALREADY_CLAIMED`。
- 改派：主管把会话指定给另一名当前有效的坐席（§7.1.3），或者放回队列；必须填写原因，并写入内部系统消息。
- `queued` 状态下没有坐席在线时，客户端进入**留言模式**（§6.3），会话状态不变。

## 4. 身份与授权

### 4.1 访客身份

- `POST /api/v1/client/customer-service/visitors`（公开接口，按 IP 限流）签发访客令牌：32 字节随机串，库中只存 SHA-256；返回 `visitorToken`。客户端存入 localStorage，之后的匿名请求用 `X-Visitor-Token` 头携带。
- 请求同时带了 `Authorization` 和 `X-Visitor-Token` 时，以登录身份为准，访客头只在合并接口中使用。
- 访客 6 个月不活跃时逻辑删除，令牌随之失效。

### 4.2 匿名项目上下文（D2）

- 匿名提交前，客户端先确保拿到访客令牌。`POST /quote-requests`、`POST /manual-requests` 收到合法 `X-Visitor-Token` 时写入 `projects.visitor_id`。头缺失或无效时照常受理，只是该项目以后不能被匿名访客用作上下文。
- 匿名访客附加项目上下文的条件：`projects.customer_user_id IS NULL AND projects.visitor_id = 当前访客`。
- 登录用户附加项目上下文的条件：`projects.customer_user_id = 当前用户`。按邮箱认领后的项目自然满足。
- 不满足条件的一律返回 404，不区分“不存在”和“无权限”。项目号不是凭据，只接受 `projectId`。

### 4.3 访客合并

`POST /customer-service/visitors/merge` 需要同时提供登录 Bearer 和 `X-Visitor-Token`：

1. 访客的全部会话改归该用户。若双方都有未结束的会话，保留最后消息较新的一方，另一方结束并写系统消息“已合并”。
2. 访客标记 `merged_user_id`，令牌失效。客户端删除本地令牌。
3. **不转移项目归属**。项目仍按已验证邮箱认领（迁移 067），避免共用电脑时把他人的匿名项目交给登录者。已挂在会话里的项目卡片只含白名单字段，可以继续展示。

### 4.4 其他

- 单个会话的实时流和读写都要校验会话属于当前主体（坐席端按权限校验）。错误信息不能泄露其他会话或项目是否存在。
- SSE 使用一次性 ticket（Redis，有效期 300 秒），复用现有 `authentication: 'events'` 机制，新增前缀 `cs`。访客 ticket 绑定访客 ID。

## 5. 上下文白名单

| 类型 | 字段 |
|---|---|
| scheme | `schemeCode`、方案名称（客户语言）、规格摘要（尺寸、开口面数） |
| project | `projectNo`、`schemeCode?`、`sourceType`、项目状态、客户类型（个人/企业）、国家、城市、展会名称、提交时间 |

- 客户语言、当前页面入口（`entryPoint`：scheme_detail / quote_receipt / my_project / floating）记录在上下文行上。
- 不包含成本、预算以外的报价信息、内部跟进、承接人私有信息或凭据。
- 坐席端另外通过 `projects.read` 权限跳转到完整项目详情，并显示项目负责人姓名供参考（D3：不自动分配给负责人）。

## 6. 客户端功能（apps/client）

### 6.1 入口

| 位置 | 携带上下文 |
|---|---|
| 方案详情页 | `{ kind: 'scheme', schemeCode }` |
| 报价/人工需求受理回执（CP-10） | `{ kind: 'project', projectId }` |
| 我的项目详情 | `{ kind: 'project', projectId }` |
| 全局悬浮按钮 | 无（仅咨询） |

点击后调用“打开会话”接口。这个接口是幂等的：复用未结束的会话；如果携带了新的上下文，就追加卡片。随后展开聊天面板。重复点击不会产生重复会话或卡片，也绝不会创建项目。

### 6.2 聊天面板

- 消息时间线：显示本主体全部轮次，各轮之间有分隔，上下文卡片穿插在时间线中。按游标向上加载历史。
- 发送：文本 1～2000 字符；每条消息带 `clientMessageId`（UUID），用于幂等重试。状态分发送中、已发送、失败（可点击重试）。
- 坐席消息按客户当前 locale 显示译文，可切换“查看原文”。译文未完成时先显示原文并标注“翻译中”；翻译失败时显示原文并标注“翻译失败”。
- 状态提示：排队中、客服已接入、客服已结束本次会话、连接中断正在重连（期间降级为每 5 秒轮询）。
- 未读角标：未读数显示在悬浮按钮和顶部导航上。
- 阿拉伯语（ar）界面使用 RTL 布局。
- 消息只按纯文本渲染，不解析 HTML 和 Markdown。

### 6.3 离线留言

- 打开会话和每次重连时取 `agentsOnline`。为 false 且会话在 `queued` 状态时，界面切换为留言模式，文案明确写“客服暂不在线，留言后将通过邮件回复”，不能显示成实时对话。
- 访客必须填写邮箱，登录用户默认使用账户邮箱，可以修改。邮箱保存在会话 `contact_email`。
- 留言消息的 `kind = offline`，会话标记 `has_offline_message`，并触发客服通知邮件（§8.3）。

### 7.1 客服角色与权限（D8）

#### 7.1.1 配置流程

沿用现有后台角色体系：角色及“账号↔角色”关联在灵通用户系统维护，本平台的 `admin_roles` 只同步角色，并在“用户角色”页为角色配置权限码。权限在每次请求时按账号当前角色实时解析。

1. 在灵通用户系统新建角色，如“客服”“客服主管”，并把客服人员账号关联到对应角色。
2. 在后台“用户角色”页刷新角色列表，为“客服”勾选客服工作台的查看和回复权限，为“客服主管”额外勾选改派权限（需要时也可勾选客服设置权限）。
3. 客服人员登录后台后，自动以坐席身份进入客服工作台，无需其他登记。

建议的角色模板（仅为指引，以“用户角色”页实际配置为准）：

| 角色 | 权限 |
|---|---|
| 客服 | `customer-service.read`、`customer-service.reply`；需要跳转项目详情时再加 `projects.read` |
| 客服主管 | 客服的全部权限，加 `customer-service.supervise`；可选 `customer-service.settings` |

一个账号可同时属于多个角色，权限取并集。例如项目跟进人员同时关联“客服”角色，就可以兼做坐席。

#### 7.1.2 权限码

在 `permissions.ts` 的权限目录中新增分组 `customer-service`（标签“在线客服”，路由 `CustomerServiceWorkbench`、`CustomerServiceSettings`）：

| 权限码 | 能力 | 依赖 |
|---|---|---|
| `customer-service.read` | 进入工作台；查看队列、本人会话、已结束会话、客服设置 | — |
| `customer-service.reply` | 抢接、释放、发送消息、写内部备注、结束会话、更新已读、设置在线/离开 | `customer-service.read` |
| `customer-service.supervise` | 查看他人进行中的会话、改派 | `customer-service.read`、`customer-service.reply` |
| `customer-service.settings` | 修改客服设置 | `customer-service.read` |

- 迁移脚本只把这四项授予 `ROLE_ADMIN`，“客服”“客服主管”等角色由管理员在“用户角色”页配置。
- 登录落地页：`accessSummary().homePath` 的顺序调整为 分析页 → 工作台 → **客服工作台**（有 `customer-service.read`）→ 个人中心。只有客服权限的账号登录后直接进入客服工作台，菜单只显示客服相关页面。

#### 7.1.3 坐席有效性

“有效坐席”的判定：账号 `enabled`，且当前所属的有效角色中包含 `customer-service.reply`。判定方式与项目承接人 `eligibleAssignee()` 相同，实时查询 `admin_roles`，不缓存。

| 场景 | 处理 |
|---|---|
| 抢接、发消息、改派目标 | 每次都校验有效性；改派目标无效时返回 409，`reason: AGENT_UNAVAILABLE` |
| `agentsOnline` 计数 | 工作台 SSE 每 15 秒心跳时重新校验；无效则从 `cs:presence` 移除并断开连接 |
| 账号被移出客服角色、被停用，或角色被撤销 reply 权限 | 账号角色变化会使登录会话失效（`session_version` 递增）；仅修改角色权限时由下一次心跳发现。发现后把该账号的 `active` 会话全部退回队列，并写系统消息“坐席已不可用，会话重新排队” |
| 改派候选列表 | `GET /agents` 只返回有效坐席，附带在线状态和当前接待数 |

坐席显示给客户的名称用 `admins.nickname`（为空时显示“客服”），不显示用户名、邮箱等账号信息。

## 8. 服务端设计（apps/server）

### 8.1 实时通道

- 收发方式：HTTP POST 发送，SSE 推送。复用 `http/client/sse.ts` 的 Redis pub/sub、心跳和重连机制，并抽成客户端和管理端共用的工具，**不引入 WebSocket 依赖**。
- 频道：
  - `cs:conv:{conversationId}`：消息创建、译文完成、会话状态变化、已读。
  - `cs:agents`：队列变化、会话分配变化（只发 ID 和类型，详情由前端再拉取）。
- 补偿：SSE 连接时带 `after=<seq>`，服务端先补发 seq 之后的消息，再推实时事件。消息 `seq` 用 bigserial 全局递增，按会话过滤。
- 坐席在线：工作台 SSE 存活期间，每 15 秒执行一次 `ZADD cs:presence <expireAt> <adminId>`（`expireAt` = 当前时间 + 45 秒）。状态为“离开”时移除。`agentsOnline` 的判定是先清理过期成员，再看计数是否大于 0。
- 客户在线：客户端 SSE 存活期间刷新 `cs:customer-presence:{conversationId}`（TTL 45 秒），用于决定是否发回复邮件。

### 8.2 翻译管道

1. 消息在事务内写入。翻译开启且源语言与目标语言不同时，同一事务里插入 `cs_message_translations(status='pending')` 行。事务提交后推送消息事件，并投递 BullMQ 任务 `cs-translate`。
2. Worker 按 `cs_translation` 用途的主备模型依次调用。提示词固定为“只翻译、不增删、保留编号和数字”；`schemeCode` 和 `projectNo` 等编号不翻译。
3. 成功后写入译文，状态改为 `done`，并推送 `message.translated`。重试 3 次仍失败则状态改为 `failed`，也推送事件。
4. 恢复：Worker 启动时以及每 5 分钟扫描一次超过 2 分钟仍为 `pending` 的行，重新投递任务。
5. 方向：客户消息翻译为坐席语言；坐席消息翻译为该会话的 `customer_locale`（以发送时为准）。系统消息使用 i18n 文案，不调用模型；内部备注不翻译。
6. 没有分配模型或翻译关闭时，不生成 `pending` 行，前端只显示原文。翻译不消耗客户积分。

### 8.3 通知

- **离线留言通知坐席**：留言写入后加入 `cs_email_outbox`，Worker 给客服设置中的通知邮箱发邮件。邮件包含会话号、上下文摘要和留言原文（附译文），按会话 10 分钟内合并为一封。
- **回复送达客户**：坐席发消息时，如果客户不在线、会话有可用邮箱、且设置已开启，就把邮件加入 outbox，延迟 5 分钟发送。期间客户上线或已读则取消。邮件使用客户语言，内容是回复的译文摘要和返回网站的链接（`?cs=open`）。链接不带任何凭据。
- 邮件发送失败按 outbox 重试，不影响消息本身。

### 8.4 保留与逻辑删除（D6）

每日 BullMQ 定时任务 `cs-retention` 执行：

- `cs_messages`：`created_at < now() - interval '6 months'` 的行写入 `deleted_at`。
- `cs_conversations`：已结束、且 `last_message_at` 早于 6 个月前的会话写入 `deleted_at`；上下文和译文随会话或消息一起过滤。
- `cs_visitors`：`last_seen_at` 早于 6 个月前、且没有未删除会话的访客写入 `deleted_at`。
- 所有查询都带 `deleted_at IS NULL`，后台也看不到已删除数据。数据库中仍保留原文，物理清除与备份策略另行确定。

### 8.5 限流

| 策略 | 限额 |
|---|---|
| 签发访客令牌 | 每 IP 每 10 分钟 10 次 |
| 访客发送消息 | 每访客每分钟 10 条，每 IP 每分钟 30 条 |
| 登录用户发送消息 | 每用户每分钟 20 条 |
| 留言 | 每访客每小时 5 条 |

## 9. 数据模型（迁移 `0xx_customer_service.sql`）

```sql
cs_visitors(
  id uuid PK, token_hash text UNIQUE NOT NULL, locale text NOT NULL,
  merged_user_id uuid REFERENCES users(id), created_at, last_seen_at, deleted_at)

ALTER TABLE projects ADD visitor_id uuid REFERENCES cs_visitors(id);

cs_conversations(
  id uuid PK, conversation_no text UNIQUE  -- 'CS-' || 序列
  customer_user_id uuid REFERENCES users(id), visitor_id uuid REFERENCES cs_visitors(id),
  CHECK (num_nonnulls(customer_user_id, visitor_id) = 1),
  status text CHECK (status IN ('queued','active','closed')),
  agent_admin_id uuid REFERENCES admins(id),
  customer_locale text NOT NULL, contact_email text,
  has_offline_message boolean NOT NULL DEFAULT false,
  last_message_seq bigint, last_message_at timestamptz,
  customer_read_seq bigint NOT NULL DEFAULT 0, agent_read_seq bigint NOT NULL DEFAULT 0,
  queued_at, claimed_at, closed_at, created_at, deleted_at)
-- 每个主体至多一个未结束会话
UNIQUE INDEX ON cs_conversations(customer_user_id) WHERE status <> 'closed' AND deleted_at IS NULL
UNIQUE INDEX ON cs_conversations(visitor_id)       WHERE status <> 'closed' AND deleted_at IS NULL
INDEX ON cs_conversations(status, queued_at) WHERE deleted_at IS NULL

cs_conversation_contexts(
  id uuid PK, conversation_id uuid REFERENCES cs_conversations(id),
  kind text CHECK (kind IN ('scheme','project')), ref text NOT NULL,  -- schemeCode 或 projectId
  project_id uuid REFERENCES projects(id), entry_point text NOT NULL,
  snapshot jsonb NOT NULL, created_at,
  UNIQUE (conversation_id, kind, ref))
INDEX ON cs_conversation_contexts(project_id)

cs_messages(
  id uuid PK, seq bigserial UNIQUE, conversation_id uuid REFERENCES cs_conversations(id),
  sender_type text CHECK (sender_type IN ('customer','agent','system')),
  sender_admin_id uuid REFERENCES admins(id),
  kind text CHECK (kind IN ('text','offline','note','context','event')),
  visibility text CHECK (visibility IN ('public','internal')),
  body text NOT NULL, locale text NOT NULL, client_message_id uuid,
  created_at, deleted_at,
  UNIQUE (conversation_id, sender_type, client_message_id))

cs_message_translations(
  message_id uuid REFERENCES cs_messages(id), target_locale text,
  status text CHECK (status IN ('pending','done','failed')), body text,
  model_id uuid, attempts int NOT NULL DEFAULT 0, updated_at,
  PRIMARY KEY (message_id, target_locale))

cs_settings(  -- 单行，带 revision 做乐观锁
  id boolean PK DEFAULT true CHECK (id), translation_enabled boolean, agent_locale text,
  offline_notify_emails text[], reply_email_enabled boolean, revision int, updated_by, updated_at)

cs_email_outbox(
  id uuid PK, conversation_id uuid, kind text CHECK (kind IN ('offline_notice','reply_notice')),
  recipient text, locale text, due_at timestamptz, sent_at, cancelled_at, attempts int, last_error text)
```

另外：`ai_model_assignments.purpose` 约束和 `AiPurpose` 类型增加 `cs_translation`（文本用途，`unitCredits` 为 null）；权限目录增加 §7.1.2 的 `customer-service` 分组，迁移只为 `ROLE_ADMIN` 追加这四项权限。坐席不建表，由 `admins.roles` 与 `admin_roles.permission_codes` 实时判定。

## 10. 接口契约

响应包装与错误格式沿用全局约定：成功返回 `{ code: 0, data }`，错误返回 `{ error: { code, reason?, message, requestId } }`。

### 10.1 客户端 `/api/v1/client/customer-service`

| 方法 | 路径 | 身份 | 说明 |
|---|---|---|---|
| POST | `/visitors` | 公开 | 签发访客令牌 → `{ visitorToken, visitorId }` |
| POST | `/visitors/merge` | 登录 + 访客头 | 合并访客会话 → `{ mergedConversations }` |
| POST | `/conversations` | 用户/访客 | 打开或复用会话，可选 `context: { kind, schemeCode? , projectId? }, entryPoint`。返回 `{ conversation, contexts, agentsOnline }`。新建会话时返回 201，复用时返回 200 |
| GET | `/conversations/current` | 用户/访客 | 当前未结束会话、未读数、`agentsOnline`。没有会话时 `conversation: null` |
| GET | `/messages?before=<seq>&limit=` | 用户/访客 | 本主体全部轮次的时间线（不含 internal 消息），附客户 locale 的译文 |
| POST | `/conversations/{id}/messages` | 用户/访客 | `{ clientMessageId, body, kind: 'text' \| 'offline', contactEmail? }`；同一 `clientMessageId` 重放时返回同一条消息 |
| POST | `/conversations/{id}/read` | 用户/访客 | `{ seq }` |
| POST | `/conversations/{id}/events-ticket` | 用户/访客 | 获取 SSE ticket |
| GET | `/conversations/{id}/events?ticket=&after=` | ticket | SSE 推送 |

错误 `reason` 取值：

| reason | HTTP 状态 | 含义 |
|---|---|---|
| `VISITOR_REQUIRED` | 401 | 既未登录也没有访客令牌 |
| `CONTEXT_NOT_FOUND` | 404 | 上下文不存在或无权使用 |
| `CONVERSATION_CLOSED` | 409 | 会话已结束，客户端应重新打开会话 |
| `CONTACT_EMAIL_REQUIRED` | 400 | 访客留言未填邮箱 |
| `RATE_LIMITED` | 429 | 触发限流 |

### 10.2 管理端 `/api/v1/admin/customer-service`

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/conversations?tab=&page=&pageSize=&projectId=` | read | 列表（tab：queue / mine / offline / all / closed；all 需要 supervise 权限） |
| GET | `/conversations/{id}` | read | 详情，包含上下文和客户信息 |
| GET | `/conversations/{id}/messages?before=&limit=` | read | 消息，包含 internal 消息和坐席语言译文 |
| POST | `/conversations/{id}/claim` | reply | 抢接；冲突时返回 409 `CONVERSATION_ALREADY_CLAIMED` |
| POST | `/conversations/{id}/release` | reply | 退回队列（仅当前坐席） |
| GET | `/agents` | supervise | 有效坐席列表（§7.1.3）：`adminId`、显示名、在线状态、当前接待数 |
| POST | `/conversations/{id}/transfer` | supervise | `{ adminId? , reason }`，不传 adminId 表示退回队列；目标坐席无效时返回 409 `AGENT_UNAVAILABLE` |
| POST | `/conversations/{id}/close` | reply | 结束会话（当前坐席或主管） |
| POST | `/conversations/{id}/messages` | reply | `{ clientMessageId, body, kind: 'text' \| 'note' }`；只有当前坐席能发 text |
| POST | `/conversations/{id}/read` | reply | `{ seq }` |
| PUT | `/presence` | reply | `{ status: 'online' \| 'away' }` |
| POST | `/events-ticket` | read | 获取工作台 SSE ticket |
| GET | `/events?ticket=` | ticket | 工作台事件流：队列变化与本人会话事件 |
| GET / PUT | `/settings` | read / settings | 客服设置；PUT 带 `expectedRevision` |

报价申请和人工需求接口不改请求体，只新增读取可选的 `X-Visitor-Token` 头（§4.2）。

## 12. 验收

| 编号 | 场景 | 通过标准 |
|---|---|---|
| CS01 | 从方案详情发起咨询 | 坐席端看到方案卡片，能收发消息 |
| CS02 | 登录用户从回执或我的项目进入 | 坐席端看到正确的项目号和方案编号；换他人 `projectId` 返回 404 |
| CS03 | 匿名提交后从回执进入 | 同一浏览器的访客可以带项目上下文；换浏览器或清空令牌后被拒绝；登录合并后会话保留 |
| CS04 | 重复进入 | 多次点击各入口和刷新页面，不新增项目，不重复创建未结束会话和上下文卡片；`project_events` 数量不变 |
| CS05 | 抢接并发 | 两名坐席同时抢接，只有一名成功，另一名收到 409 |
| CS06 | 坐席离线 | 客户端显示留言模式，访客必须填写邮箱；后台“留言待回复”可见；通知邮箱收到邮件；坐席回复后客户收到邮件 |
| CS07 | 翻译 | en/ja/ar 等客户与中文坐席双向收到译文；模型故障时显示原文并标注，收发不中断；关闭翻译后只显示原文 |
| CS08 | 实时与重连 | 断网恢复后消息不丢、不重复；重试发送（相同 `clientMessageId`）不会产生重复消息 |
| CS09 | 隔离 | 访客/用户无法读写他人会话或订阅他人频道；internal 备注不出现在客户端；错误信息不泄露存在性 |
| CS10 | 保留期 | 把数据时间回拨超过 6 个月后执行任务：消息和会话不再出现在任何接口，数据库中 `deleted_at` 已写入 |
| CS11 | 权限 | 没有 supervise 权限时看不到他人进行中会话、不能改派；没有 settings 权限时不能修改设置 |
| CS13 | 客服角色 | 在灵通用户系统建“客服”角色并关联账号、在“用户角色”页授予 read + reply 后，该账号登录直接进入客服工作台并能抢接；把账号移出角色或撤销 reply 后，不再计入 `agentsOnline`、不能抢接，其进行中会话退回队列 |
| CS12 | 故障隔离 | Redis、翻译或邮件故障时，已提交的项目和已写入的消息不受影响，恢复后补推或补发 |
