## 0. 使用方法

1. 先完成 §1.3 的开工前置项。
2. 按 §4 的里程碑顺序开发。M1～M4 是服务端，M5 和 M6 是两个前端；M2 完成后接口契约冻结，前端即可并行开发。
3. 每个任务都写明了**落点文件**、**实现要点**和**完成标准**。数据库和接口契约分别以 §5 和 §6 为准，事件协议见 §7。
4. 每个里程碑结束时执行对应子项目的检查命令（§9.4），服务端改动后按 `apps/server/AGENTS.md` 重新部署 dev 栈并验证。
5. 提交按 §10 拆分，遵循 Conventional Commits。

## 2. 代码核对结论与落地调整

以下几处设计与当前代码不完全吻合，按右列方式落地。它们不改变业务语义。

| ID | 设计表述 | 代码现状 | 落地方式 |
|---|---|---|---|
| G1 | §8.2“事务提交后投递 BullMQ 任务 `cs-translate`” | API 进程不持有 BullMQ Queue；现有生成任务都是“同事务写 outbox，Worker 轮询分发”（`workers/generation-outbox.ts`） | `cs_message_translations` 的 `pending` 行本身就是 outbox。Worker 的调度任务 `cs-translation-outbox` 每秒认领 pending 行并投递到新队列 `booth-cs`（任务名 `cs.translate`，`jobId = cs-translate-{messageId}-{locale}`，BullMQ 不允许自定义 ID 含 `:`；任务完成或失败后即移除，超时重投不会被去重吞掉）。超过 2 分钟仍为 pending 的行会被重新投递，同时满足 §8.2 第 4 条 |
| G2 | §8.4“每日 BullMQ 定时任务 `cs-retention`” | Worker 定时工作统一使用 `workers/scheduler.ts` 的 `ScheduledTask` | 注册为 `ScheduledTask`，`intervalMs = 1 小时`。判定条件基于时间，执行是幂等的，频率高于每日不影响结果，也不依赖进程重启时间 |

## 3. 总体技术方案

### 3.1 组件与数据流

```
client 面板 ──POST 消息──► API（事务：写消息 + 翻译 pending 行 + 更新会话 [+ 邮件 outbox]）
     ▲                       │ 提交后 PUBLISH
     │ SSE (cs:conv:{id})    ├──► cs:conv:{id}   仅客户可见事件（含消息体）
     │                       └──► cs:agents      ID 级事件（按连接过滤）──SSE──► admin 工作台 ──REST 拉详情
     │
Worker：cs-translation-outbox → booth-cs 队列 → 调用翻译模型 → 写译文 → PUBLISH message.translated
        cs-emails（离线通知 / 回复通知）· cs-retention（逻辑删除）· cs-agent-sweep（坐席失效退回队列）
Redis：事件票据 · cs:presence(ZSET) · cs:agent-away:{adminId} · cs:customer-presence:{convId} · 限流计数
```

可靠性原则（对应 CS08、CS12）：

- **消息先落库，后推送。** PUBLISH 失败只记录 warn 日志，不回滚、不报错；SSE 重连时用 `after=<seq>` 补发，断线期间客户端每 5 秒轮询。
- 翻译和邮件都通过 outbox 表重试，失败不影响已写入的消息。
- 调用 AI 和 SMTP 时不持有数据库锁（遵守 server AGENTS 的队列约束）。

### 6.4 关键流程（事务内容）

**打开会话 `openConversation(subject, context?, entryPoint, locale)`**

1. 如果带了 context，**先在事务外**用 `resolveContext()` 鉴权并生成快照（只读查询）。失败时返回 404 `CONTEXT_NOT_FOUND`。
   - scheme：`schemes` 中 `code=$1` 且已发布（与客户端方案详情的可见条件一致，复用 `modules/schemes` 中的查询）。
   - project（user）：`customer_user_id = $user`。
   - project（visitor）：`customer_user_id IS NULL AND visitor_id = $visitor`。
2. 事务：`pg_advisory_xact_lock(hashtextextended('cs-open:'||subjectKey,0))` → 查找未结束会话 → 没有就插入（`customer_locale = locale`）。
3. `INSERT INTO cs_conversation_contexts … ON CONFLICT (conversation_id, kind, ref) DO NOTHING RETURNING id`。只有真正插入时，才追加一条 `kind='context'`、`visibility='public'` 的系统消息，并更新 `last_message_seq/last_public_seq/last_message_at`。
4. 提交后 publish：有新上下文时发 `message.created`；新建会话时向 `cs:agents` 发 `queue.changed`。
5. 返回 `agentsOnline`（§6.5）。**整个过程不读写 `projects` 和 `project_events`**（对应 CS04）。

**客户发消息 `postCustomerMessage`**

1. 锁定会话：`SELECT … FOR UPDATE WHERE id=$1 AND 属于 subject AND deleted_at IS NULL`，不存在时返回 404。
2. 先按 `(conversation_id,'customer',client_message_id)` 查找已有消息：存在且 body 相同时返回 200 重放；body 不同时返回 409 `IDEMPOTENCY_CONFLICT`。
3. 会话为 closed 时返回 409 `CONVERSATION_CLOSED`（重放检查在这一步之前，保证断线重试成功）。
4. offline：访客必须提供 `contactEmail`，否则返回 400 `CONTACT_EMAIL_REQUIRED`。登录用户未提供时使用账户邮箱（`users.email`）。只有会话为 queued 时才允许 offline，否则按 text 处理。
5. 插入消息；会话更新 `customer_locale = 请求 locale`、`contact_email`（若提供）、`has_offline_message ||= offline`、`awaiting_since = COALESCE(awaiting_since, now())`（仅 queued）以及 seq/时间字段。
6. 翻译：读取 `cs_settings`，如果 `translation_enabled`、已分配 `cs_translation` 模型、并且 `locale <> agent_locale`，则插入 pending 译文行。
7. offline：为每个 `offline_notify_emails` 地址执行 `enqueueOfflineNotice()`（§6.6）。
8. 提交后 publish：`cs:conv` 发 `message.created`（含 DTO），`cs:agents` 发 `message.created`（ID 级）。

**坐席发消息 `postAgentMessage`**：步骤与上面类似。额外要求：

- 先执行 `eligibleAgent(client, adminId)`，无效时返回 409 `AGENT_UNAVAILABLE`。
- text 必须满足 `status='active' AND agent_admin_id=$me`。
- 译文目标为当前 `customer_locale`；note 不翻译，也不发布到 `cs:conv`。
- text 发送后执行 `scheduleReplyNotice()`（§6.6）。

**抢接 `claim`**

```sql
UPDATE cs_conversations SET status='active', agent_admin_id=$2, claimed_at=now(), awaiting_since=NULL
WHERE id=$1 AND status='queued' AND deleted_at IS NULL RETURNING …
```

在同一事务中先执行 `eligibleAgent`（无效时返回 409 `AGENT_UNAVAILABLE`）。影响 0 行时返回 409 `CONVERSATION_ALREADY_CLAIMED`。成功后写 public event `claimed`（`eventParams: { agentName }`），并 publish `conversation.updated`。

**释放 / 改派 / 结束 / 坐席失效**：都是条件更新加一条 event 消息。

- 释放和退回队列：`status='queued', agent_admin_id=NULL, awaiting_since=now(), queued_at=now()`。
- 改派给指定坐席：更新 `agent_admin_id`，状态保持 active。
- 结束：`status='closed', closed_at=now(), close_reason='agent'`，取消该会话的 pending reply_notice 之外的邮件（离线通知照常发出）。
- `requeueAgentConversations(adminId)`：将该坐席全部 active 会话退回队列，并写 public event `agent_unavailable`。

**访客合并 `mergeVisitor(userId, visitorId)`**（§4.3）

1. 依次对 user 和 visitor 加 advisory lock（按 key 排序，避免死锁）。
2. 如果双方都有未结束会话，按 `last_message_at` 保留较新的一方。另一方 `status='closed', close_reason='merged'`，写 event `merged`。如果被结束的一方是 active，同时释放其坐席。
3. `UPDATE cs_conversations SET customer_user_id=$user, visitor_id=NULL, origin_visitor_id=$visitor WHERE visitor_id=$visitor`（在第 2 步之后执行，避免违反唯一索引）。
4. 访客写入 `merged_user_id/merged_at`；之后用该令牌请求时返回 401。
5. **不修改 `projects`**（对应 CS03）。

### 6.5 坐席在线与有效性

```ts
// modules/customer-service/agents.ts —— 判定方式同 projects/assignment.ts 的 eligibleAssignee
export async function eligibleAgent(db, adminId): Promise<boolean>  // enabled 且有效角色权限包含 customer-service.reply
export async function listAgents(db, redis): Promise<AgentDto[]>     // 候选账号 SQL + 每人 eligibleAgent + ZSCORE 判断在线 + active 数

// modules/customer-service/presence.ts
const PRESENCE = 'cs:presence';                                     // ZSET member=adminId score=expireAtMs
export async function touchAgent(redis, adminId)                     // 若不存在 cs:agent-away:{id}：ZADD PRESENCE now+45s
export async function setAway(redis, adminId, away: boolean)         // away：SET cs:agent-away:{id} 1 EX 43200 + ZREM；online：DEL + touchAgent
export async function agentsOnline(redis): Promise<boolean>          // ZREMRANGEBYSCORE PRESENCE -inf now；ZCARD > 0
export async function touchCustomer(redis, conversationId)           // SET cs:customer-presence:{id} 1 EX 45
export async function customerOnline(redis, conversationId)
```

- 工作台 SSE 连接建立时，以及每次心跳（15 秒）时：`eligibleAgent()` 为 false → `ZREM`、`requeueAgentConversations()`、断开连接；为 true → `touchAgent()`。只有 read 权限、没有 reply 权限的账号不计入在线。
- Redis 不可用时 `agentsOnline()` 返回 false（客户端进入留言模式，比误显示“在线”更安全），并记录 warn 日志。
- `cs-agent-sweep`（Worker，60 秒）：扫描 `status='active'` 会话涉及的 `agent_admin_id`，对其中无效的坐席执行 `requeueAgentConversations()`，覆盖坐席没有打开工作台的情况。

### 6.6 邮件 outbox 规则

| 类型 | 入队时机 | 合并 / 取消 | 内容 |
|---|---|---|---|
| `offline_notice` | 客户留言写入时，每个通知邮箱一行 | 已有待发行时不再新增（唯一索引 + `ON CONFLICT DO NOTHING`）。新建时 `due_at = GREATEST(now(), 该会话该收件人最近一封 sent_at + 10 分钟)`，`after_seq` = 上一封的覆盖上限，没有上一封时为 0 | 中文邮件：会话号、客户、上下文摘要、`after_seq` 之后的全部 offline 消息原文和中文译文（发送时已完成的译文）。附后台工作台链接，链接不带凭据 |
| `reply_notice` | 坐席发 text 时，满足四个条件：`reply_email_enabled`、会话有 `contact_email`（登录用户没有时使用账户邮箱）、`customerOnline()` 为 false、没有待发行 | `due_at = now() + 5 分钟`，已有待发行时不变（合并）。客户 SSE 连接建立或调用 read 接口（seq ≥ 待发邮件覆盖的消息）时设置 `cancelled_at`。投递前再检查一次 `customerOnline()`，在线则取消 | 客户语言（`locale = customer_locale`）：坐席回复的译文摘要（没有译文时用原文，最多 3 条，每条截断到 200 字），以及链接 `${CLIENT_PUBLIC_URL}/?cs=open` |

投递逻辑沿用 `receipt-emails.ts`：单条 SQL 用 `FOR UPDATE SKIP LOCKED` 取得 120 秒租约；失败退避 `min(60·2^(n-1), 3600)` 秒；6 次后或永久失败时写入 `failed_at`。日志不输出收件人。未配置 SMTP 时不注册该任务，记录停留在 outbox。

## 7. 实时事件协议

所有事件都写成 `event: update\ndata: <json>\n\n`（与现有流一致），JSON 的 `type` 字段区分事件类型。

### 7.1 客户端流 `GET /conversations/:id/events?ticket=&after=`

- 鉴权：票据 `subject` 必须等于 `:id`，并且会话属于票据中的主体（不满足时返回 404，不泄露是否存在）。
- 建立连接：先 SUBSCRIBE `cs:conv:{id}`，再补发 `seq > after` 的 public 消息（每条一个 `message.created`），最后发 `{ type: 'ready', conversation }`。先订阅再补发，可以避免中间的事件丢失；客户端按 `id` 去重。
- 心跳回调：`touchCustomer()`；`touchVisitor()`（每 5 分钟最多更新一次 `last_seen_at`）。
- 连接建立时取消该会话 pending 的 reply_notice。

| type | 载荷 |
|---|---|
| `message.created` | `{ message: MessageDto }` |
| `message.translated` | `{ messageId, seq, translation }`（只针对坐席消息） |
| `conversation.updated` | `{ conversation: ConversationDto }` |
| `read` | `{ agentReadSeq }` |
| `ready` | `{ conversation }` |

### 7.2 工作台流 `GET /events?ticket=`

- 只订阅 `cs:agents`，事件只含 ID：`{ type, conversationId, status, agentAdminId, seq? }`。type 取值：`queue.changed`、`conversation.updated`、`message.created`、`message.translated`、`read`。
- **按连接过滤**：没有 supervise 权限时，丢弃 `agentAdminId` 既不是 null 也不是本人的事件。
- 连接建立时先推送 `{ type: 'ready', counts }`。前端收到事件后防抖 300ms，再通过 REST 拉取列表或增量消息（`after=`）。

### 7.3 `src/http/sse.ts` 公共工具签名

```ts
export interface EventStreamOptions {
  channels: string[];
  /** SUBSCRIBE 完成后执行，返回需要补发的事件（按顺序写出） */
  replay?: () => Promise<unknown[]>;
  /** 每条 pub/sub 消息的过滤或改写；返回 null 表示丢弃 */
  filter?: (channel: string, payload: string) => string | null;
  /** 每 15 秒心跳（写出 `event: ping`）时调用；返回 false 时关闭连接 */
  onHeartbeat?: () => Promise<boolean | void>;
  onOpen?: () => Promise<void>;
}
export async function streamEvents(redis: Redis, reply: FastifyReply, options: EventStreamOptions): Promise<void>
```

theme/artwork 改为 `streamEvents(redis, reply, { channels: [`theme-job:${id}`], replay: async () => [await fetchState()] })`，行为保持不变。

同一 API 进程内所有 SSE 共用一条 Redis 订阅连接（按 `redis` 实例懒创建），频道按引用计数：首个连接 `SUBSCRIBE`，最后一个连接离开时 `UNSUBSCRIBE`。订阅连接不自动重连，出错或断开时关闭其上全部 SSE，由前端重连补发，下一条 SSE 重建订阅连接；API 退出时 `closeEventStreams(redis)` 释放它。

心跳写成具名事件 `event: ping`（`data: {}`），不用 SSE 注释：注释不会触发浏览器端任何监听。客户端会话流与工作台流各有看门狗，连续 45 秒（3 次心跳）收不到任何事件就主动断开，按断线处理（降级轮询 + 退避重连）。这样可以覆盖代理吞掉上游断开的情况：例如 dev 栈 API 重启时，Vite 代理不会关闭已开始推送的下游响应，浏览器收不到 `error`，工作台会一直显示“实时连接正常”，但坐席已经不在 `cs:presence` 中。

## 11. 风险与待确认

| 编号 | 风险 / 事项 | 影响 | 处理 |
|---|---|---|---|
| R1 | 外部系统移除角色后，本地 `admins.roles` 要等下次 `/me` 或登录才会同步（G5） | CS13“移出角色”场景存在延迟 | P0 接受；如需立即生效，再评估 `cs-agent-sweep` 定期向灵通查询账号角色（需要外部接口支持服务端凭据，另行确认） |
| R2 | SSE 长连接占用 API 进程连接数 | 坐席和客户在线人数多时 HTTP 连接数增加 | Redis 侧已改为进程级共享订阅连接（§7.3），连接数不再随 SSE 数增长；共享连接断开会同时关闭该进程上全部 SSE，依赖前端退避重连与 `after` 补发 |
| R3 | 翻译模型偶发改写编号 | 译文中的编号错误 | 编号占位符保护 + 校验失败时换模型（M4-1） |

| R5 | 离线通知邮箱人工填写错误 | 留言无人知晓 | 设置页逐项校验格式；投递永久失败会记录在 `cs_email_outbox.failed_at`。P1 可在设置页展示投递状态 |
| CQ1～CQ4 | 设计 §13 | — | 按设计中的“当前处理”执行，本计划不改变 |
