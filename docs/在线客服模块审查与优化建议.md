# 在线客服模块审查与优化建议

> 审查日期：2026-10-09  
> 审查方式：静态代码审查，未执行测试、浏览器操作或运行环境复现。  
> 本文中的“代码可确认”指可以从现有代码路径确认缺口，不代表已经在运行环境复现。代码位置以审查时版本为准。

## 1. 总体结论

现有在线客服是一个较完整的自建客服系统，已包含：

- 客户端访客身份、登录后会话合并、方案与项目上下文卡片。
- 管理端公共队列、抢接、释放、改派、内部备注。
- HTTP 发送消息与 SSE 实时推送。
- 双向翻译、离线留言通知、回复邮件、数据保留期。

基础设计具备消息先落库、发送幂等、抢接并发控制、访客令牌 HttpOnly、内部备注隔离等能力。

当前最需要补齐的是异常场景下的一致性：**断线恢复、切换会话、切换账号，以及已有消息的译文更新同步**。建议先修复可靠性问题，再扩展图片附件、快捷回复、满意度等功能。

## 3. 问题清单

### CS-B01：工作台断线后，消息和会话列表缺少完整恢复机制

**优先级：P1｜证据状态：代码可确认**

管理端断线降级只定时刷新统计数；重新连接成功也只接收 `ready.counts`，没有同步当前消息、会话详情和列表。

触发场景：

1. 客服工作台断网。
2. 客户发消息，或其他客服进行了改派、结束等操作。
3. 网络恢复后界面显示实时连接正常。
4. 当前内容仍可能停留在断线前，直到后续事件或人工重新进入触发刷新。

代码依据：

- `apps/admin/apps/web-antd/src/store/customer-service.ts:73–76`：收到 `ready` 更新 counts 后直接返回。
- 同文件 `:143–146`：降级轮询只调用 `refreshCounts`。
- `apps/admin/apps/web-antd/src/views/customer-service/workbench/index.vue:119–129`：页面依赖实时事件刷新。
- `apps/server/src/http/admin/customer-service/index.ts:103`：服务端重连只补发 counts。

修复建议：重连成功触发一次完整校准；降级期间同步当前列表、详情和消息；消息补拉持续到 `hasMore=false`。

验收场景：断线期间分别发生新消息、改派、结束会话，重连后无需人工刷新即可看到正确状态与消息。

### CS-B02：切换会话时，旧请求可能把 A 客户消息写入 B 客户面板

**优先级：P1｜证据状态：代码可确认**

管理端部分请求有会话 ID 校验，但加载历史消息、翻译完成后重取消息、发送成功后合并消息这三个路径没有统一校验。

例如在 A 会话发送回复，服务器响应较慢，此时切换到 B；A 的发送响应回来后，会直接合并进 B 的消息列表。

代码依据：`apps/admin/apps/web-antd/src/views/customer-service/workbench/components/ConversationPanel.vue`：

- `:158–164`：翻译结果请求返回后直接合并。
- `:170–177`：历史消息返回后直接合并。
- `:183–195`：发送响应直接写当前列表。

影响：消息显示错乱，客服可能误判上下文并回复错误内容。此处确认的是前端显示污染，并非已确认服务端把消息存入错误会话。

修复建议：所有异步请求绑定会话 ID 和加载版本，返回时核验；发送队列、失败重试及草稿按会话分别保存。

验收场景：人为延迟 A 的发送、历史和翻译请求，切换到 B 后再返回响应，B 面板不得出现 A 的消息。

### CS-B03：退出或切换账号后，旧请求可能恢复上一个账号的聊天数据

**优先级：P1｜证据状态：代码可确认的竞态风险**

`resetCustomerService()` 会清空状态，但不会让正在执行的请求失效。

账号 A 的历史消息请求尚未返回时，用户退出或登录 B，旧响应仍可以写入全局消息和会话状态；部分打开流程还会继续尝试建立连接。

代码依据：`apps/client/src/features/customer-service/useCustomerService.ts`：

- `:93–98`：历史请求返回后直接写全局状态。
- `:109–118`：当前会话请求返回后直接写全局状态。
- `:139–148`：异步打开完成后继续连接。
- `:280–287`：重置没有请求版本失效处理。

修复建议：增加身份与会话生命周期版本；账号切换立即使旧请求、定时回调、连接创建结果失效。可结合 AbortController，但仍需结果版本校验。

验收场景：A 请求未返回时退出、切换 B，随后返回 A 的响应，消息、会话、未读数和连接状态不得恢复为 A 的数据。

### CS-B04：SSE 建立后没有完整复核登录状态与权限

**优先级：P1｜证据状态：代码可确认，撤权效果需运行验证**

连接建立时有认证，但长连接期间检查不完整：

- 登录客户的心跳直接返回 `true`，不复查登录会话。
- 管理端保存连接建立时的 `supervise` 权限。
- 只读客服连接的心跳直接返回 `true`。
- 可回复坐席只检查是否仍是有效坐席，没有完整复查该登录 Session 和主管权限。

代码依据：

- `apps/server/src/http/authentication.ts:54–79`：认证发生在请求建立时。
- `apps/server/src/http/client/customer-service/index.ts:112–116`。
- `apps/server/src/http/admin/customer-service/index.ts:97–109`。

影响：服务端撤销登录会话后，已有连接不一定及时停止接收消息；撤销主管权限但保留普通客服权限时，已有连接仍可能沿用主管事件过滤范围。管理端事件主要包含 ID 与状态，不能据此直接推断所有详情接口也发生越权。

修复建议：心跳检查 Session 有效性及权限版本，失效立即断流；主管权限变化后重新计算过滤范围。

验收场景：保持 SSE 在线，分别撤销 Session、只读权限和主管权限，验证旧流在约定时间内断开或收窄范围，重新连接使用最新权限。

### CS-B05：翻译完成事件丢失后，消息可能一直显示翻译中

**优先级：P1｜证据状态：代码可确认**

消息新增时先显示原文和 pending 翻译，随后依靠 `message.translated` 更新。但补偿查询按 `seq > 当前已知最大 seq` 拉取，翻译完成不会产生新的消息 seq。

翻译恰好在断线期间完成时，重连补拉无法获取这条已有消息的新译文。关闭再打开面板也不一定恢复，因为 `loaded=true` 时仍只拉新增消息。

代码依据：

- `apps/client/src/features/customer-service/useCustomerService.ts:68–69,87–97,145–146`。
- `apps/server/src/modules/customer-service/messages.ts:44–47`：SSE 补发也是按消息 seq。
- `apps/server/src/modules/customer-service/translation.ts:107–109`：更新原译文记录后发布事件。

修复建议：重连时重取近期消息，并专项刷新仍 pending 的译文。现阶段可先采用针对性的状态校准，不必引入复杂事件框架。

验收场景：消息已经显示但译文尚未完成时断线，待翻译完成后重连，译文状态必须恢复为 done 或 failed。

### CS-B06：新一轮会话创建失败时，用户输入会丢失

**优先级：P2｜证据状态：代码可确认**

普通发送失败已有 pending 消息可重试，但创建新会话失败不在保护范围内：

1. 输入框触发发送后立即清空。
2. `enqueue()` 先创建新一轮会话。
3. 创建成功后才加入 pending。
4. 如果创建失败，既没有输入内容，也没有失败消息可重试。

会话已经结束后再次发送，是明确的触发场景。

代码依据：

- `apps/client/src/features/customer-service/Composer.vue:14–18`。
- `apps/client/src/features/customer-service/OfflineForm.vue:18–24`。
- `apps/client/src/features/customer-service/useCustomerService.ts:238–247`。

修复建议：先保存待发送消息，再创建或获取会话；整个流程统一进入 sending／failed 状态。

验收场景：结束会话后发送新消息，让创建会话请求失败，原文必须保留在输入框或失败消息中，并可重试。

### CS-B07：访客会话合并失败后，没有可靠恢复途径

**优先级：P2｜证据状态：代码可确认**

前后端存在提前清除身份信息的问题：

- 前端发合并请求之前就删除访客标记，失败只记日志。
- 服务端在 `mergeVisitor()` 成功前就设置清除 Cookie。

网络失败时，前端后续可能不再触发合并；事务失败且错误响应带回清 Cookie 时，还可能失去访问原访客会话的凭据。错误响应是否保留该 Cookie 头，需要运行验证。

代码依据：

- `apps/client/src/features/customer-service/visitor.ts:26–30`。
- `apps/server/src/http/client/customer-service/index.ts:45–50`。

修复建议：成功合并，或确认访客已失效后，再清标记与 Cookie；临时失败保留可重试状态。

验收场景：模拟网络失败和合并事务失败，重新尝试后可完成合并，历史会话仍可访问，且不会重复归属。

### CS-B08：客服自己发送的消息也会触发新消息提醒

**优先级：P2｜证据状态：代码可确认**

工作台提醒只判断 `message.created`、当前坐席和 active 会话。但服务端给客户消息、客服回复、内部备注及部分系统消息都发布相同类型事件，没有发送者信息供前端区分。

代码依据：

- `apps/server/src/modules/customer-service/conversations.ts:34–37`。
- `apps/server/src/modules/customer-service/events.ts:19`。
- `apps/admin/apps/web-antd/src/store/customer-service.ts:78–84`。

影响：客服自己回复也可能触发提示音，内部操作也可能被当作新消息，削弱真正客户消息的提醒价值。声音实际播放还取决于浏览器音频权限。

修复建议：事件携带 `senderType`、`kind`，新消息提醒仅针对客户消息；排队提醒单独处理。

验收场景：客户消息触发提醒，客服自己的回复、内部备注及接入系统消息不触发客户新消息提醒。

## 4. 优化建议

### CS-O01：在线状态及时同步

客户端主要在打开面板、重连时读取 `agentsOnline`。连接正常且面板一直打开时，没有定期刷新或在线状态事件。

可能出现客服全部离开后仍显示排队模式，或客服上线后仍显示离线留言表单。

代码位置：`apps/client/src/features/customer-service/useCustomerService.ts:57–74,263–269`。

建议推送在线状态变化，或在面板打开时低频刷新。此项是对现有“打开与重连时读取”设计的增强。

### CS-O02：回复邮件以未读状态为主要依据

回复邮件是否入队依赖 SSE 在线标记，而不是最终是否已读：

- 客户刚关闭面板，在线标记还会存活最多约 45 秒。
- 此时客服回复，可能直接不创建邮件任务。
- 客户随后一直没有回来，也没有补偿任务重新检查该回复。

代码位置：

- `apps/server/src/modules/customer-service/presence.ts:51–60`。
- `apps/server/src/modules/customer-service/emails.ts:30–39`。

建议回复先创建延迟提醒，到期以已读游标为主要判断条件；在线状态作为辅助条件，并明确页面后台运行是否算已读。

### CS-O03：客服草稿与失败消息按会话保留

目前切换会话直接清空 `body` 和 `pending`，临时查看另一位客户会丢失原草稿或失败消息。

代码位置：`apps/admin/apps/web-antd/src/views/customer-service/workbench/components/ConversationPanel.vue:109–115`。

建议优先实现当前登录会话内的内存保存；是否需要刷新后保留，再按业务需要决定。

### CS-O04：完善分页补拉、列表请求隔离和已读语义

- 两端部分增量查询固定取 100 条，客户端 SSE 补发固定最多 500 条，没有完整消费 `hasMore`。应循环拉取直到追平，避免较长断线期间积累的消息恢复不全。
- 会话列表请求应增加版本校验，避免快速切换页签或翻页时，旧响应覆盖新页面数据。
- 历史消息量增长后可按实际性能引入虚拟列表。
- 未读上报应结合页面可见性，避免后台标签页收到消息就直接标记已读。

相关位置：

- `apps/client/src/features/customer-service/useCustomerService.ts:77–90`。
- `apps/server/src/modules/customer-service/messages.ts:44–47`。
- `apps/admin/apps/web-antd/src/views/customer-service/workbench/components/ConversationPanel.vue:132–148`。
- `apps/admin/apps/web-antd/src/views/customer-service/workbench/index.vue:55–68`。

## 5. 修复顺序

| 批次 | 修复范围 | 核心验收场景 |
| --- | --- | --- |
| 第一批 | 会话与账号异步隔离、SSE 撤权 | A 请求未返回时切 B；退出后旧响应不能回填；撤权后旧流停止或收窄范围 |
| 第二批 | 工作台断线恢复、译文补偿、分页追平 | 断线期间发消息、改派、翻译完成，恢复后无需人工刷新 |
| 第三批 | 新会话发送失败、访客合并恢复 | 创建会话失败不丢字；合并失败可重试且历史仍可访问 |
| 第四批 | 提醒去噪、在线状态、邮件、草稿 | 自己发消息不触发新客户消息提醒；离开未读可收到提醒；切会话保留草稿 |

## 6. 验证建议

现有测试已涉及发送幂等、抢接互斥、访客隔离、内部备注、静默断线检测等基础场景。本次仅检查了相关测试源码与测试项，未运行它们，不能据此声明测试通过。

接下来最有价值的是增加交错时序测试：

1. **请求延迟与会话切换**：旧会话的历史、译文、发送响应延后返回。
2. **请求延迟与账号切换**：退出或切换账号后旧请求才完成。
3. **断线期间发生业务变化**：消息新增、翻译完成、改派、结束会话。
4. **大量积压消息**：超过单次补拉上限后仍能完整恢复，无重复、无缺口。
5. **长连接撤权**：撤销 Session、read、supervise 后验证旧连接行为。
6. **发送准备阶段失败**：新会话创建失败仍保留输入与重试入口。
7. **访客合并失败**：网络故障与事务失败后可恢复，不提前丢失凭据。
8. **提醒准确性**：客户消息、自己的回复、内部备注分别验证提醒规则。
9. **邮件与已读**：关闭面板后在线标记未过期期间收到回复，最终未读时仍有可靠提醒。

涉及实现修改时，按对应子项目 `AGENTS.md` 执行类型检查和测试；服务端核心逻辑使用 Docker `check` 服务验证，避免集成测试因缺少环境变量而被跳过。

## 7. 审查边界

- 本文是当前源码的静态审查记录，不是运行验收报告。
- 未进行浏览器复现、网络故障注入、数据库并发实验或性能压测。
- 竞态问题的发生概率、撤权后的具体窗口和 Cookie 错误响应行为，需要针对性测试确认。
- 优化建议中涉及已读、在线和邮件提醒的语义，应先明确业务期望，再固化为验收条件。
