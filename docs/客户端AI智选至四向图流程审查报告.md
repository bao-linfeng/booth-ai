# 客户端 AI 智选至四向图流程审查报告

审查日期：2026-10-09

代码基线：`bce387e`（开始审查时工作区干净；收尾发现其他工作修改了服务端资产查询及其测试，本轮未改动这些文件）

范围：AI 智选筛选 → 方案详情 → AI 换主题 → 选定效果 → AI 四向图；附带核对登录、积分提交、询价交接。

术语：本文“四向图”指当前产品的正面、背面、左侧、右侧方向底图，即 `ArtworkJob` 的“四面素材”。

需求参照：`docs/灵通AI展台方案平台_一期客户端开发需求_v1.0.md:302-327,390-417`，包括换主题登录墙、原图/新图与失败重做，以及四面正交素材的预览、单张与整包下载。原始单图 30 秒目标需真实供应商计时，本轮未据代码推断达标。

## 1. 结论

**主流程已经实现，但刷新恢复、身份切换、同页路由切换及跨阶段上下文传递仍有缺口。应优先修复付费生成的幂等恢复和操作对象一致性，再处理筛选与出图后的可恢复性。**

已有的可靠性设计值得保留：

- 智选请求序号隔离、草稿恢复、过期结果提示，以及结果列表图片换签。
- 换主题的价格刷新、防抖、确认弹窗、同页面同请求键重试。
- 主题结果的“预览”和“选定”分离；保存采用版本校验，结果不确定时禁止继续。
- 异步任务同时使用 SSE 和 10 秒兜底轮询。
- 四向图固定主题结果及选择版本，服务端逐方向验收，四方向齐全才允许完整交付。
- 服务端同请求键重放、积分预占和任务 Outbox 事务写入。

本报告将**运行复现**、**静态确认**、**条件性风险**分开标注。客户端模拟网络测试不能证明真实模型质量、真实积分账本或生产网络均无问题。

本次重新核对了当前实现，未沿用旧审查中已经失效的结论：智选会话读写现已共用版本与校验；标准“智选 → 详情 → 询价”交接已有测试；匿名检索在正常登录时会通过 `linkVisitorToUser` 归属到用户。因此本报告的身份问题针对 visitorId 轮换后旧会话仍被恢复，而非断言匿名检索一律无法用于换主题。

## 2. 流程与关键交接字段

```text

    → requirements/parse（attemptId、parseId）
    → 澄清 / scheme-matches（searchId）
    → sessionStorage 保存需求与结果
    → SchemeDetail（code、searchId）
        → SchemeTheme（code、searchId、sourceAssetId）
            → theme-offers（5 分钟报价）
```

## 3. 问题清单

优先级：P1 = 可能重复预占积分、操作错对象或阻断重要流程；P2 = 特定操作下失败、数据交接错误或恢复困难；P3 = 局部展示/追踪问题。

### B01 · P1 · 换主题提交的幂等键仅在内存，刷新后无法确认原提交

**分类：客户端状态缺陷；重复预占属于满足指定时序的跨层风险，未执行真实扣费。**

**证据：**

- `apps/client/src/pages/SchemeTheme.vue:70,217,223-255`：确认对象保存在 `ref`，新确认生成 `crypto.randomUUID()`；未持久化待确认请求。
- `apps/server/src/modules/generation/theme/service.ts:115-125`：仅按用户和 `requestKey` 重放。
- 同文件 `:85-97,147-180`：缓存只复用完整成功任务；旧任务仍在 pending/running 时，新键会走新任务和积分预占。

**触发：**创建请求已被服务端接受，但回执丢失；用户刷新/离开后返回，重新确认相同参数，旧任务尚未完成。

**影响：**原任务无法通过原键恢复，存在重复创建及再次预占积分的路径。相同页面不刷新时的重试已复用原键，问题集中在跨页面生命周期。不能将此描述为“所有重试都会重复扣费”。

同类边界：提交结果不确定后，用户关闭确认框再改参数，`SchemeTheme.vue:144-149` 也会清除 confirmation。应保留原提交的可查询记录，而不是让参数编辑同时抹掉未确认任务。

**建议：**按用户保存完整待确认提交，包括请求键、报价、参数及状态；返回页面先恢复原请求，通过同键重放确认结果。确认已拒绝或用户明确发起新一轮时才新建键。存储失败应明确反馈，不能假装已可靠保存。

**验收：**模拟“服务端接受但客户端超时”，刷新后继续提交；只存在一个业务任务和一次积分预占。

### B02 · P1 · 同组件切换路由参数后，页面和操作仍可能指向旧对象

**分类：组件生命周期缺陷；运行复现范围见第 6 节。**

**证据：**

- `apps/client/src/App.vue:17`：无业务身份 key 的 `RouterView`。
- `apps/client/src/pages/SchemeDetail.vue:352-364`：只在挂载时加载详情。
- `apps/client/src/pages/SchemeTheme.vue:31-34,129-134`：方案编号、检索编号在 setup 中读取一次。
- `apps/client/src/pages/ThemeJob.vue:23,66-69,120,150`：任务编号固定，加载、保存选择及继续操作使用该编号。

**触发：**SPA 内从 `/schemes/A` 切到 `/schemes/B`，或从 `/theme-jobs/A` 切到 `/theme-jobs/B`，组件被复用而不是重新挂载。主题编辑页仅改变 `searchId` 也有相同上下文陈旧问题。

**影响：**地址栏已是 B，但详情、下载、主题生成或选择保存仍可能是 A。普通“列表 → 详情 → 返回列表”未必触发，不能以此路径正常排除问题。

**建议：**页面监听自身业务身份并重置、重新加载，旧请求使用序号/取消机制丢弃。或对需要隔离的路由按业务身份设置 key；不要不加区分地对所有 query 变化重挂整站。

同类模式也出现在 `QuoteRequest.vue:27-35`（只读取一次 code/任务 query）；本报告主要复核前三个页面，修复时应同步检查询价页，不能将仅修复详情页视为全链路已解决。

**验收：**真实路由复用下切换 code/jobId/searchId，画面、请求载荷、客服上下文和下游链接均与新身份一致。

### B03 · P1 · 退出登录函数递归调用自身，未调用服务端登出

**分类：代码可直接确认的函数遮蔽缺陷；运行复现范围见第 6 节。**

这是全链路的身份边界问题，尤其影响付费任务后的退出/换号。

**证据：**

- `apps/client/src/composables/useAuth.ts:4` 导入 API `logout`，`:43-46` 内部又声明同名函数并执行 `await logout()`，实际解析到内部函数本身。
- `apps/client/src/components/navbar/UserAvatar.vue:24,116` 将此函数绑定至真实退出菜单。

**影响：**递归直到栈溢出，随后可能多次执行清理和跳转；预期服务端会话撤销请求没有发出。构建通过无法发现这种业务递归。

**建议：**导入明确命名为 `logoutUser` 等并调用；退出进行中防重入，确保清理只执行一次。

**验收：**点击一次退出：API 登出一次、身份清理一次、导航一次，无栈溢出；服务端失败时也只执行一次本地清理。

### B04 · P1 · 身份清理后仍恢复旧智选 attemptId，后续匹配可能主键冲突

**分类：静态确认的跨层缺陷，数据库实际错误响应尚待集成验证。**

**证据链：**

1. `apps/client/src/stores/auth.ts:26-32` 清理身份时更换 visitorId。
2. `features/selection/session.ts:5,8-24` 智选存储使用固定 key，没有用户/访客归属。
3. `features/selection/useSelectionSession.ts:27-31` 恢复原会话；`useSelectionFlow.ts:217-219` 恢复旧 attemptId/parseId/searchId。
4. `apps/server/src/modules/selection-analytics/recording.ts:8-20` 先按 attemptId + visitorId 查找；查不到时仍使用传入 attemptId 插入。
5. `apps/server/migrations/027_selection_analytics.sql:1-7` attemptId 是全局主键。

**触发：**已有真实检索 → 身份失效或退出导致 visitorId 轮换 → 同标签页恢复智选并继续匹配。

另一入口是外部登录：`apps/client/src/router/external-login.ts:19-24` 在同步身份前调用 clearAuth，已有智选草稿同样需要处理归属变化。

**影响：**旧 ID 已存在但不属于新访客，插入会冲突；旧需求仍显示在新身份会话中，新账号进入旧 searchId 的换主题页还可能被服务端拒绝。

**建议：**智选会话记录身份归属；身份变化时清除或显式迁移非敏感需求，并重新生成 attemptId，清空服务端归属 ID。服务端不要把“已存在但不属于当前访客”的 ID 再次插入；返回明确错误或生成新 attemptId，不能绕过归属校验。

**验收：**检索后退出、登录另一账号、令牌失效重登、多标签页 visitorId 变化，均不复用旧身份 ID、不产生 500、不自动带入前账号需求。

### B05 · P2 · 手动删除已解析描述后，仍发送空文本解析请求

**分类：客户端状态与后端校验契约冲突；运行复现范围见第 6 节。**

**证据：**

- `apps/client/src/features/selection/useSelectionFlow.ts:57,164-174`：先判断 `textChangedSinceParse` 并解析，再检查是否有有效文本。
- `apps/server/src/http/client/selection/index.ts:41`：解析文本要求 `minLength: 1` 且包含非空白字符。

**触发：**输入描述并成功匹配 → 编辑描述 → 用退格删空或只留空格 → 保留表单条件并点击匹配。

**影响：**本应按表单继续匹配，却调用非法的空文本解析并进入错误状态。使用页面“清空输入”按钮会清解析状态，所以两种清空方式行为不一致。

**建议：**先规范化并判断有效文本；空文本时清理解读状态并按表单匹配，不调用 parse。统一键盘清空与按钮清空的状态转换。

**验收：**已解析后，分别通过退格、全选删除、仅空格和清空按钮清空，均不发送空解析请求。

### B06 · P2 · 主题结果继续询价时丢失 searchId，可混入另一轮智选需求

**分类：静态确认。**

**证据：**

- `ThemeJob.vue:148-150` 继续询价/四向图仅传 `themeJobId`，尽管任务数据有 `searchId`。
- `ArtworkJob.vue:192` 继续询价只传 `themeJobId`、`artworkJobId`。
- `QuoteRequest.vue:31,46` 从本地当前智选会话取需求并随申请提交。
- `features/selection/handoff.ts:31-41` 仅在传入 searchId 时严格匹配；未传时只检查当前会话及方案编号。
- `apps/server/src/modules/projects/snapshot.ts:73-100` 校验主题结果版本，但需求取提交的 requirementContext 重新计算；不会自动从主题的 searchId 纠正客户端带错的需求。

**触发：**检索 S1 选中方案 A 并生成主题 T1 → 在同标签页另做检索 S2，也返回方案 A → 打开历史主题 T1 并继续询价。

**影响：**T1 的主题可能携带 S2 的需求；没有本地草稿时又可能丢失原始需求。这不是旧报告中的会话版本不匹配，而是新链路的身份字段丢失。

**建议：**由任务的可信 searchId 恢复原始需求上下文，跨阶段持续传递并严格核对；未知来源时宁可不附带需求，也不要仅凭方案编号猜测。若历史询价要求完整恢复，应从服务端读取该次检索。

**验收：**同方案两次不同检索，历史主题/四向图询价只能使用原检索需求；不接受当前会话的另一轮需求。

现有 `apps/client/tests/theme-job.test.mjs:149-162` 断言下游 query 只有 themeJobId，因此现有测试通过也不能覆盖需求来源一致性；需要增加真正的“主题结果写入路由 → 询价页读取需求”测试。

### B07 · P2 · 四向图存储异常会干扰任务提交和成功回执处理

**分类：代码确认的异常分支问题，触发依赖浏览器存储失败；运行覆盖见第 6 节。**

**证据：**`apps/client/src/pages/ArtworkJob.vue:82-88,116-130`。

- 读取 sessionStorage 失败被笼统归为“无法确认上下文”。
- 先设置内存 pending，再执行 `setItem`，最后才提交请求；写入抛错时第一次点击未发请求，但提示“本次提交已保留”。
- 请求成功后先 `removeItem` 再跳转；删除失败时回执已获得，却仍停留在提交不确定状态。

**触发：**浏览器存储被策略阻止、写入配额耗尽，或存储 API 抛异常。

**影响：**用户难以区分未提交、已提交和已保存重试信息；下一次点击可能从内存继续，但刷新不一定可恢复。

**建议：**分别处理存储失败与网络结果；保存失败明确告知恢复能力受限，按明确策略阻止首次付费提交或提供可靠恢复渠道。已拿到成功回执时不能因为清理本地存储失败阻止进入任务页。

该项也需注意提示准确性：存储写入失败时，内存 pending 仍可能存在，下一次点击可尝试原键；因此不能笼统称为“彻底无法提交”，实际缺陷是首次行为与提示不符，以及刷新恢复不可靠。

**验收：**分别注入 getItem/setItem/removeItem 异常，核对真实请求次数、提示、保留的请求键和导航结果。

### B08 · P2 · 图片签名过期处理只覆盖智选列表，后续页面存在断点

**分类：静态确认的生命周期缺口；真实 S3 过期与浏览器缓存组合待验证。**

**证据：**

- `features/selection/useSchemeImages.ts:5-8,49-70` 仅负责匹配结果换签。
- 方案图片签名 300 秒：`apps/server/src/modules/selection/repository.ts:158-166`；详情和主题编辑页只加载一次。
- 主题结果签名 900 秒：`apps/server/src/http/client/theme-jobs/index.ts:64-71`。
- 四向图签名 300 秒：`apps/server/src/modules/generation/artwork/queries.ts:63-77`。
- `useAsyncJob.ts:113-120` 终态停止轮询；`ThemeJob.vue` 正常成功视图没有通用刷新入口，图片无重新签名错误恢复。

**触发：**页面停留超过有效期，再打开尚未加载的大图、切换图片，或浏览器重新发起图片请求。

**影响：**可用资产显示为失败/破图。已缓存的图片可能仍可见，因此不能断言“过期瞬间所有图都会消失”。四向图有手动刷新，主题结果恢复入口较弱。

**建议：**对实际可见页面在重新可见、接近过期或图片失败时重新取链接；保留当前 assetId/resultId。图片获取状态与任务生成状态分开，避免为换签长期轮询已完成任务。

**验收：**模拟过期 + 缓存未命中，详情大图、主题结果和四向图均能恢复，且不会改变用户选择或新建生成任务。

### B09 · P2 · 四向图报价过期后首次提交必然失败，缺少明确报价刷新流程

**分类：静态确认。**

- 后端报价 TTL 为 300 秒：`apps/server/src/modules/generation/artwork/offers.ts:8-23`。
- 前端类型包含 expiresAt，但 `ArtworkJob.vue:111-130` 提交不检查有效期，也不预先刷新报价。
- 除 401/402 等少数状态外，4xx 一律提示“主题选择或费用已变化，请刷新并重新确认”，不区分 `OFFER_EXPIRED`、模型不可用、参数错误。

**触发：**进入四向图创建页后停留超过 5 分钟，再首次点击生成。

**影响：**多一次可避免的失败和手动刷新。服务端拒绝过期报价是正确行为，问题是客户端缺少恢复交互，并非服务端错误扣费。

**建议：**新提交前获取有效报价；价格变化时展示并重新确认。已提交但回执不确定的 pending 请求必须优先用原键重放，不能因报价过期先换键。按稳定 reason 展示对应恢复动作。

**验收：**报价过期、价格变化、模型不可用、已接受但丢回执等场景走不同且正确的恢复路径。

### B10 · P3 · 清空描述按钮未清 parseId，检索记录会关联旧解析

**分类：客户端请求上下文残留；运行复现范围见第 6 节。**

**证据：**`useSelectionFlow.ts:89-95` 清空 parseResult 和 parsedRequirement，但未清 parseId；`:145-147` 仍发送该 ID。服务端 `selection/service.ts:81-85` 将其写入检索记录。

**影响：**界面显示按表单筛选、textProvided=false，但记录仍挂在旧描述解析上，干扰追踪与分析。不直接等同于匹配算法使用了旧文本。

**建议：**明确“清空描述”转换，清除解析 ID 和澄清确认状态；保留用户确认的表单字段时明确告知。

**验收：**解析 → 清空输入 → 表单匹配，请求不带旧 parseId，新记录不引用旧解析。

### B11 · P3 · 主题失败原因展示为未翻译的 GENERATION_FAILED

**分类：静态确认。**

- 服务端 `http/client/theme-jobs/index.ts:88` 对失败返回 `GENERATION_FAILED`。
- 客户端 `features/theme-jobs/labels.ts:25-32` 只映射其他三个原因，未知值原样返回。
- `ThemeJob.vue:238` 将该文本直接展示。

**影响：**真实失败时用户看到内部代码，无法理解原因及下一步；现有失败原因映射与实际响应不一致。

**建议：**补齐实际契约中的通用失败原因、多语言友好 fallback；后续按可对外公开的稳定原因区分重试、服务不可用等，不把供应商原始错误直接输出。

**验收：**使用后端真实 failed 响应，页面不显示内部英文枚举，积分释放状态与重试入口明确。

## 4. 可优化项

以下不全部视为 bug，需按产品价值排序。

### O01 · 优先 · 将“主题选择”作为明确版本交接，避免跨标签页悄然换图

当前 `ThemeJob.vue:150` 只传 themeJobId，下游 `ArtworkJob.vue:76-81` 重新读取“当前选择”。若另一标签页在两步之间改变选定结果，下游会拿到另一张图；服务端后续版本校验正确，但无法验证用户离开上页时想用哪张。

建议传递/核对预期 resultId、selectionRevision，不一致时展示变化，要求用户确认。若产品明确规定始终采用最新选择，则界面需要清楚表达，不能同时暗示一直固定上一页选择。

### O02 · 优先 · 主题偏好继承智选条件，并保存编辑草稿

`SchemeTheme.vue:112-113` 默认选目录中的第一行业、第一风格，没有继承智选；页面刷新、返回修改或失败后“重新生成”会重新初始化品牌参数。

建议按同一 searchId 的已确认行业/风格预填；多选来源需让用户明确选择。品牌色、关键词、张数、源图按用户和方案保存草稿，与待确认付费请求分别管理。

### O03 · 优先 · 四向图补真实页面与跨页面测试

现有测试覆盖智选、详情、主题编辑与主题选择，但未发现直接加载 `ArtworkJob.vue` 的独立页面测试。测试跳转到 artwork URL 不等于覆盖四向图创建、恢复、下载和绑定。

至少覆盖：选定主题 → 四向图创建 → 回执丢失后恢复 → 部分成功 → 单张下载 → 完整成功 → ZIP → 询价/项目绑定，以及 409、402、存储失败、参数切换。

### O04 · 中 · 未完成四向图优先继续查看，重做与补做要区分

创建页显示历史任务，但仍可创建相同上下文的整套任务。用户返回创建页不一定想重复生成；部分成功后的“重新生成”也是整套四方向，并非只补缺失方向。

建议显著展示正在进行的同上下文任务和“继续查看”；重做清楚提示重新预占四方向费用。只补失败方向属于新业务能力，需要明确版本与交付规则后再做，不要在 UI 上伪装成已支持。

### O05 · 中 · 明确四向图的质量边界，并提供大图检查

当前方向通过 prompt 约束，来源只有一张主题参考图：`apps/server/src/modules/generation/artwork/prompt.ts:19-38`。文件验收检查方向数量、格式、分辨率等，不等于验证背面/侧面几何正确。

建议四图使用已有预览组件放大比较，显示统一的前后左右基准及“方向底图”身份。用有结构真值的样例评估左右反转、背面复制、文字镜像、墙体新增等；不要把 `deliveryStatus=ready` 解释为可直接施工或印刷。现有“尺寸和印刷适配仍需确认”提示应保留。

### O06 · 中 · 筛选条件的展示与编辑能力对齐

`RequirementForm.vue:16-17,43-62` 常规表单主要提供标准尺寸与偏好，AI 解析后的 required/excluded 条件、关键词、自定义长宽等可出现在总结中，却没有统一的逐项编辑入口。

当解析结果有自定义长宽、但 boothSpaceId=null 时，标准尺寸下拉仍显示占位文字（`RequirementForm.vue:14,46`、`OptionSelect.vue:14-16`），用户很难从该控件看出当前实际尺寸。建议显示自定义尺寸摘要及编辑入口，避免看起来像尚未填写。

建议“查看全部条件”支持定位编辑，清楚区分必须满足、偏好、排除，允许单项移除。澄清页也应沿用同一能力，降低用户只能改写自然语言或全部重置的成本。

### O07 · 中 · 积分和错误恢复形成统一体验

主题页有余额和二次确认，四向图页展示预占但没有同等级的余额/确认交互；主题完成页仅展示“已结算”，不如四向图页的预占、扣除、退回明细完整。

建议统一展示本次最大预占、成功计费规则、实际结算、退回、无重复扣费的恢复入口。对 429/服务不可用/登录失效提供具体反馈，避免统一“网络失败”。

### O08 · 后续 · 小范围维护性与性能改进

- 详情、主题编辑、智选仍直接调用 `apiFetch`，可将实际重复的方案详情和目录读取收敛到已有 API 层，统一类型与错误处理。
- `apps/server/src/modules/selection/repository.ts:162-163` 返回的 thumbnailUrl 与原图 URL 相同，客户端标为缩略图并不意味着加载更小文件。可评估实际图片字节大小和移动端流量，再决定是否生成独立缩略图。
- `SchemeDetail.vue:73-89` 对每个图片资料并发取下载链接，可限制并发或按可见项加载，避免资料很多时瞬时放大请求。
- `ThemeJob.vue:22` 状态标签只计算一次，切语言后可能仍是原语言；改为响应式计算。已有的服务器匹配理由也需要明确语言切换后的刷新策略。
- 分阶段展示耗时/断线恢复状态，避免用户把 SSE 暂时断开误认为任务没有执行。

## 5. 建议修复顺序与验收矩阵

| 批次 | 工作 | 验收重点 |
| --- | --- | --- |
| 第一批 | B01、B02、B03、B04 | 不重复创建付费任务；不操作旧对象；退出只执行一次；换号后不复用旧身份 |

| 后续迭代 | O04～O08 | 降低重复操作与出图判断成本，改善转化和维护性 |

最小回归矩阵：

| 维度 | 必测场景 |
| --- | --- |
| 筛选 | 空白灵感、纯表单、自然语言、澄清、手动删空、清空按钮、重置、旧结果编辑 |
| 路由 | 同组件 A→B、只换 searchId、返回、刷新、历史任务直达 |

### 6.4 后续真实环境验收的最小数据准备

- 两个可登录测试账号，至少一个具有足够的测试积分。
- 两个已审核发布、资源齐全的方案；同一个方案能够被两组不同需求匹配，用于检索上下文交接验证。

- 真实浏览器中覆盖移动端视口、长时间后台挂起、存储限制和图片缓存未命中；这些行为不能全部由 happy-dom 模拟代替。
