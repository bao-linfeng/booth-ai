# 权限合并方案

> 状态：草案
> 日期：2026-10-22

## 背景

当前权限系统定义了 24 个模块、102 个权限码（`apps/server/src/modules/identity/permissions.ts`）。6 种资产类型各自拆出 read/upload/replace/update/delete/preview/download，字典管理拆出 7 个 CRUD 操作，AI 模型配置拆出 9 个操作——粒度过细。

目前只有 `ROLE_ADMIN` 一个角色（被授予全部 102 个权限码），但即将引入客服、销售、方案编辑、运营等角色。配置角色时需要在 97 个动作中逐一勾选，体验差且容易遗漏。

## 设计原则

1. 每个模块以 `read`（查看）和 `write`（编辑）两档为基础
2. 只在有明确角色隔离场景时保留独立动作（如发布/派单/主管监管）
3. 6 种资产类型合并为一个 `assets` 模块
4. `dashboard` 和 `workspace` 合并为一个仪表盘入口
5. `search-analytics` 合并进 `searches`

## 模块依赖（合并后）

合并前有 `moduleDependencies` 和 `actionDependencies` 两层依赖。合并后大幅简化：

```typescript
const moduleDependencies: Record<string, string[]> = {
  bom: ['schemes.read', 'dictionaries.read'],
  credits: ['users.read'],
  searches: ['users.read', 'schemes.read'],
  prompts: ['schemes.read'],
  assets: ['schemes.read'],
};

const actionDependencies: Record<string, string[]> = {
  'schemes.publish': ['schemes.write'],
  'customer-service.supervise': ['customer-service.reply'],
};
```

说明：
- 合并前 `assets-masks.upload` 依赖 `assets-renderings.read`、`assets-masks.preview` 依赖 `assets-renderings.preview`——合并为统一 `assets` 模块后，这些同模块内依赖消失
- `prompts.create`/`update` 依赖 `prompts.preview`——合并为 `prompts.write` 后消失
- `schemes.review`/`publish` 依赖 `schemes.readiness`——`readiness` 合并进 `schemes.read`，`review` 合并进 `schemes.write`，`publish` 只需依赖 `schemes.write`

#### 4. `http/admin/assets/index.ts` 重点改动

当前逻辑通过 `assetPermissionCode(type, action)` 动态拼权限码，按资产类型做细粒度检查。合并后：

- 删除所有 `assetPermissionCode` 调用
- `canViewImage` 函数简化为检查 `assets.read`
- 列表/详情路由统一用 `config: { permissions: ['assets.read'] }`
- 上传/替换/修改/删除在 handler 中统一检查 `requireAdminPermission(request, 'assets.write')`
- 下载/预览统一检查 `requireAdminPermission(request, 'assets.download')`

## 风险与注意事项

### 不可逆操作

- 旧迁移文件不可修改（SHA-256 校验），合并只能通过追加新迁移实现
- 新迁移执行后，`admin_roles.permission_codes` 中的旧码被替换为新码，**不可回滚**（除非再追加一个反向迁移）

### `assetPermissionCode` 删除的连锁影响

该函数被 10 处调用，每处都需要替换为固定的 `'assets.write'` 或 `'assets.download'`。函数本身有一个特殊行为：某些资产类型没有某个操作时（如效果图没有 download），返回一个目录外的码，`hasAdminPermission` 对其一律判为未授予。合并后这个边界逻辑不再需要——统一的 `assets.download` 对所有类型一视同仁。

### 历史权限码残留

`admin_roles.permission_codes` 中可能残留已废弃的码（如 `questions.*`），`resolveAdminPermissions` 会通过 `allPermissionCodes.includes` 过滤掉它们。简化迁移只映射已知旧码，未知码保持原样（被过滤掉不影响行为）。

### `customer-service/agents.ts` SQL 查询

该文件直接在 SQL 中拼接权限码字符串检查坐席资格，不走 `hasAdminPermission`。当前用的 `customer-service.read` 和 `customer-service.reply` 保留，不受影响。

### 前端 `accessSummary` 路由白名单

合并后 `Workspace` 路由名挂到 `dashboard` 模块的 `routes` 数组，只需 `dashboard.read` 即可看到两个仪表盘页面。
