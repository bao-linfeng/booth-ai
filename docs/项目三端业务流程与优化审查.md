### 1.1 总体判断

**三端的核心业务骨架已经比较完整，主要问题集中在跨页面数据交接、销售运营闭环和异常处理入口，而不是缺少大量基础功能。**

- **服务端**：事务、积分、资料快照、任务恢复等基础较扎实；复杂度主要集中在生成任务与积分一致性、多版本资料交接。SU、渠道归属、伙伴项目、客服上下文等接口仍是单行占位文件。
- **优先投入方向**：修复询价交接和检索历史隔离，确认项目数据范围，补齐运营待办，明确通知闭环，再优化复杂模块。

## 3. 业务缺口与优先问题

### B-01 智选需求未正确带入报价申请

**分类：已确认问题。优先级：第一批。**

证据：

- `apps/client/src/pages/AISelection.vue:103`：持久化会话版本为 `4`。
- `apps/client/src/pages/QuoteRequest.vue:63`：读取时仅接受 `selection.version === 2`。
- `apps/server/src/modules/projects/snapshot.ts:99`：服务端依赖 `requirementContext` 生成匹配摘要。

影响：用户智选后进入报价页，当前逻辑无法读取原始自然语言需求、已确认条件，以及供服务端重新计算匹配差异的上下文。报价仍可能提交成功，但销售拿到的项目缺少选型背景。

建议：把智选会话读写、版本和校验集中到业务模块，报价页通过统一方法取得交接数据。不要仅修改版本数字，否则后续改版仍可能发生相同问题。

验收标准：

- 从智选结果进入报价并提交，后台项目能看到原始需求、确认条件、匹配摘要。
- 过期或无效上下文不会被错误关联到其他方案。
- 无智选上下文直接进入方案报价时，仍能按预期提交。

### B-02 在线客服缺少正式接入

**分类：需求明确的待完成能力。优先级：第二批。**

需求依据：`docs/灵通_AI_展台方案平台_第一期需求书_v1.0.md:188` 要求询价进入在线实时客服。

当前检查客户端业务代码，未发现对应客服 SDK 或携带项目上下文的会话入口。服务端 `apps/server/src/http/client/customer-service/index.ts` 只有一行注释（“A6 客服会话上下文”），也未在 `http/client/index.ts` 注册。选型资料已有 `docs/LiveHelperChat_Zoho_SalesIQ_网易七鱼海外版_三方对比.md`，但尚未形成选型结论。

需求书 §9.1 还要求客服“全球节点可达、中文客服与海外客户可实时翻译沟通”，供应商选型时应一并验收。

影响：提交申请已经实现，但客户对方案适配、资料制作或报价时效有疑问时，仍缺即时沟通通道。

建议：在报价回执、项目详情、方案详情接入统一客服入口，携带方案编号、项目编号和经过授权的用户上下文，提供客服离线时的回退方式。

验收标准：客服端能识别咨询关联的方案或项目；客服离线时客户仍可留下需求；已提交的项目不因重复进入客服而重复创建。

### B-03 下次跟进时间尚未形成待办闭环

**分类：业务闭环不足。优先级：第二批。**

证据：

- `apps/admin/apps/web-antd/src/views/projects/OperationModal.vue:207`：有下次跟进时间字段。
- `apps/server/src/modules/projects/admin-service.ts:59`：校验该时间。
- 同文件 `:76`：保存至跟进事件。
- 当前项目列表缺少到期/逾期筛选，Worker 调度中未发现对应提醒任务。

影响：销售可以记录“下周联系”，但平台不会帮助找到“今天该联系谁、哪些已经逾期”。当前是记录字段，不是可执行待办。

建议最小闭环：

1. 明确当前有效的下次跟进时间。
2. 支持我的待跟进、今日到期、已逾期查询。
3. 完成跟进后更新或清除下一次计划。
4. 成交、关闭后停止提醒。
5. 在此基础上接入通知渠道。

验收标准：新建跟进计划后可在对应日期的待办中找到；改派后由新承接人处理；终态项目不继续产生无效提醒。

### B-04 默认承接策略隐含在代码中

**分类：业务规则已确认并实现（2026-10-07）。优先级：第一批。**

原始证据：默认选取最早创建、启用且拥有跟进权限的管理员；无合格人员时返回 `ASSIGNMENT_UNAVAILABLE`（503），业务规则隐含在代码中。

确认口径：

- 报价申请和人工需求统一分给后台显式指定的默认承接人；该人员须已启用，并具备有效的 `projects.read` 和 `projects.follow-up` 权限。
- 未配置、人员停用或权限失效时暂停新需求受理，不自动换人，不进入待分配池。返回 503 与稳定业务原因 `ASSIGNMENT_UNAVAILABLE`；不创建项目、事件、通知或成功回执。客户端保留填写内容，明确提示未受理，可稍后提交或咨询客服。
- 已受理请求的同键同体重放返回原回执，不因承接配置失效重复创建或否认原受理结果。
- 已有项目保留负责人及历史记录；失效负责人不能继续跟进，后台列表 / 详情显示异常，由具备 `projects.assign` 权限的人员人工改派。终态项目保留历史负责人，重开后才能改派。
- 项目列表顶部展示接单状态与失效原因；配置修改复用分配权限，有修订冲突检测及审计记录。更改默认人只影响新申请。
- 迁移 `066_project_assignment_config.sql` 创建空配置，需要后台显式指定，不将旧代码的隐式选择固化成业务决定；已有项目不迁移负责人。

实现入口：`apps/server/src/modules/projects/assignment.ts`、`admin-service.ts`，管理后台 `views/projects/AssignmentConfig.vue`。

验收：未配置 / 停用 / 撤权阻止新增申请且无残留；配置恢复后正常分配；已有项目保持负责人、授权人工改派；并发配置只接受一个修订；客户端明确区分未受理与网络结果未确认。

验证记录（2026-10-07）：服务端两套类型检查及默认测试通过（297 通过、20 跳过）；六个相关 PostgreSQL 集成测试文件实际执行，18 通过、0 跳过，覆盖配置、两类受理、撤权、改派、幂等与真实 HTTP 错误响应。管理端类型检查、客户端类型检查及构建通过。开发栈已应用迁移 066，API / worker 健康；默认承接人为 null，需后台显式配置后才能恢复新受理。

页面运行验证：隔离 Chrome + mock API 实际验证管理端四种接单状态、行内配置、保存失败保留选择；客户端两类申请在已知承接 503 后保留表单并恢复编辑，在未知 503 后保留原 requestKey 重试。已检查桌面 / 手机截图；此项不包含真实 SSO 或真实业务写入。

### B-05 项目消息通知未覆盖完整事件链

**分类：业务闭环不足。优先级：第二批。**

证据：

- 新项目受理写入通知：`apps/server/src/modules/projects/service.ts:27–28、60–61`。
- 补齐四面素材写入通知：`apps/server/src/modules/projects/artwork-delivery.ts:32–34`。
- 项目改派仅记录事件：`apps/server/src/modules/projects/admin-service.ts:50–51`，未对应写入通知。
- 通知重试耗尽后标记失败：`apps/server/src/modules/projects/notifications.ts:43–47`。
- 通知接口当前为查询和已读：`apps/server/src/http/admin/project-notifications/index.ts:17–27`，未提供人工重投操作。
- 外部投递依赖 webhook 配置：`apps/server/src/worker.ts:115–120`；未配置时保留待投递事件。这不等于站内收件箱不可用。
- 站内收件箱不按收件人过滤：`apps/server/src/modules/projects/notification-inbox.ts:34–49` 对所有拥有 `notifications.read` 权限的管理员返回全部项目通知，只记录各自的已读状态（另见 B-09）。
- 跟进记录、报价修订、状态变化只写 `project_events`，不进入通知 Outbox（`admin-service.ts:76、108`）。
- 客户侧没有任何通知：项目状态或公开结果（`public_result`）更新后，客户只能主动打开“我的项目”查看。

影响：新承接人可能无法通过消息中心得知改派；所有通知对所有有权限的管理员可见，人数增加后会变成噪声；外部投递失败后，缺少业务人员可操作的补偿入口。

建议先明确通知矩阵：

| 事件 | 应通知对象 |
| --- | --- |
| 新需求受理 | 承接人/接单岗位 |
| 项目改派 | 新承接人 |
| 客户补齐资料 | 当前承接人 |
| 跟进到期 | 当前承接人 |
| 外部投递失败 | 运维或指定管理人员 |
| 项目状态/公开结果变化 | 客户（是否通知、通过什么渠道，待业务确认） |

然后补失败重投、错误原因与处理记录。重投应沿用事件去重约定，不能造成重复业务操作。

工作台指标口径（均只统计当前管理员作为承接人的项目）：

- 进行中项目：状态为 pending / following / quoted 的项目数。
- 待受理：状态为 pending 的项目数。

- 最新动态：本人负责项目的最近 10 条项目事件；项目改派后，原承接人不再看到其动态。
- 未读消息：本人在消息通知中未标记已读的项目消息数。

### B-07 当前转化统计不等于询价或成交转化

**分类：经营优化项。优先级：第三批。**

证据：`apps/server/src/modules/selection-analytics/statistics.ts:35–41` 当前计算的是检索记录中有关联登录用户的独立访客数，占全部独立访客数的比例。字段名 `anonymousVisitors` 实际统计的是全部独立访客，包含已登录访客，命名容易误导。

该指标不能直接回答哪些方案带来了询价、品牌调整是否提升成交、用户在哪一步流失。

关联现状：

- 检索 → 主题生成：已有确定性关联，`theme_jobs.search_id`（`apps/server/migrations/044_theme_job_search.sql`）。
- 检索 → 报价/人工需求项目：智选会话已有 `searchId`，但报价输入（`apps/server/src/modules/projects/domain.ts`）与 `projects` 表均无检索关联字段。

对照页面清单 §6.1（AP-21）规定的统计范围，当前实现还有以下缺口：

| 规定内容 | 当前情况 |
| --- | --- |
| 0 命中需求排行（缺口需求清单） | `selection-analytics/recording.ts:84` 已记录 `zero_match_reasons`，但统计接口与看板只给出无匹配次数，没有按原因或条件聚合 |
| 热门筛选偏好（面积、开口、行业、风格） | 热门需求词只统计 `mode='filtered'` 的需求词，没有结构化条件排行 |
| 活跃设备与用户检索频次分布、单次选型时长 | 未实现 |
| 浏览器指纹 | 实际为客户端 `localStorage` 中随机生成的 `v_<uuid>`（`apps/client/src/lib/api-client.ts:8–15`），清除站点数据或更换浏览器即变成新访客，不是指纹 |
| 记录客户端 IP 与 User-Agent | `selection_searches` 表（`027_selection_analytics.sql`）没有这两列 |

IP、UA 与指纹涉及个人信息，是否采集、保留多久，应先与合规要求确认，不建议直接补采。

建议：先统一指标口径与名称，再从“检索 → 项目”这条确定性关联补起，建立检索 → 选方案 → 生成 → 询价 → 报价 → 成交的链路，避免仅靠用户与时间窗口推测来源。

验收标准：每个指标有明确分子、分母、时间口径与去重规则；可从统计结果追溯到对应记录；页面清单 §6.1 与实际统计范围一致（未做的项从清单中移除或排期）。

### B-08 访客检索历史会带出登录用户的记录

**分类：已确认问题。优先级：第一批。**

证据：

- `apps/client/src/lib/api-client.ts:8–15`、`:54`：访客 ID 存在 `localStorage`，所有请求都携带 `x-visitor-id`。
- `apps/client/src/stores/auth.ts:23`：`clearAuth()` 退出登录时不轮换访客 ID。
- `apps/server/src/http/client/searches/index.ts:48–52`：未登录时按访客 ID 查询历史。
- `apps/server/src/modules/selection-analytics/queries.ts:27–33`：按 `visitor_id` 查询时没有排除 `user_id IS NOT NULL` 的记录。

场景：同一浏览器上，用户 A 登录后检索，检索记录同时写入 A 的用户 ID 和该浏览器的访客 ID；A 退出后，任何人在该浏览器打开“我的检索”，都能看到 A 登录期间的检索原文（可能包含公司名、品牌、预算）和结果。展会现场、代理商共用电脑时尤其容易发生。

建议：访客查询只返回 `user_id IS NULL` 的记录；退出登录时轮换访客 ID。如需支持“登录前检索并入账号”，应在登录时显式迁移，而不是让访客身份读取账号数据。

验收标准：登录用户的检索在退出后不能以访客身份查询；新增的回归测试覆盖“登录检索 → 退出 → 访客查询”。

### 5.4 服务端生成任务恢复策略

**分类：已处理（2026-10-07）。人工重试、取消、退还积分入口仍未提供。**

原始问题（行号对应修复前版本）：

- `apps/server/src/workers/theme-outbox.ts`、`artwork-outbox.ts`：主题与四面素材分发实现不对称——主题分发检查任务状态并重试已保留的终态队列记录，画稿分发直接 `add`。
- `reconcileThemeOutbox` 与 `recoverPendingGenerationJobs` 对“pending/queued + 队列 failed/completed”给出相反处置（前者重试、后者结算），结果取决于两个定时任务的执行顺序。
- `recoverGenerationJobs` 没有逐条隔离错误，一条任务出错会中断整轮扫描，并跳过画稿。
- 后台只有列表和详情两个 GET 接口；`reconcileJobCredits` 无法修复的 `issues` 只写 warn 日志，后台看不到。

处理结果：

- 分发合并为 `apps/server/src/workers/generation-outbox.ts`：两类任务语义一致（锁任务行、跳过已离开 pending/queued 的任务、提交后推送 `queued` 事件）。已存在的队列记录交给恢复器处理。
- 恢复合并为 `apps/server/src/workers/generation-recovery.ts`，由纯函数 `decideRecovery` 表达恢复矩阵（数据库状态 × 队列状态 × 租约/截止时间 → 重入队、重试、结算或等待），删除 `reconcileThemeOutbox`。每条任务单独隔离错误，结果写入 Worker 日志。
- 矩阵要点：运行中任务过了截止时间就结算；队列记录丢失就重入队；pending/queued 遇到队列 failed 时结算（从未被认领，没有截止时间约束，重试可能无限循环并长期冻结积分），与 Worker failed 处理器一致；运行中任务遇到 failed、或任何任务遇到 completed 时重试。
- 故障场景由测试覆盖：Redis 丢任务、进程在 add 前后被杀、COMMIT 失败、生成完成但结算失败、租约争用耗尽重试（`generation-outbox-integration`、`credit-invariants-integration`、`generation-recovery` 测试）。
- 对账结论写入 `theme_jobs` / `artwork_jobs` 的 `credit_issue`、`credit_issue_at`（迁移 `071`），修复后自动清空。后台生成任务页可以按“积分对账：异常”筛选，列表会显示异常标签，详情页会说明异常原因。

仍待处理：后台人工处置入口（重试、取消、退还积分）需要先明确权限与审计要求，这次没有实现。

### 6.2 核心集成测试在标准检查中全部跳过

服务端积分、项目、资产隔离、Outbox 等集成测试依赖专用数据库/Redis 环境变量，缺少配置时跳过。

这不只是“可能”：`apps/server/tests/` 中有 17 个测试文件含依赖环境变量的用例，共涉及 10 个变量（`PROJECT_`/`CREDIT_`/`THEME_`/`ASSET_`/`ARTWORK_`/`BOM_`/`SELECTION_`/`AI_MODEL_`/`PROMPT_TEMPLATE_TEST_DATABASE_URL` 与 `THEME_TEST_REDIS_URL`）。而文档推荐的检查入口 `infra/compose.dev.yaml:137–145` 的 `check` 服务直接执行 `npm run test`，没有设置其中任何一个变量。因此按标准流程执行时，项目、积分、生成恢复、通知收件箱、检索历史等数据库集成用例全部跳过，输出中只显示为 skipped，而同文件里的单元用例照常通过，容易被误读为“测试通过”。

仓库没有 CI 工作流（无 `.github/workflows`），`lefthook.yml` 也只是未启用的示例模板，提交和推送都不会触发任何检查。

建议检查结果明确列出：

- 已执行通过。
- 已执行失败。
- 因环境缺失跳过。
- 未覆盖的关键场景。

本项目复杂逻辑涉及真实事务与队列，不能只依赖类型检查或 mock 测试证明可靠。建议在 `check` 服务中创建独立测试库并注入上述变量，让集成测试默认执行。本次未执行测试，不给出运行通过结论。

## 8. 后续验收建议

针对高价值链路执行真实环境验收，并记录测试数据、操作步骤、结果与跳过项：

1. **选型询价**：智选 → 详情 → 报价 → 后台查看完整需求。
2. **人工需求**：无匹配 → 人工提交 → 后台关联方案 → 报价跟进。
3. **生成扣费**：费用确认 → 生成成功/部分成功/失败 → 积分结算核对。
4. **资料交付**：主题选择 → 四面素材 → 下载 → 项目绑定。
5. **资料变更**：方案或清单更新后，旧页面提交/下载得到明确结果；已受理项目快照保持一致。
6. **销售承接**：受理 → 改派 → 下次跟进 → 报价发送依据 → 终态/重开。
7. **通知补偿**：渠道失败 → 自动重试 → 失败可见 → 人工处置。
8. **故障恢复**：队列丢任务、进程退出、结算中断后的任务状态与积分一致性。
9. **隐私隔离**：同一浏览器登录检索 → 退出 → 访客查看“我的检索”，不应出现登录期间的记录。
10. **数据范围**：非承接人尝试跟进、报价、改派他人项目，结果与 B-09 确认的规则一致。
11. **SU 进入**：SU 带 `token` 打开网页 → 静默登录 → 进入指定方案 → 主题生成扣费，核对积分归属（依赖 4.2 的边界结论）。
12. **性能基线**：按需求书 §9.1 核对智选响应 ≤5 秒、图生图单图 ≤30 秒；智选统计已提供 `p95DurationMs`，可直接作为依据。

## 9. 最终建议

**先把“客户需求完整交给正确的人，并确保有人按时处理”做扎实，再扩展 AI 功能。**

当前明显短板位于这一段。优先修复数据交接、建设真实工作台和跟进通知，通常比增加更多生成参数或经营图表更能改善一期业务效果。
